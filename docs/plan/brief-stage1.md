# Задача: каркас прототипа ситибилдера с упором на симуляцию трафика

## Контекст
Делаю 3D-градостроительный симулятор, сердце которого — симуляция трафика.
Продуктовая цель: город уровня Cities: Skylines 2, минимум 100k жителей, с заделом на 1M.
Сейчас — прототип на Godot 4 + C# ради быстрых итераций. Позже ядро симуляции
переедет на Rust (через godot-rust/gdext), поэтому архитектура с первого дня
готовится к этой миграции. Графика пока примитивная; в будущем — low-poly мультяшный стиль.

Цель этого прогона (этап 1): 1 000 машин + базовый общественный транспорт (автобусы)
одновременно ездят по процедурному городу; есть замеры производительности и качества трафика.

## Архитектурные правила (портируемость на Rust)
1. Sim.Core не знает про Godot: ни одного `using Godot`, никакого ввода, рендера, файлов.
2. Data-oriented: агенты — struct в плотных массивах (SoA, где это даёт выигрыш).
   Сущности адресуются целочисленными handle (index + generation). Никаких ссылок между
   объектами, наследования сущностей и class для агентов.
3. Горячий цикл без аллокаций: 0 байт на тик в стационарном режиме. В Sim.Core запрещены
   LINQ, замыкания, boxing, string, исключения в горячем пути, System.Random, DateTime.Now,
   Console, async/Task (enforce через Microsoft.CodeAnalysis.BannedApiAnalyzers).
4. Детерминизм: фиксированный тик dt = 1/20 с, собственный seeded PRNG (PCG или xoshiro),
   фиксированный порядок обновления. Тест: одинаковые seed + сценарий -> одинаковый хэш
   состояния после N тиков.
5. Узкое C-подобное API как будущий FFI: Simulation.Create(ScenarioDesc), Step(int ticks),
   Enqueue(in Command) с плоскими struct-командами (BuildRoad, SpawnTrip, SetSignalPlan...).
   Состояние наружу — только снапшот-буферы ReadOnlySpan<VehicleRenderData>
   (позиция, курс, тип, id). Клиент не трогает внутренности ядра.
6. Сценарии и параметры — JSON, независимый от языка: Rust-версия будет гонять те же файлы,
   и метрики можно будет сравнить один в один.
7. Каждое значимое решение — короткий ADR в docs/adr/ (контекст, решение, последствия).

## Симуляция (этап 1)
- Дорожная сеть: граф полос. Сегменты с N полосами в каждую сторону и лимитом скорости;
  на перекрёстках — connector-полосы под разрешённые манёвры.
- Генератор города: seed-зависимая сетка примерно 3x3 км, артерии 2+2 полосы, улицы 1+1,
  несколько нерегулярных узлов, параметр масштаба для сценариев побольше.
- Движение: IDM для следования за лидером; упрощённый MOBIL для смены полосы
  (подготовка к повороту и обгон). Машины никогда не проходят сквозь друг друга.
- Перекрёстки: светофоры с фиксированным планом фаз; «уступи дорогу» и STOP на второстепенных;
  помеха справа по умолчанию; правило «не въезжай, если выезд занят».
- Маршруты: A* с весом = время в пути, кэш маршрутов по парам зон, бюджет запросов на тик.
- Поездки: зоны-источники и стоки, генератор OD-пар; машина появляется на краю или парковке
  и исчезает только по прибытии. Деспаун застрявших запрещён — вместо него метрика stuck.
- Автобусы: маршруты как последовательность остановок, остановки в кармане или у обочины,
  стоянка зависит от числа пассажиров; пассажиры пока — счётчик ожидающих; интервал настраивается.
- Типы ТС (car, bus): длина, ускорение, торможение — в JSON.

## Godot-клиент (этап 1)
- Машины через MultiMeshInstance3D (по одному на тип ТС), меши — коробки с цветом по типу;
  дороги — плоские ленты; здания отсутствуют или кубы-заглушки.
- RTS-камера: панорама, зум, вращение.
- Интерполяция между тиками: симуляция 20 Гц, рендер 60+ FPS.
- Оверлеи по горячим клавишам: тепловая карта загрузки сегментов, фазы светофоров,
  маршрут выбранной машины.
- Перф-HUD на F3: FPS, frame time, tick ms (p50/p95), число агентов, аллокации на тик, GC.
- Визуально проверить клиент в облаке ты не сможешь: добейся, чтобы проект собирался и
  импортировался без ошибок, а в отчёте перечисли, что мне проверить руками.

## Метрики и бюджеты
Команда `Sim.Headless bench --scenario <имя> --ticks N --out perf/results/<имя>.json`
пишет JSON:
- perf: tick_ms p50/p95/p99/max, ticks_per_sec, vehicle_updates_per_sec,
  alloc_bytes_per_tick (стационар), gc_gen0/1/2, peak_memory_mb, bytes_per_vehicle,
  pathfind_queries, pathfind_ms_p95
- traffic: avg_speed_kmh, avg_trip_time_s, trips_completed_per_min, stuck_vehicles
  (стоят >60 с игрового времени), gridlock_flag, bus_headway_deviation_s,
  топ-10 перекрёстков по пропускной способности (машин/мин)
Лестница сценариев: s1k (1 000 машин + 10 автобусных маршрутов), s10k, s100k, s1m (headless).
Бюджеты этапа 1 для s1k: tick p95 <= 1 мс, alloc = 0 B/тик, stuck = 0 за 30 мин игрового
времени. Для s10k/s100k/s1m бюджетов нет — только зафиксировать базовые цифры.
`compare` сверяет с perf/baseline.json: регрессия tick p95 > 10% или любые аллокации -> exit 1.
Baseline обновляется только командой `update-baseline` с объяснением в сообщении коммита.
Все цифры — только из реальных прогонов, никогда не придумывай и не округляй «на глаз».

## Дисциплина
### CLAUDE.md (до ~150 строк, по-русски)
Кратко: правила выше, команды build/test/bench/compare и Definition of Done —
сборка без предупреждений, тесты зелёные, bench-smoke s1k без регрессии, ADR при
архитектурном решении, baseline менялся только осознанно.
### Сборка
Directory.Build.props: Nullable enable, TreatWarningsAsErrors, AnalysisLevel latest-recommended,
EnforceCodeStyleInBuild. .editorconfig. BannedSymbols.txt подключён только к Sim.Core.
### Хуки Claude Code (.claude/settings.json + исполняемые bash-скрипты в .claude/hooks/)
Скрипты должны работать и в облаке (Linux), и в Git Bash на Windows; пути через
$CLAUDE_PROJECT_DIR; блокировка — exit 2 с понятной причиной в stderr.
- PreToolUse (Edit|Write): запрет `using Godot` в src/Sim.Core/**; запрет ручной правки
  perf/baseline.json (только через update-baseline).
- PreToolUse (Edit|Write): если во входном JSON хука нет agent_id (значит, пишет основная
  сессия-оркестратор), разрешать запись только в docs/** и CLAUDE.md, иначе exit 2.
- PostToolUse (Edit|Write, файлы *.cs): быстрая сборка затронутого проекта; при ошибке —
  exit 2, чтобы ты сразу видел ошибки компилятора.
- Stop: если в git diff есть изменённые .cs — dotnet test + bench-smoke s1k (2 000 тиков)
  + compare; при провале exit 2 с причиной. Проверяй stop_hook_active, чтобы не зациклиться.
- PreToolUse (Bash): защита main (дублирует рулсет GitHub) — запрет
  git push в main/master, любого push --force / --force-with-lease, git branch -D main,
  git reset --hard на main; exit 2. В main изменения попадают только через PR.
- SessionStart: если $CLAUDE_CODE_REMOTE = true — проверить и при необходимости поставить
  .NET SDK из global.json (через dotnet-install.sh), пробросить PATH через $CLAUDE_ENV_FILE.
  Это страховка: основной путь — setup script облачного окружения, его ставит человек.
### Git
.githooks/pre-commit: dotnet format --verify-no-changes + build + unit-тесты;
scripts/bootstrap.sh включает `git config core.hooksPath .githooks`. .gitignore под Godot и .NET
(.godot/ не коммитим), .gitattributes с LFS для *.glb, *.png, *.wav.
Conventional Commits, маленькие коммиты по шагам.
Без соавторства Claude: в .claude/settings.json задай "attribution": {"commit": "", "pr": ""}
и "sessionUrl": false внутри attribution (убирает трейлер Claude-Session и ссылку на сессию в PR).
Страховка: .githooks/commit-msg отклоняет коммит, если в сообщении есть «Co-Authored-By: Claude»
или «Generated with Claude Code».
### CI (.github/workflows/ci.yml)
На push и PR: restore, build -warnaserror, test, bench-smoke s1k + compare с baseline,
JSON-результаты как артефакт. Godot-проект в CI пока не собираем.

## Автономность и оркестрация
Основная сессия — оркестратор. Код она не пишет и файлы проекта сама не правит: только
планирует, раздаёт задачи субагентам, проверяет результаты, мержит и решает, что дальше.
Сама она пишет только docs/plan/*, docs/adr/*, docs/REPORT-*.md и CLAUDE.md.

Модели субагентов (параметр model у Agent):
- fable — творческие и архитектурные задачи: API ядра, модель перекрёстков, маршрутизация,
  генератор города, разбор профиля и выбор оптимизации, ревью ADR. Лимит Fable исчерпан -> opus.
- sonnet — обычная работа: реализация подсистем по готовой спецификации, тесты, бенчи,
  Godot-клиент, CI, хуки.
- haiku — рой для мелких правок: переименования, предупреждения, доки, однотипные тесты,
  правка JSON-сценариев.
Лимит одновременно работающих агентов: fable <= 3, sonnet <= 8, haiku <= 20.
Веди учёт в docs/plan/agents.md (агент, модель, задача, статус) и не превышай лимиты.

Как раздавать задачи:
- Каждая задача — самодостаточный бриф: цель, границы (какие файлы можно трогать), критерий
  готовности (какие тесты и метрики должны пройти), что запрещено. Субагент не видит этот разговор.
- Параллельные агенты работают в изолированных git worktree (isolation: "worktree"), каждый в своей
  ветке. Оркестратор мержит по одной ветке и после каждого мержа гоняет build + test + bench-smoke.
- Задачи, которые трогают API ядра или одни и те же файлы, не параллель: только последовательно.
- Результат агента проверяй по фактам (тесты, JSON метрик), а не по его отчёту.

Самоитерация без человека:
- Работай по docs/plan/roadmap.md: этапы -> задачи -> критерии готовности. Закрыл задачу — сверь
  метрики, обнови план, бери следующую. Человека может не быть часами — подтверждений не жди.
- Цикл: план -> раздача -> мерж -> проверка -> запись в отчёт -> следующая задача.
- Останавливайся (и объясняй в docs/REPORT-*.md) только если: необратимое решение с равными
  вариантами; три неудачные попытки подряд по одной задаче; нужен доступ, секрет или деньги;
  этап закрыт.

Сохранение:
- Перед любым большим изменением (рефакторинг API ядра, смена модели данных, правка > 10 файлов,
  мерж серии веток) — checkpoint: коммит + ветка checkpoint/<дата>-<суть>, push. Именно ветка, а не тег:
  GitHub-прокси облака не пропускает push тегов и удаление веток.
- После каждого успешного мержа — коммит и push; локальные ветки агентов удаляй;
  удалённые ветки после мержа PR удаляет сам GitHub.
- Если всё сломалось — откат к последнему checkpoint, а не латание поверх.

Мерж в main (делаешь сам, без человека):
- В main — только через PR. `gh pr` в облаке не работает (прокси закрывает GraphQL), поэтому REST:
  создать PR:  gh api repos/{owner}/{repo}/pulls -f title=... -f head=<ветка> -f base=main -f body=...
  статус CI:   gh api repos/{owner}/{repo}/commits/<sha>/check-runs
  мерж:        gh api -X PUT repos/{owner}/{repo}/pulls/<номер>/merge -f merge_method=squash
- Мержи, только когда все check-runs = success, а в описании PR есть before/after из bench.
  CI красный -> чини в той же ветке (через субагента), push, жди повторного прогона. В обход CI не мержи:
  рулсет GitHub такой мерж всё равно отклонит, обходить его не пытайся.
- Только squash-мерж: история main остаётся линейной. Заголовок PR — в формате Conventional Commits.
- После мержа: git fetch, новая рабочая ветка от свежего main, следующая задача из roadmap.
- Force push, переписывание истории и удаление main запрещены всегда.

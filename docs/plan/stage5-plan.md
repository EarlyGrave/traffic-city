# Этап 5 — черновик плана (2026-10-28, оркестратор)

Черновик на утверждение владельцу. Источник — техдолг `docs/REPORT-stage4.md` и `REPORT-stage3.md`.

## Цель этапа (предложение)
**Большой жилой город едет, игрок строит его руками.** Сейчас ядро умеет почти всё, но:
- s10k-res стоит в пробке;
- s100k не держит бюджет;
- в клиенте нет инструментов.

## Блоки

### 5.1 Затор s10k-res — первым (решение владельца 2026-10-28)
- **Симптомы:**
  - ожидания ≥ 60 с — 9.3 %;
  - поездок в минуту 343 → 222 при росте жителей в 2.6 раза;
  - `*-res` не выходят на рампу (~560 из 1 000 машин на s1k-res).
- **Шаг 1 — разбор (opus):** где стоят машины (узлы, повороты, парковки, выезды с участков), спрос против ёмкости сети.
- **Шаг 2 — исправление:** сеть, спрос или правила — по итогам разбора.
- **Приёмка:** бюджет ожиданий для `*-res` предлагает разбор, утверждает владелец.

### 5.2 Масштаб s100k ≤ 15 мс
- Сейчас 26.94 мс. Фаза 3 (маршруты) ≈ 4 мс в среднем.
- **Шаги:**
  - параллельные запросы фазы 3 (`scale.md` §7);
  - пороги timed-reroute (−27 % запросов, меняет поведение);
  - stuck s100k у светофоров и уступающих левых.
- **s1m:** дойти до полной загрузки, зафиксировать цифру.

### 5.3 Ожидания s10k-peds ≤ 0.15 %
- Сейчас 0.485 %. Идея — разнесённый переход `AtMedian`; цель 3.1 — p95 ожидания пешехода ≤ 30 с.

### 5.4 Тесты и метрики
- **Три res-теста на legacy:** откалибровать на профилях (агрегат против micro, поиск парковки > 20 с, `res_stuck`).
- **stuck в бенче:** сводка и JSON расходятся.
- **Нестабильный тест** `RenderView_LastWins`.

### 5.5 UI и инструменты в клиенте

## Решения владельца (2026-10-28)
Все три — по рекомендациям: цель A («большой город едет + инструменты»); после 5.1 — 5.2 и 5.5 параллельно; Rust-пилот на паузе.
Распределение: 5.1 (затор s10k-res) — локал; 5.2 (масштаб s100k) — облако, эталон бенча там же. 5.5 — после ответов владельца по `ui-spec.md` §14 и Figma (UI0).

> **2026-10-28: 5.1 разбор затора s10k-res (L45).** Причина — ёмкость, а не правила: `day_s` 3600, пиковый спрос ~8 900 car legs/мин при пропускной ~1 100–1 350; сеть насыщена с 06:20 первых суток и не восстанавливается (ко 2-м суткам ожидания ≥ 60 с ~34 %, `res_stuck` 143k). Не связано с RP8. `*-res` «без рампы» — критерий рампы не для режима жителей; stuck сводки = значение на последнем тике. Варианты A–D — `docs/design/res-congestion.md` §6, ждёт решения владельца.

> **2026-10-28, решение владельца по 5.1:** затор s10k-res — проблема теста, а не ядра: пробка при перегрузке — задача игрока. Делаем вариант 2: перекалибровать s10k-res под ёмкость сети (бюджет как для s10k) + стресс-тест перегрузки (очереди ограничены, город восстанавливается при падении спроса). Вариант A (одна машина на k поездок) — отложен до вопроса производительности больших жилых городов.

## 5.2 — ход работ (облако)
- **2026-10-28: спека P (агент 169):** `docs/design/routing-parallel.md`, ADR-0032. Параллельная фаза 3 даёт ≈ −3 мс
  (s100k `off` p95 ≈ 23.5–24 мс); 15 мс в `off` недостижимы — критерий K1 (`scale.md` §0) задан для `lod auto`.
- **2026-10-28: замер `auto` (агент 171):** контроллера L3 в ядре нет (S4/S5 не делались) — `auto` = `off`, meso 0.
- **Решение владельца 2026-10-28:** карт-бланш облаку на все оптимизации 5.2 по рекомендациям оркестратора; условие —
  **ни одна метрика не хуже прежней** (p95, 0 B/тик, ожидания ≥ 60 с, stuck, s1k/s10k/s10k-peds без регрессии).
  Порядок: P1 → P2 (фаза 3) ∥ освежение спеки S4/S5 (opus) → S4 → S5 → S7 лестница → верификатор → timed-reroute (если нужно).
  Захват расширен на `Api/`, `World/PhaseList.cs`, `Save/` (блоки LOD).

> **2026-10-28: 5.1b влита (L46).** s10k-res перекалиброван (`initial_fill` 0.07, ~11.2k жителей): ожидания ≥ 60 с медиана 0 % (было 33.8 % на пике 2-х суток), отмен и res_stuck 0, пик пула ~5.9k из 12k. Стресс-тест `ResOverloadTests` (SlowFact, `TC_SLOW=1`) на `s10k-res-overload`: очереди ограничены, 0 B — зелёный; «пул ночью опустошается» — Skip: при перегрузке город не восстанавливается (пул 11 999/12 000 в 05:00, ожидающих выезда 32k, сеть деградирует до gridlock).

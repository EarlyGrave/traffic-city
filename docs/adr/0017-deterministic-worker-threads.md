# ADR-0017: Детерминированные потоки-воркеры для фаз «чистых по машине» (5, 6, 10)

- Статус: принято, 2026-10-24 (шаг 2.4c). Номер зарезервирован ADR-0016 («резерв: 2 потока фазы 5») и `sim-lod.md` §10 п.5.
- Разбор и замеры: `docs/design/hotpath.md` §8. Затрагивает `core-api.md` §0 (I4), §3 (потокобезопасность), §7 (фазы 5, 6, 10),
  §10 (тест 0 B); `BannedSymbols.txt`. Не меняет правила движения и результат симуляции: **хэш состояния не зависит от числа потоков**.

## Контекст
После ADR-0016 (P1–P5) s10k: tick p95 4.33–4.74 мс при цели ≤ 4 мс, p50 ≈ 3.0–3.1. Разбор хвоста (hotpath.md §8.1):
- p95/mean = 1.30–1.42. Время фаз 4–10 на одном и том же тике двух прогонов **не коррелирует** (r = 0.005–0.05), а внутри
  прогона медленные тики идут сериями (автокорреляция на лаге 1 — 0.64–0.76) и замедляют все фазы разом: хвост — это эпизоды
  замедления общего 4-vCPU контейнера, **мультипликативный** шум. Он уменьшается только вместе со средним.
- Периодической работы, которую стоило бы размазать, почти нет: MOBIL уже разнесён по индексу (время фазы 5 по `tick % 10`
  ровное), а маршрутные всплески (детерминированные, r = 0.78 между прогонами: пересчёт весов раз в 600 тиков + волна кастомизации
  14 тиков × 20 000 релаксаций, хвост работы запросов до 60 000 релаксаций за тик) дают в p95 не больше 0.14–0.25 мс даже при
  идеально ровной фазе 3; бюджетами сценария достижимо −0.02…−0.13 мс.
- Внутри фазы 5 (≈ 40% тика): поиск лидера ≈ 15%, `ObstacleGap` ≈ 10%, IDM ≈ 5%, MOBIL ≈ 3%, остальное — проход по памяти.
  Обход фазы 5 по полосам замерен: **+7%** к фазе 5 (хэш тот же) — отвергнут.
- Фазы 5, 6, 10 пишут только поля машины `i` (core-api §7) и читают состояние, которое в этой фазе никто не пишет.
  Подтверждено: прототип с обходом по полосам и прототип на 2 потоках дают тот же хэш s10k (tick 6100 `861672e99fa95a39`,
  6300 `c73832373fb67bd3`). Общие записи в дереве вызовов фазы 5 — только счётчики `SimWork` (через `ref`).
- Прототип «фаза 5 на 2 потоках» (копия кода, не в репо), s10k, 3 пары прогонов поочерёдно, load ≈ 1.2–1.5:
  tick p95 **4.71/4.35/4.38 → 3.68/3.71/3.47 мс** (−19% в среднем), p50 3.37/2.90/2.88 → 2.95/2.76/2.45, фаза 5 mean 1.32 → 0.84 мс (×1.57).

## Решение
1. **Исполнитель диапазонов в ядре** (`Sim.Core/Util/WorkerPool.cs` или аналог): `W − 1` постоянных потоков-воркеров, создаются в
   `Simulation.Create`, останавливаются в `Dispose`; главный поток — воркер № 0. Задание фазы — число чанков (диапазоны индексов
   `[k·C, min(HighWater, (k+1)·C))`, `C` = 256 по умолчанию) и предвыделенный объект задания фазы (без делегатов-замыканий).
   Чанки раздаются динамически атомарным счётчиком; главный поток работает сам и **не ждёт воркер, который не успел начать**
   (CAS-«заявка» воркера на участие; если главный выбрал все чанки раньше — заявка отменяется). Ждать можно только чанк, уже
   взятый воркером. Воркер между тиками спит на событии; главный будит его в начале `Step`, в пределах `Step` воркер крутится
   (spin без `Sleep`) — политика spin/park выбирается замером в P6.
2. **Контракт параллельной фазы** (проверяемый): функция машины `f(i)` читает только данные, которые в этой фазе никто не пишет,
   пишет только элементы `[i]` своих выходных массивов и **локальные аккумуляторы воркера**. Аккумуляторы — только целые
   (`SimWork`, `HardClamps`): сумма не зависит от порядка. Вещественные аккумуляторы в параллельных фазах запрещены (если понадобятся —
   частичные суммы по чанку, слияние в порядке номера чанка, статическая нарезка). Никаких ленивых кэшей, общих scratch-буферов, PRNG.
3. **Распараллеливаются фазы 5 (P6), затем 6 и 10 (P7).** Фазы 1–4, 7–9 остаются последовательными (пишут общие списки, билеты,
   очереди). Порядок фаз и обход «по возрастанию индекса» для последовательных фаз не меняются.
4. **Число потоков — параметр среды, не сценария**: `Simulation.Create(desc, in SimRuntimeOptions { WorkerThreads })`, по умолчанию 1
   (поток не создаётся, код как сейчас). Не входит в хэш, сейв, JSON сценария. Хэш при 1, 2, 3 потоках обязан совпадать (тест).
   `bench --threads N` (по умолчанию 1), JSON пишет `threads`; `compare` отказывается сравнивать прогоны с разным `threads`.
   Гейт s1k и `perf/baseline.json` — при `threads = 1` (s1k 0.5 мс, потоки там не нужны). Godot-клиент — `min(2, ядер − 1)`.
5. **Правила ядра**: I4 переформулируется: «детерминизм не зависит от числа потоков; параллельны только фазы с контрактом п.2».
   `System.Threading.Tasks` по-прежнему запрещён; в `BannedSymbols.txt` добавить `T:System.Threading.ThreadPool` и
   `T:System.Threading.Tasks.Parallel` (явно) — потоки только из исполнителя ядра. Тест 0 B для `threads > 1` меряет
   `GC.GetTotalAllocatedBytes(precise: true)` (аллокации воркера не видны в `GetAllocatedBytesForCurrentThread`).

## Последствия
- Ожидаемо s10k: tick p95 ≈ **3.3–3.6 мс** при load ≈ 1.5 (P6 замерен ≈ 3.5–3.7, P7 оценка ещё −0.15…−0.25); запас к 4 мс ≈ 10–17%.
- Риски: (1) на загруженном контейнере воркер может быть вытеснен посреди чанка — главный ждёт этот чанк (≤ 1/40 фазы), а если воркер
  не стартовал, главный делает всё сам (в прототипе так прошло 9–18 тиков из 7 900); при load 3–5 выигрыш меньше — верификатор
  меряет и при обычной загрузке, и отчитывается `uptime`. (2) Пропущенная общая запись в дереве вызовов (новый счётчик, кэш)
  — гонка; ловится тестом «хэш при 1/2/3 потоках» и тестом независимости от порядка (фаза в обратном порядке индексов даёт те же
  выходы). (3) Воркер крутится внутри `Step` — CPU второго ядра в пределах тика; между `Step` спит.
- Rust: тот же контракт — `par_chunks_mut` по выходным срезам (`Accel`, `LaneChangeDir`, `Clamp*`) с `zip`, аккумуляторы — `fold` +
  `reduce` целых; без `unsafe`. FFI: `sim_create(desc, opts)` с `worker_threads`.
- LOD (ADR-0013): meso-ветка фаз 5–6 так же чиста по машине — тот же исполнитель; неравномерность (meso думает 1 тик из 4) сглаживает
  динамическая раздача чанков. Параллельные фазы 4/7 по цветам ячеек (`sim-lod.md` §10 п.5) — следующий ADR-дополнение поверх
  этого исполнителя (задание = ячейки одного цвета вместо диапазонов индексов).
- Скорость игры ×2/×3 на s1m (`sim-lod.md` §11 п.3) получает тот же рычаг: `WorkerThreads` до 4.

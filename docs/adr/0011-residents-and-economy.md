# ADR-0011: Модель жителя и экономики: город — записи с расписанием, поездка — агент, деньги — проводки

- Статус: предложено, 2026-10-26 (этап 3.2, архитектор, агент #107). Номер зарезервирован `cs2-lessons.md` (топ-5 №1).
- Спецификация и задачи Z1–Z9: `docs/design/zoning-demand.md`. Спрос и выбор — ADR-0021. Затрагивает (поправки делают задачи):
  `core-api.md` §3, §5, §7, §9; `save-format.md` §3, §12, приложение A; `scenario-format.md` (секции `calendar`, `zoning`, `residents`,
  `economy`, `choice`); `pedestrians.md` §3 (житель-заготовка становится одним из источников ног); `modding.md` §3.3, M10 (здания);
  `player-tools.md` §1, §11 (`PaintZone`, участки при сносе).
- Решения владельца, обязательные: в 3.2 — только жители, работа и спрос; бюджет города (налоги, содержание, земля) — этап 4
  (`stage4-plan.md` §4.2), здесь — только точки расширения. Бюджет s10k + ~20k пешеходов ≤ 4 мс при 2 потоках уже занят трафиком.

## Контекст
- Сейчас машины — OD-генератор с фиксированной целью `vehicles.count` (core-api §7, фаза 2); житель-заготовка (`Peds/ResidentStore`,
  ADR-0020 п. 6) — без handle, без экономики, без расписания, жители не рождаются и не уходят.
- CS2 три года чинит экономику (`cs2-lessons.md` E1–E4): формулы не прогнали на долгих симуляциях (E1), вероятностные переходы без
  гарантии прогресса — бездомные и «замёрзшее» заселение (E2), спрос рушился на больших городах, решения шли по колеблющимся запасам
  («богатство»), а не по потокам (E3), смена модели без миграции сейвов (E4).
- Цена тика задаётся проходами по всем агентам (ADR-0019). Жителей в 4–40 раз больше, чем машин в пути (s10k ≈ 40 тыс., s100k ≈ 400 тыс.),
  поэтому житель вне поездки должен стоить 0 за тик, как пешеход между событиями (ADR-0020 п. 2).
- 10 лет игрового времени микросимуляцией не прогнать: при сутках 3 600 с это 263 млн тиков (s10k 2.4 мс → ≈ 7 суток счёта).

## Решение
1. **Два слоя с односторонним контрактом.** Слой города (`Sim.Core/City/`): участки, здания, жители, деньги, расписание — записи,
   меняются событиями и дневными проходами. Слой поездок — существующие агенты (машина, пешеход, пассажир). Граф зависимостей за тик
   без циклов: календарь → события жителя → выбор (читает только сглаженные времена и вчерашние итоги) → заявка ноги → агент →
   прибытие → наблюдение → сглаженные времена (в фиксированный тик). Обратная связь — только через сглаженные величины с задержкой.
2. **Сущности — SoA с handle (index + generation)** через `Util/HandlePool`: `Lot` (участок у стороны сегмента: зона R/C/I/нет,
   плотность), `Building` (на участке; для C/I здание = фирма, отдельной сущности фирмы нет), `Resident` (1 запись = 1 человек;
   домохозяйств, детей и пенсионеров нет — Парето). Связи — индексы и интрузивные списки (жители дома, работники фирмы), без ссылок
   между объектами. Типы зданий — данные (`buildings.json` пакета, ADR-0015 M10): строки только дописываются, сейв хранит параметры.
3. **Житель — конечный автомат с дедлайнами.** Состояния: дома, на работе, в магазине, в пути (нога), ждёт отправления, ищет работу,
   без жилья. У каждого не-конечного состояния есть дедлайн и детерминированный выход (поиск — FIFO-сопоставление, без жилья —
   переезд, затем отъезд из города). Случайных проверок «раз в N» нет. Метрика `res_stuck` — жители в состоянии дольше дедлайна —
   по построению 0 и ловит ошибки (как `stuck` для машин). Поездку агента не обрываем: правило «застрявших не деспауним» остаётся.
4. **Расписание.** Календарь `calendar.day_s` (дефолт 3 600 с симуляции = игровые сутки), сутки делятся на слоты по 5 игровых минут.
   Каждый день житель планирует туры: рабочий (если занят) и 0–2 дискреционных (магазин/досуг в C) — число, цель, способ и слот
   выезда выбирает ADR-0021. Нога исполняется агентом: машина (если `HasCar`), пешком или «пешком → автобус → пешком» (ADR-0020).
   Способ выбирается на тур (уехал на машине — вернётся на ней). Машина появляется в начале полосы сегмента участка и прибывает в
   точку участка (`DestS`); парковки — этап 4.4.
5. **Деньги — целые `long`, двойная запись.** Все счета: жители, здания, `External` (внешний мир), `City` (казна, в 3.2 потоков нет).
   Любой поток — `Ledger.Transfer(from, to, amount, kind)`; начальные средства и отъезды — проводки с `External`. Инвариант:
   **Σ всех счетов = 0 в любой тик** (проверка в тесте и debug, сумма — в JSON бенча). Потоки 3.2: зарплата (фирма → работник за
   отработанную смену), покупка (житель → C при визите), закупка (C → I по продажам), экспорт (`External` → I по выработке).
   Решения — по сглаженным потокам (EWMA дохода, выручки, прибыли), никогда по балансу (урок E3). «Виртуальных владельцев» нет.
   Цены и ставки — параметры `economy` (заглушки до 4.2) с проверкой баланса потоков в стационаре (спека §7).
6. **Рост — от доступности, с ограничением скорости.** Здание возникает на свободном зонированном участке по баллу доступности
   (logsum ADR-0021) и спросу своей зоны; жители въезжают в свободное жильё при спросе R; фирмы нанимают и сокращают по сглаженной
   прибыли; переезды и смена работы — не больше `max_*_per_day`. Индикаторы спроса R/C/I для клиента — те же величины, по которым
   решает модель (урок E1).
7. **Время и масштаб.** Слой города в тике стоит O(событий), а не O(жителей): события жителей — свой `TimerWheel`, дневные проходы
   размазаны курсором по тикам суток, сглаживание времён — порциями. Всё последовательно, однопоточно, целочисленно
   (новый поток PRNG `RngStream.Demand = 8`). Бюджет — спека §11: слой города ≤ 0.1 мс к p95 на s10k-res.
8. **Ускорение для «10 лет» — агрегатное исполнение ног, а не пропуск тиков.** `residents.trip_execution = "aggregate"`: нога без
   агента, длительность — сглаженное время OD × поправка загрузки ячеек (BPR по суммарным ногам периода, калибровка по 1 дню micro),
   прибытие — событие колеса. Тот же код решений, другой исполнитель. Переключение micro ↔ aggregate — на границе суток, ноги в пути
   доезжают своим исполнителем. Гибрид «агрегат вне активных LOD-ячеек» в игре отвергнут (ADR-0013: идентичность машин, телепорт на
   границе, эффект наблюдателя) — резерв для s1m в 4.1.
9. **Сейв и миграция (урок E4).** Блоки `LOTS`, `BLDG`, `RESD`, `SKIM`, `LEDG`, `BTYP` — только при `demand.model = "residents"`.
   `world_version` — следующий свободный (ожидаемо **w5**: w3 — сеть с дырами ADR-0023, w4 — ассет у дороги ADR-0015; **согласовать при
   мерже**). Миграция с предыдущей версии: блоков нет, поведение побитово прежнее. Корпус + тест «старый сейв → 3 дня → инварианты».
10. **Совместимость.** Без `demand.model = "residents"` состояние, хэш и сейв побитово прежние (лестница s1k/s10k/s100k и `*-peds`
    не меняются). Житель-заготовка ADR-0020 остаётся источником для `*-peds` (`peds.source = "preform"`), в режиме города ноги
    пешеходов заказывает город (`"city"`). Заготовку удалить, когда лестница бюджетов перейдёт на `*-res` (этап 4).

## Точки расширения (этап 4.2)
`City` — счёт уже есть; виды потоков `Tax`, `Rent`, `Fare`, `Maintenance`, `Construction` зарезервированы в `FlowKind`;
деньги в обобщённой стоимости (плата за проезд, топливо — ADR-0021) — член с нулевым весом; стоимость земли — из балла доступности
участка (уже считается для роста); стоимость стройки — `tools.costs` (ADR-0023 §11). Грузовики I → C — вид ноги `Freight` зарезервирован.

## Альтернативы
| Вариант | Цена за тик | Риски | Итог |
|---|---|---|---|
| Житель как агент, обход всех жителей каждый тик | O(жителей): 40k × 0.1 мкс ≈ 4 мс | весь бюджет | отвергнуто |
| Агрегатные потоки по зонам (OD-матрица, без жителей) | ≈ 0 | нет «кто куда едет», нет инспектора, стыки с пешеходами-агентами | отвергнуто |
| **Записи с событиями + агенты только в пути** | O(событий) ≈ 3–5 событий за тик на s10k-res | дедлайны и колесо — код | **выбрано** |
| Деньги float / только балансы без проводок | — | дрейф сумм, нет инварианта сохранения, детерминизм | отвергнуто |
| Решения по балансам (как «богатство» CS2) | — | колебания, обвал спроса на масштабе (E3) | отвергнуто |
| «10 лет» micro с пропуском пустых тиков | ≥ 1 мс за тик с машинами | недели счёта | отвергнуто |
| «10 лет» micro по одному дню в год + агрегат между ними | s100k: 31 мин на день | долго, но ловит дрейф | частично: на s10k раз в год, на s100k только калибровка |

## Последствия
- Новое поведение только в сценариях `*-res` (`s1k-res`, `s10k-res`, `s100k-res`) со своими golden-хэшами; бюджет s10k-res — спека §11.
- Число машин в режиме города — следствие расписания (пик/межпик), а не параметр; `vehicles.count` не действует, ёмкости — по пику.
- Новые инварианты в DoD каждой экономической задачи: сохранение денег, сохранение людей, `res_stuck = 0`, спрос в коридоре (ADR-0021).
- Rust: всё — плоские массивы `i32/i64/u8`, колесо и FIFO — `Vec<u32>`, без float в решениях, без `HashMap` с обходом.
- Риски: (1) баланс потоков ведёт к накоплению денег у одной стороны — проверяется дрейфом счетов на 10 лет (спека §7.4);
  (2) агрегат расходится с micro — калибровка и годовой контрольный день micro на s10k; (3) сжатые сутки (поездка 5 мин = 2 игровых
  часа) — вопрос владельцу.

## Уточнения реализации (Z4, 2026-10-26)
- Экономика (`City/Economy.cs`), рынки (`City/Market.cs`) и рост (`City/Growth.cs`) исполняются дневным проходом по курсору: здания и жители - порциями за четверть суток каждый, затем одним тиком спрос, снос, въезд и рост
  (`CityPhase.DayPass`; `all = true` - целиком, для агрегата). Накопители зданий - пары «сегодня/вчера»; то, что проход платит сам (товары, экспорт), идёт в сегодняшний слот и входит в прибыль на следующий день: результат не зависит от порядка зданий.
- Деньги: только `Ledger.Transfer`, Σ счетов = 0 проверяется тестами (фаззер проводок, сутки на s1k-res, сейв-валидатор). `Goods` - одной I-фирме по жребию (вес - вчерашняя выработка) вместо раздачи всем: ожидание то же, цена O(C-фирм) вместо O(C·I).
- Рынок труда сопоставляет теми же функциями при создании города и днём; внутри ячейки первая достижимая фирма берётся со сдвигом по `Seq`. Прежнее правило Z1 «первая фирма со свободным местом» набивало несколько десятков первых фирм до ёмкости; конец смены
  выпускал десятки машин одной фирмы на одну полосу, и обратная нога ждала дольше `wait_max_s` (причина `res_stuck > 0` в отчёте Z2; замер s1k-res: 49 фирм и `res_stuck` = 6 за сутки против 396 фирм и 0 у рынка).
- Дедлайны жителя (поиск работы, выселение) и здания (стройка, снос) исполняются дневным проходом; нарушение, просроченное больше чем на двое суток, считается `res_stuck`. На 30 сутках s1k-res micro `res_stuck = 0`.
- Любое изменение набора или состояния зданий увеличивает `Buildings.Version` - от неё перестраиваются производные скимов и рынка.
- Точки 4.2 (`Tax`, `Rent`, `Fare`, `Maintenance`, `Subsidy`) только зарезервированы в `FlowKind`: бюджет города - этап 4 (решение владельца). Стоимость стройки жилья пока не списывается (в 4.2 - со счёта `City`).

## Уточнения реализации (Z5, 2026-10-26)
- Агрегатная нога (`Demand/AggregateExec.cs`) - обычное событие жителя: `InLeg` без агента, `ResidentEvent.Arrive` в колесе жителей, завершение тем же `TripLegs.CompleteLeg`, что у micro (скимы, деньги визита и смены, конец тура). Поэтому «10 лет» исполняют те же решения и те же проводки; PRNG агрегат не читает.
- Переключение micro/aggregate - команда 24, применяется на границе суток; micro -> aggregate калибрует `K` по только что законченным суткам. Остатки micro-пешеходов снимаются сбросом `BuildRoad` в первый тик суток агрегата (жители не должны ждать автобус, которого больше нет), автобусы не выпускаются.
- Пока агентов нет, фазы трафика 2-10 не выполняются, а `Step` перепрыгивает тики без событий (`TimerWheel.NextDue/AdvanceTo`); дневные проходы агрегата идут целиком. s1k-res: 1 год игрового времени за 17 с (Release, 1 поток), число ног за 6 суток на 2.5% выше micro.

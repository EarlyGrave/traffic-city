# ADR-0002: Публичное API ядра и модель данных

- Статус: принято, 2026-10-24
- Спецификации: `docs/design/core-api.md`, `docs/design/scenario-format.md`

## Контекст
Sim.Core должен держать 1 000 машин при tick p95 ≤ 1 мс и 0 B/тик, не упираться в тупик на пути
к 1M и переехать на Rust без переделки клиента. Правила ТЗ: SoA, handle вместо ссылок,
детерминизм (dt = 1/20 с, свой PRNG), узкое FFI-подобное API, JSON-сценарии, общие для языков.
Несколько агентов будут реализовывать подсистемы параллельно, поэтому нужны зафиксированные
сигнатуры, раскладки структур и границы папок до начала кода.

## Решение
1. **Фасад** `Simulation`: `Create(in ScenarioDesc)` / `TryCreate`, `Step(int)`, `Enqueue(in Command)`,
   read-only `ReadOnlySpan<T>`-снапшоты, `ref readonly SimCounters`, `ComputeStateHash()`, `Dispose()`.
   Все публичные типы — blittable struct с явным `Pack`/`Size`; `ReadOnlySpan` ↔ `ptr+len` в C ABI.
2. **Handle** — `readonly struct { int Index; int Generation; }` на каждый вид сущности; пул —
   free-list LIFO, поколение нечётное = живой, 0 = Null. Невалидный handle → no-op + счётчик.
3. **Команды** — `[StructLayout(Explicit, Size = 64)]` tagged-union (`CommandKind` + payload),
   кольцевая очередь фиксированной ёмкости, FIFO, применяются в фазе 1 следующего тика;
   переполнение — отбрасывание со счётчиком, результат команды — через `SimEvent` с эхом `Tag`.
4. **Снапшот** `VehicleRenderData` 32 B, массив длиной `MaxVehicles`, индекс = слот; двойная
   буферизация prev/curr по `tick & 1`. Оверлеи: `SegmentLoad[]`, `SignalState[]`, `LaneSignals[]`,
   маршрут выбранной машины — срез общей арены `RouteStep[]` (без аллокаций).
5. **Модель сети**: Node / Segment (N полос в каждую сторону, лимит) / Lane (Normal, Connector, BusBay);
   полоса — полилиния с кумулятивным `s`; все полосы сегмента параметризованы по оси (общий `s`),
   connector — Безье, сэмплированный в полилинию (единый код геометрии).
6. **Машины** — SoA в `VehicleStore`; порядок на полосе — intrusive двусвязный список (`Ahead/Behind`)
   с `LaneHead/LaneTail`; лидер O(1); при смене полосы машина — «ghost» в исходной полосе до конца манёвра.
7. **Тик** — 10 фиксированных фаз (команды → спавн → маршруты → перекрёстки → поведение read-only →
   интеграция → переходы → прибытие → метрики → снапшот); «не проходят сквозь» — клэмп по позиции
   лидера на начало тика (не зависит от порядка → фазы 5–6 параллелизуемы позже).
8. **PRNG** — PCG32 с подпотоками по подсистемам; **хэш** — FNV-1a 64 по битовым образам полей в
   фиксированном порядке.
9. **Ёмкости** — все из `ScenarioDesc.Capacities`, выделяются в `Create`; нехватка — отложить/отбросить
   + счётчик + событие, никогда не исключение в `Step`.
10. **Сценарии** — JSON `format_version: 1`, человеческие единицы (км/ч, с), дефолты в загрузчике;
    IDM/MOBIL из Treiber & Kesting (городской набор, T = 1.2 с запасом на дискретизацию).

## Последствия
- Sonnet-агенты реализуют по папкам (`Api/ World/ Network/ Gen/ Agents/ Rules/ Routing/ Transit/ Metrics/ Util/`)
  параллельно; изменение публичной сигнатуры требует правки `core-api.md`.
- Клиент обходит `MaxVehicles` слотов за кадр; при 1M это 32 MB на буфер — приемлемо для headless,
  для рендера 1M потребуется компактный список живых (зарезервировано как расширение API).
- Общая `s`-параметризация полос даёт погрешность скорости на кривых ≤ `LaneWidth/R`; принято.
- Правила перекрёстков и A* проектируются отдельно (шаг 3) поверх зафиксированных структур
  (`Connector`, `ConflictGroup`, `SignalStore`, `RoutePool`), без смены раскладок.
- Хэш и метрики сравниваются с Rust-версией один в один — требование скалярной float-арифметики без FMA.

## Отвергнутые альтернативы
- **Компактный список активных машин в снапшоте** — требует сопоставления prev/curr по id на клиенте
  (словарь, аллокации); слот-индексация проще и ложится на MultiMesh с фиксированным `instance_count`.
- **Отсортированный массив машин на полосу** вместо списка — вставка при смене полосы O(n) и сдвиги
  памяти; список даёт O(1) при уже найденных соседях. Бинарный поиск по массиву — вариант для этапа 2.
- **xoshiro128\*\*** — нет встроенных подпотоков; PCG32 даёт их через инкремент и побитово совпадает с `rand_pcg`.
- **xxHash64** для хэша состояния — быстрее, но хэш не на горячем пути; FNV-1a проще портировать и верифицировать.
- **Class-команды / делегаты** — аллокации и не ложатся на FFI.
- **2D-коллизии между машинами** — не нужны: инвариант порядка на полосе + ghost при смене полосы дают
  гарантию без геометрии.
- **Генератор города вне ядра (в хосте)** — тогда Rust- и C#-хосты должны были бы совпасть ещё и по
  генератору; внутри ядра он детерминирован seed'ом и общий для метрик.

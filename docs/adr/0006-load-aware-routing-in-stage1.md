# ADR-0006: Учёт загрузки в маршрутизации переносится в этап 1

- Статус: принято, 2026-10-24 (оркестратор)

## Контекст
Бюджет s1k требует stuck = 0 за 30 мин. После правил перекрёстков (ADR-0004) и светофоров по спеке 24/3/1
остаётся 9 эпизодов stuck — все в одном насыщенном коридоре (Yield 53 → 125 → Yield 52 → 121 → Signal 51):
спрос на коридор выше пропускной способности узла 51, очередь стоит > 60 с. Это не дедлок и не баг ворот
(диагностика `DescribeChain`); правки ворот и длины фаз дальше не помогают. Статические веса (ADR-0005)
направляют все поездки по кратчайшему пути, поэтому коридор перегружается — та же проблема, за которую
ругают Cities: Skylines 2.

## Решение
Реализовать сейчас два пункта из `docs/design/routing.md` §9:
1. **Вес по загрузке**: `SegCost[w] = Length / (SpeedLimit · max(SpeedRatio[w], 0.2))` из `SegmentLoads`,
   пересчёт раз в 30 с игрового времени (фиксированный тик пересчёта — детерминизм), версия весов
   инвалидирует магистрали кэша лениво (как `NetworkVersion`).
2. **Перемаршрутизация по времени**: раз в 60 с для машин с остатком маршрута > 1 км — через `RerouteQueue`
   и бюджет запросов на тик (не больше доли бюджета, чтобы не задушить новые поездки).
Порог stuck (60 с), правила безопасности и don't-block-the-box не меняются.

## Последствия
- Поток расходится по параллельным улицам; ожидаем stuck → 0 и рост пропускной способности.
- Больше промахов кэша сразу после пересчёта весов → выше нагрузка на A*; следим за tick p95.
- Детерминизм сохраняется (пересчёт по номеру тика, целочисленная/фиксированная арифметика весов).
- Для s100k/s1m усиливает потребность в иерархии маршрутизации (этап 2).

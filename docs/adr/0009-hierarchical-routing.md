# ADR-0009: Иерархическая маршрутизация — многоуровневый оверлей ячеек (CRP-подобный) и ленивые маршруты

- Статус: предложено, 2026-10-24 (шаг 2.2 этапа 2)
- Спецификация: `docs/design/routing.md` §9. Дополняет ADR-0005 (A*, кэш магистралей) и ADR-0006 (веса по загрузке).

## Контекст
Плоский A* по направленным сегментам (ADR-0005) не масштабируется (REPORT-stage1, шаг 5):
- s100k: A* = 57% CPU главного потока; `RouteBuilder.GetTrunk` 42% (промахи кэша магистралей: при каждом
  пересчёте весов раз в 30 с `WeightsVersion++` инвалидирует **все** магистрали), куча `Pop` 25%, плановая
  перемаршрутизация 11.7% (идёт прямым поиском без кэша). Один полный поиск ≈ 1.35 мс / 9 100 раскрытий (routing.md §13).
- s1m: маршрут ≈ 470 шагов × 1.1 M машин ≈ 4 ГБ арены при `max_route_steps` 128 M (1 ГБ); очередь маршрутов отстаёт.
- Требования: веса по загрузке меняются раз в 30 с (ADR-0006), `BuildRoad` добавляет сегменты в игре, 0 B/тик,
  детерминизм, плоские массивы без ссылок (порт на Rust), s1k без регрессии.
- Владелец (2026-10-24): проект не в релизе, совместимость не держим — разрешён любой редизайн маршрутизации, структур ядра,
  API и формата сценариев ради целей (s10k ≤ 4 мс, s100k ≤ 15 мс, задел на s1m) и порта на Rust. Поэтому `RoutePool` с
  магистралями, кэш по парам зон и хабы не сохраняются «ради совместимости».

Масштаб сети (оценка по формулам `scenario-format.md` §2.1, `block_m` 150, 15% улиц удалено; DirSeg = 2 × сегменты):

| | s1k | s10k | s100k | s1m |
|---|---|---|---|---|
| карта, км | 3×3 | 6×6 | 15×15 | 48×48 |
| DirSeg (вершины A*) | ≈ 1.7 k | ≈ 5.6 k | ≈ 34 k | ≈ 350 k |
| зон / пар зон | 60 / 3.6 k | 192 / 37 k | 1 020 / 1.04 M | 9 600 / 92 M |

## Рассмотренные варианты

«Релаксация» = проверка одной дуги/элемента матрицы (≈ 3–15 нс), «раскрытие» = извлечение из кучи (≈ 50–100 нс).

|---|---|---|---|---|---|---|

Ключевые доводы за оверлей: (1) город — сетка с зонами 500 м, разбиение на ячейки получается из координат,
без разбиения графа; (2) веса меняются часто и локально — CRP-кастомизация ровно для этого; (3) маршрут естественно
хранится **компактно** как последовательность граничных DirSeg с уровнем и разворачивается лениво по ячейкам —
это и снимает арену s1m (≈ 4 ГБ → ≈ 0.35 ГБ); (4) код — тот же A* и те же плоские массивы, без нового класса алгоритмов.

## Решение
1. **Один путь кода для всей лестницы**: `routing.levels` = 1..4 (s1k 1, s10k 1, s100k 2, s1m 3). Кэш магистралей по парам зон,
   `ZoneData.HubNode`, `RouteCache`, `RefCount` и сборка «префикс + магистраль + суффикс» **удаляются**. Плоский A* остаётся
   только как эталон в тестах (`levels = 0` — тестовый режим «весь граф — одна ячейка», в сценариях лестницы не используется).
2. **Ячейки**: уровень 1 — квадрат `cell_m` (дефолт 1 000 м = 2×2 зоны) по bounding box сети в `Create`; уровень ℓ+1 — `fanout`×`fanout`
   (дефолт 4) ячеек уровня ℓ. Узел → координаты ячейки уровня 1 (с зажимом к краю сетки ячеек), выше — целочисленным делением.
   `CutLevel(u)` — старший уровень, на котором начало и конец DirSeg в разных ячейках; граничные вершины уровня ℓ — `CutLevel ≥ ℓ`.
3. **Оверлей**: у каждой ячейки входы (граничные DirSeg, кончающиеся в ней) и выходы (начинающиеся в ней) и плотная матрица
   `вход × выход` стоимостей кратчайшего пути **внутри** ячейки (уровень 1 — по DirSeg, уровень ℓ — по матрицам подъячеек).
   Плоские массивы, индексы, запас ёмкости строк/столбцов под `BuildRoad`.
4. **Кастомизация** (пересчёт матриц) — в `Create` целиком; в игре — «волна» после пересчёта весов (ADR-0006): только ячейки, где
   вес сегмента изменился больше порога, и их предки; работа размазана по тикам бюджетом релаксаций, порядок фиксирован.
5. **Запрос** — однонаправленный A* с той же евклидовой эвристикой по многоуровневому графу (правило уровня CRP: из вершины —
   дуги старшего уровня, чья ячейка не содержит ни старт, ни цель), индексная 4-арная куча с decrease-key. Точный кратчайший путь
   по текущим матрицам.
6. **Маршрут** = компактный **план** (стек `DirSeg | уровень << 28` в отдельной арене) + **окно** из ≤ 16 полосовых шагов `RouteStep`
   в фиксированном слоте (`RouteStore` вместо `RoutePool`: слот = handle маршрута, окно по адресу `slot × window_steps`,
   без bump-арены шагов и её компактификации). Окно дозаполняется ленивым развёртыванием плана (локальный поиск внутри одной ячейки) из очереди
   фазы 3 заранее, за ≥ 3 сегмента до конца окна. Навигация (фазы 4–7) читает окно так же, как сейчас `RouteStep`.
7. **Плановая перемаршрутизация** (ADR-0006) — по дрейфу: раз в 60 с считается остаток стоимости плана при
   текущих весах (O(длина плана), матрицы — O(1) на дугу); запрос — только если остаток вырос > 15% (+ 20 с) против ожидаемого.
8. **Бюджет** — в единицах работы (релаксации): `routing.work_budget_per_tick` на запросы, отдельно
   `routing.customize_budget_per_tick` на волну; дозаполнение окон обслуживается первым.

## Последствия
- Маршруты — точные кратчайшие (по текущим матрицам), без объезда через хабы; распределение трафика меняется на всей
  лестнице, включая s1k → хэши s1k меняются, baseline s1k переснимается осознанно (отдельный коммит), stuck = 0 за 30 мин
  перепроверяется; «без регрессии s1k» = `compare` tick p95 в допуске 10% и 0 B/тик.
- Новое состояние: оверлей (`Routing/Overlay*`), `RouteStore` (план + окно), очередь дозаполнения, волна кастомизации; хэш
  дополняется. Сценарий: новая секция `routing`, ёмкость `max_plan_steps`; `max_routes` = слоты маршрутов (машины +
  поездки с маршрутом, без магистралей), `max_route_steps` удаляется (= `max_routes × window_steps`),
  `capacities.pathfind_budget_per_tick` переезжает в `routing`; `format_version` → 2.
- Клиент (`RouteView`) видит только окно (≤ 8 сегментов вперёд) — лента маршрута короче; полный план наружу не отдаётся.
- s1m: кастомизация уровня 3 тяжёлая (≈ 0.5 млрд релаксаций на полную волну) → период пересчёта весов на s1m длиннее (`cost_recalc_s`).
- `BuildRoad` пока добавляет только сегменты к новым/изолированным узлам (core-api §4.2), поэтому существующие кратчайшие пути
  не сокращаются; при появлении перестройки узлов потребуется синхронная кастомизация затронутых ячеек (заложено) и
  пересчёт ALT, если он будет включён.
- Ожидаемый выигрыш на запрос s100k ≈ 3×, s1m ≈ 10–20×; основной выигрыш s100k — отсутствие «штормов» магистралей и запросы по
  дрейфу. Если доля `RoutePhase` на s100k останется > 15%, план Б — ALT-потенциалы на верхнем уровне (задача H4 в routing.md §9.12).
- Отвергнуто сейчас: матрица хабов, CH (динамика), CCH (риск реализации; вернуться при порте на Rust).

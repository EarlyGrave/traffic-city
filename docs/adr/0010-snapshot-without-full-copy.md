# ADR-0010: Снапшот машин — без копирования, дешевле на машину, длина = HighWater

- Статус: принято, 2026-10-24 (шаг 2.3)
- Спецификация: `docs/design/core-api.md` §3, §5.1–5.2, §7 (фаза 10)
- Уточняет ADR-0002 п.4 (снапшот), не меняет раскладку `VehicleRenderData`.

## Контекст
REPORT-stage1 (шаг 5): на s1k `SnapshotPhase.Run` = 15.9% тика, `Buffer.Memmove` = 10.4%; вывод отчёта —
«полный буфер копируется каждый тик». Разбор того же трейса (`s1k.speedscope.json`, стек каждого сэмпла) и кода:

- **Копирования нет.** Буферы `World.Render[2]` уже переключаются по `SnapshotTick & 1`, `Vehicles`/`PreviousVehicles`
  отдают `ReadOnlySpan` прямо на массивы ядра. `SnapshotPhase` пишет поля поэлементно.
- **`Memmove` 10.4% целиком под `IntegratePhase.Run`** (`Array.Copy(v.S, v.SOld, hw)`, ~5 КБ на s1k). Под
  `SnapshotPhase.Run` — 15.6% собственного времени (`Evaluate` заинлайнен), 0.3% в `LaneGeometry.Evaluate`, 0% Memmove.
- 10% на копию 5 КБ неправдоподобно: `dotnet-sampled-thread-time` останавливает поток в safe point, время
  «сползает» к ближайшему вызову. Доли профиля — ориентир, не точная мера; см. «Открытые вопросы».

Реальная цена фазы 10 на слот (`HighWater` = 1 280 на s1k): поиск отрезка полилинии, `sqrt` + деление
(нормировка `dir`), `MathF.Atan2`, `RenderFlags` (5 массивов + `Lanes[lane].Kind`), запись 32 B, обнуление
мёртвых слотов, даже если они уже нулевые. Клиенту при этом нужны `prev`/`curr` каждого тика (интерполяция 20 Гц → 60+ FPS).

## Варианты
| Вариант | Цена фазы 10 | Интерполяция (prev/curr) | Детерминизм, хэш | FFI (владение, время жизни) | 0 B/тик |
|---|---|---|---|---|---|
| A. Двойной буфер со сменой индекса | уже так; копии нет | prev = Tick−1, сопоставление по слоту | буферы не в хэше | память ядра, валидна до `Step` | да |
| B. Тройной буфер + публикуемый индекс | как A | как A | как A | читать можно параллельно со `Step` | да |
| C. Компактный список живых | +ведение списка/перестановок | prev/curr по разным позициям → поиск по handle (словарь/скан) | как A | как A, но длина ≠ слотам | да, но сложно |
| D. Запись в буфер прямо в `IntegratePhase` | экономит второй проход | как A | ломает порядок: фазы 7–8 меняют `Lane`/`S`/живость после 6 | как A | да |
| E. Грязные диапазоны | +учёт; движется почти всё | как A | как A | клиенту — выгрузка диапазонов | да |
| F. Снапшот по запросу клиента (ленивый) | 0 в `Step`, та же работа в кадре клиента | prev = Tick−1 только если клиент читал на прошлом тике; при `Step(n>1)` — нет | хинт `PointHint` не влияет на результат (см. ниже) | материализация в вызове клиента | да |
| G. **Дешевле на слот** (кэш курса, нормировка по нужде, пропуск нулевых) | −`Atan2`, −`sqrt`/div у машин без `Lateral`, −запись мёртвых | как A, побитово то же | кэш выводится из `LanePoints`, в хэш не входит | без изменений | да (кэш выделяется в `Create`) |
| H. **Длина спанов = `HighWater`** (не `MaxVehicles`) | без изменений | `prev.Length ≤ cur.Length`, слоты те же | без изменений | `ptr+len`, len меняется по тикам | да |

## Решение
1. **A остаётся** — это уже «снапшот без копирования». Раскладка `VehicleRenderData` (32 B), индекс = слот,
   prev/curr по `tick & 1` — без изменений. Корректируем REPORT-stage1: снапшот не копируется.
2. **G** — снижаем реальную цену фазы 10, результат побитово тот же:
   - `NetworkStore.LanePieceHeading : float[MaxLanePoints]` — курс отрезка `k → k+1` полилинии, считается тем же
     выражением, что сейчас (`d = b − a; dir = len > 1e-9 ? d·(1/len) : (1,0); atan2(dir.Z, dir.X)`), там же, где
     `NetworkBuilder` пишет точки полос (сегменты, connector'ы, `BuildRoad`). Производные данные: **не входят** в хэш
     сети/состояния (golden `GoldenS1kNetworkHash` не меняется).
   - `LaneGeometry.EvaluatePos(...)` → `pos` + индекс отрезка; `dir` (sqrt) — только если `Lateral != 0`.
   - Мёртвый слот обнуляется, только если `buf[i].Flags != 0` (буфер уже нулевой — не трогаем).
3. **H** — `Vehicles.Length = SnapshotSlots` = `HighWater` пула на момент снапшота (монотонно не убывает),
   `PreviousVehicles.Length` = его `SnapshotSlots` на тике раньше (≤). Клиенту s10k/s100k не надо обходить
   `MaxVehicles` слотов при частичной загрузке; на s1k без изменений.
4. **B, F — отложены** (не нужны сейчас): B — когда `Step` уйдёт в отдельный поток клиента (Godot worker /
   Rust-поток); F — только как режим headless (`SnapshotEnabled = false`, §5.2 core-api, зарезервировано): для клиента
   работа та же, а гарантия prev = Tick−1 теряется. **C, D, E — отвергнуты** (таблица).

## Последствия
- Детерминизм: буферы снапшота, `PointHint` и `LanePieceHeading` не в хэше. Результат `Evaluate` не зависит от
  `PointHint`: оба цикла поиска сходятся к единственному `h = max{k : pointS[k] ≤ s}` (с клэмпом), поэтому порядок
  и число материализаций не меняют ни хэш, ни снапшот.
- 0 B/тик: новый массив — один, в `Create` по `MaxLanePoints` (4 B на точку: s1m при ёмкости 15M — +60 МБ к 571 МБ пика).
- FFI/Rust: `tc_sim_vehicles(sim, &cur, &cur_len, &prev, &prev_len)` — указатели в память ядра, клиент только читает,
  валидны до следующего `tc_sim_step`/`tc_sim_destroy`. В Rust — `&self`-заимствование `&[VehicleRenderData]`,
  `step(&mut self)` его запрещает компилятором. `atan2` Rust и .NET могут разойтись в последнем ulp — допустимо,
  снапшот не входит в сравниваемый хэш.
- Клиент Godot и `Sim.Headless render`: уже обходят `cur.Length` и проверяют `i < prev.Length` + `Index`/`Generation`;
  правка кода не требуется, только проверка сборки. Тест `SimulationTests` на `Length == MaxVehicles` меняется.
- Ожидаемый выигрыш G на s1k неизвестен до замера (основной кандидат — `Atan2` на каждую машину); критерий шага
  2.3 (−≥ 8 п.п. доли `SnapshotPhase`) проверяется тем же методом, что в REPORT-stage1. Не достигнут — отчёт с фактом,
  следующий рычаг — F для headless (не для клиента).

**Задача 2.3-impl (sonnet).** Спека: core-api §5.1–5.2, §7 строка 10; этот ADR «Решение».
- `src/Sim.Core/Network/NetworkStore.cs` (+ `LanePieceHeading`), `NetworkBuilder.cs`, `NetworkBuilder.Connectors.cs`
  (заполнение при записи точек), `LaneGeometry.cs` (`EvaluatePos` без нормировки, возврат индекса отрезка).
- `src/Sim.Core/Api/SnapshotPhase.cs` (п.2 решения, `World.SnapshotSlots[2]`), `Simulation.cs` (срезы длиной `SnapshotSlots`).
- Тесты `tests/Sim.Core.Tests/Api/SnapshotTests.cs`:
  1) **эквивалентность**: в тест перенести прежний `SnapshotPhase` как `LegacySnapshot.Fill(World, Span<…>)` (свой
     массив хинтов); s1k-подобный сценарий из `TestScenarios`, 600 тиков, на каждом тике все слоты `< SnapshotSlots`
     совпадают с эталоном: `X, Z, Heading, Speed, LateralOffset` — `==` (±0 равны), остальные поля — побитово; слоты
     `[SnapshotSlots, MaxVehicles)` эталона — нули;
  2) кэш курса: после `Create` и после `BuildRoad` для каждого отрезка каждой полосы `LanePieceHeading == atan2(норм. d)`;
  3) `Vehicles.Length == HighWater`, `PreviousVehicles.Length ≤ Vehicles.Length`, prev = снапшот прошлого тика;
  4) существующие 0 B/тик, детерминизм и `GoldenS1kNetworkHash` — зелёные без правки. Правятся только ожидания длины в
     `tests/Sim.Core.Tests/Api/SimulationTests.cs` (строки с `MaxVehicles, sim.Vehicles.Length` и `PreviousVehicles[i]`
     после первого `Step` — теперь prev пуст, core-api §5.2).
- `bench/Sim.Bench/SnapshotBenchmarks.cs`: `SnapshotPhase.Run` на прогретом s1k-мире (2 400 тиков) — before/after в отчёт.
- Проверка своей области: `dotnet build -warnaserror` (sln и `game/TrafficCity.csproj`), тесты `~Api`/`~Network`, `dotnet format`.

**Верификатор (haiku) после мержа:** bench s1k + `compare`; профиль s1k тем же способом, что REPORT-stage1 шаг 5
(`dotnet-trace`, `dotnet-sampled-thread-time`, рампа завершена) → доля `SnapshotPhase.Run` до/после.
**Критерий:** доля `SnapshotPhase.Run` ≤ 7.9% (было 15.9%), `compare` без регрессии, 0 B/тик, stuck = 0.

## Отвергнутые альтернативы
- **C. Компактный список** — та же причина, что в ADR-0002: prev/curr лежат по разным позициям, клиенту нужен поиск
  по handle; ядру — поддержка плотности при деспауне. H даёт главный плюс (короткий обход) без этого.
- **D. Запись в `IntegratePhase`** — после фазы 6 идут переходы и деспаун (7–8): снапшот был бы не того тика, а слияние
  фаз мешает распараллеливанию фаз 5–6 (этап 2).
- **E. Грязные диапазоны** — в стационаре движется почти каждая машина; выгода только при выгрузке в GPU, не в ядре.

## Открытые вопросы
- Профиль по сэмплам смещён к safe point'ам. Честная мера — время фаз через `OnPhaseEnd` (core-api §3), который
  описан, но не реализован; предлагается в шаг 2.1.
- `Memmove` 10.4% под `IntegratePhase` (копия `S → SOld` 5 КБ) — вероятно, артефакт сэмплера; проверить в шаге 2.4.

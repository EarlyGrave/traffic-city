# ADR-0014: Бюджет рендера и LOD — бюджеты кадра на два класса GPU, 3 LOD + дальнее представление, точки → heatmap

- Статус: предложено, 2026-10-26 (этап 3.3, архитектор). Номер зарезервирован `docs/design/cs2-lessons.md` (риск №4, R1–R3).
- Спецификация и план задач V1–V10: `docs/design/render.md`. Затрагивает `modding.md` §4.3 (числа и правила вместо заглушки, формат
  `render-budgets.json` 2), ADR-0015 (п. «числа задаёт ADR-0014»), `core-api.md` §5.2 («точки» — без изменения ядра, см. п. 6),
  `sim-lod.md` §11 п. 1 (ответ владельца реализуется здесь). Визуальный стиль (палитра, форма машин, небо, цвет heatmap) — **не здесь**, это владелец.
- Решения владельца, обязательные: машины вдали — точками до порога, дальше heatmap загрузки (2026-10-24, к ADR-0013); панель узла по клику
  (2026-10-25, к ADR-0018); целевое железо — ноутбук среднего класса, 6–8 ядер, до 4 потоков симуляции (`CLAUDE.md` «Бюджеты»).

## Контекст
- CS2 (R1, R2): ассеты без бюджета треугольников и без LOD, тени от всего подряд, свой куллинг мимо движка — GPU-узкое место годами.
  Наш защитный механизм уже есть наполовину: M6 отклоняет glTF без корневых `LOD0..LODn` (`LodMissing`), но `max_tris = null`.
- Клиент сейчас (P5): машины — бокс на тип в одном `MultiMesh` с AABB 200 км (движковый куллинг выключен), на дальнем плане **раздуваются**
  `dist/500` (×6.6 на общем плане 3.3 км), пешеходы — капсулы, раздуваются `dist/70` (×47), heatmap пешеходов — прозрачные ленты 14 м по всем
  рёбрам, heatmap машин — пересборка всего `ArrayMesh` дорог раз в 0.5 с. Теней, LOD, чанков нет.
- Замер агента 108 (llvmpipe, 1280×720, `--warmup-ticks 2400`, 300 кадров, камера по умолчанию ≈ 3.3 км, `render.md` §2): s1k — 21.1 FPS;
  s1k-peds `auto` (пешеходы heatmap) — 18.8; `heat` — 16.5; `agents` (раздутые капсулы) — **9.7**. Раздувание и прозрачные ленты на весь экран —
  главный перерасход (+56 мс и +6…13 мс к 47 мс кадра s1k). llvmpipe — растеризация на CPU: абсолют ≠ GPU, годится только «до/после».
- GPU в облаке нет. Значит, бюджет должен проверяться метриками, не зависящими от GPU (draw calls, примитивы, объекты, память), детерминированно.

## Решение
1. **Два класса целевого GPU, один набор ассетов, два пресета** (`low`/`high`), 1080p, путь рендера Forward+ (Compatibility — fallback и облако):

   | На кадр (худший вид: общий план s100k / крупный план центра) | `low`: интегрированная (Iris Xe, Radeon 680M/780M, Arc 1xxV) | `high`: мобильная дискретная (RTX 3050–4060 Laptop, 4–8 ГБ) |
   |---|---|---|
   | Цель FPS (кадр) | 30 (33.3 мс), `scaling_3d` 0.75 (FSR1) | 60 (16.7 мс), 1.0 |
   | Треугольники, основной проход | ≤ 2.0 M | ≤ 5.0 M |
   | Треугольники, тени | ≤ 0.5 M | ≤ 1.5 M |
   | Draw calls, все проходы | ≤ 1 000 (тени ≤ 250) | ≤ 2 000 (тени ≤ 600) |
   | Текстуры (VRAM, сжатые, с мипами) | ≤ 512 МБ | ≤ 1.5 ГБ |
   | Клиент на главном потоке (без шага ядра) | ≤ 6 мс | ≤ 4 мс |

   Числа — проектные бюджеты (оценка по классу железа), не замер; на железе владельца проверяет V8. Не влезли — режем дистанции/лимиты пресета,
   а не бюджет ассета.
2. **Ассет: 3 LOD + дальнее представление**, конвенция M6 (корневые `LOD0..LODn`) остаётся. Пределы на уровень (треугольники / поверхности):
   ТС 1200/2, 300/1, 60/1 (текстура ≤ 512²); здание 5000/3, 1000/1, 200/1 (≤ 1024²); проп 500/1, 100/1, 20/1 (≤ 256²). Поверхность = draw call
   на инстанс-батч, поэтому их число ограничено. У зданий и пропов **LOD2 без текстур** (цвет материала/вершин) — клиент сливает его в меш чанка.
   Дальнее представление строит клиент, ассет его не несёт: ТС — **точка**, здание — **бокс-импостор** (AABB LOD2 + средний цвет, 10 треугольников,
   слит в чанк), проп — нет. Октаэдрические/запечённые импосторы отвергнуты (текстурная память и пайплайн запекания без выигрыша при виде сверху).
3. **Дорога** (спорное место M6): профиль — плитка 1 м вдоль +Z, `min_lods = 2` (48/2 и 16/1 треугольников на 1 м); третий уровень — плоская лента
   по полилинии — клиент строит сам для любой дороги. Требовать от моддера третий уровень, равный ленте, бессмысленно. Валидатор проверяет длину
   плитки (`ProfileBounds`).
4. **Дистанции** (до пресета; `low` умножает на `lod_scale` 0.7): ТС 60 / 200 / 600 м, точки до 2 500 м, дальше машин нет — дороги несут heatmap
   `SegmentLoads`; пешеходы 40 / 150 м, точки до 900 м (как сейчас `PedFarDistance`), дальше heatmap `PedEdgeCounts`; здания 150 / 500 / 1 500 м,
   импостор до 6 000 м; дорога 250 / 1 000 м, лента до 6 000 м. Обоснование: при 1080p и FOV 60° один пиксель ≈ 0.00107·d м — машина 4.5 м на 600 м
   = 7 px (60 треугольников достаточно), на 2 100 м = 2 px (точка того же размера). Гистерезис 10%. Раздувание по дистанции **убирается**: точка
   держит размер ≥ 2 px шейдером, а не раздутой геометрией.
5. **Батчи и куллинг — штатные средства Godot**, своё — только где Godot не умеет:
   - динамика (ТС, пешеходы): `MultiMesh` на (тип, LOD) + один `MultiMesh` точек на вид агента; отбор — `SetRenderView` ядра + дистанция на CPU
     (движковый LOD/visibility_range у `MultiMesh` действует на весь батч, поэтому разбиение по LOD делает клиент); лимит инстансов на уровень
     из пресета, переполнение уменьшает порог уровня (обратная связь, без сортировки);
   - статика (дороги, здания, пропы): чанки 250 м (ближние уровни) и 2 000 м (дальние: лента дороги, импосторы), точный AABB, frustum culling
     и `visibility_range` движка без `fade` (fade = прозрачный проход); здания LOD0/LOD1 — `MultiMesh` на (архетип, LOD) только в ближнем кольце;
   - occlusion culling, SDFGI/VoxelGI, объёмный туман — нет на этапе 3 (iGPU; вид сверху почти ничего не перекрывает); вернуть — по ADR с замером.
6. **Точки и heatmap без изменения ядра**: прямоугольник `SetRenderView` = след фрустума на земле, обрезанный дистанцией точек (2 500 м); дальше
   клиент машины не рисует. Heatmap — свойство шейдера дорог: индекс сегмента в атрибуте вершины, цвет из текстуры данных (`SegmentLoads` → 1 тексель
   на сегмент, обновление 2 Гц), смешение по дистанции за порогом точек; F1 включает heatmap везде. Пересборки меша нет. Так же пешеходы
   (`PedEdgeCounts`), ленты непрозрачные. «Второй прямоугольник раз в 4 тика» в ядре (core-api §5.2) — только если V8 покажет фазу 10 > 1 мс на
   s100k с прямоугольником точек; отдельная задача ядра.
7. **Тени**: один направленный свет, PSSM; тени отбрасывают только ТС LOD0, здания LOD0–LOD1, пропы LOD0, высотой AABB ≥ 1 м; точки, ленты,
   импосторы, heatmap, пешеходы (`low`) — никогда. `low`: 2 сплита, 300 м, атлас 2048; `high`: 4 сплита, 800 м, 4096.
8. **Числа живут в `content/render-budgets.json`** (формат 2: пределы на уровень, поверхности, сторона текстуры, дистанции, дальнее представление,
   пресеты; формат 1 читается). Код валидатора и клиента их не дублирует. Новые коды валидатора: `LodSurfaces`, `LodTextured`, `TextureOverBudget`,
   `ProfileBounds` (`LodOverBudget` уже есть). Ассет, не прошедший проверку, клиент не грузит (заглушка «?», M7), CI падает (`validate-package`).
9. **Прокси-метрики в облаке**: клиент пишет JSON с `Performance`/`Viewport.GetRenderInfo` (draw calls, примитивы, объекты — отдельно основной
   проход и тени; память текстур/буферов), счётчики инстансов по уровням и время главного потока по слоям, при `--fixed-fps 20` (1 тик на кадр —
   детерминированно) в фиксированных позах камеры. Гейт: превышение бюджета п. 1 по счётчикам или рост > 10% к baseline клиента → ошибка; FPS
   llvmpipe — справочно. FPS и время кадра на реальном GPU — та же команда у владельца (`render.md` §8).
10. **Панель узла по клику** — аналитический пик (луч → плоскость земли → ближайший узел по сетке), без физических коллайдеров у статики;
    UI ≤ 60 draw calls, обновление 4 Гц.

## Последствия
- Ассетам есть жёсткая рамка до начала low-poly арта; превышение ловит CI и клиент одной и той же проверкой (`Sim.Scenarios`).
- Общий план перестаёт зависеть от числа агентов в кадре: точки — 1 draw call, heatmap — 0 дополнительных; раздувания нет.
- Здания и пропы с текстурой на LOD2 отклоняются — дальние уровни у моддеров только цветом. Подъём формата бюджетов до 2 — без подъёма
  `content_format` (поля необязательные, формат 1 читается).
- Бюджет кадра сходится, только если шаг ядра не на главном потоке: s100k p95 15 мс при 30 FPS даёт кадры по 2 тика (30 мс) — вне бюджета.
  Вынос шага в поток меняет контракт «спаны валидны до следующего Step» (core-api §5.2) — отдельный ADR (открытый вопрос `render.md` §11).
- Метрики llvmpipe ≠ GPU: draw calls у Compatibility и Forward+ различаются (у Forward+ есть depth prepass) — baseline клиента по окружению
  (как ADR-0007), бюджет п. 1 — по Forward+ на железе владельца.
- R1–R3 `cs2-lessons.md`: R1 закрывается V2 + V8, R2 — п. 5, 7, R3 — п. 6 (полностью — с вынесенным шагом и компактным снапшотом).
- Отвергнуто: импосторы с запеканием, свой куллинг/occlusion, раздувание вдали, автоматический mesh LOD Godot для `MultiMesh` (выбирает уровень
  по AABB всего батча), heatmap пересборкой меша, третий уровень профиля дороги у моддера.

## Реализация V3 (ТС, 2026-10-26, агент 115)
- `game/Scripts/VehicleLayer.cs`: на тип ТС три `BoxBatch` (LOD0 - кузов+кабина 24 тр., LOD1 - бокс 12 тр., LOD2 - плоская крышка 2 тр.) и один батч
  точек (`PointBatch`, `game/Shaders/points.gdshader`, квад 1x1 с масштабом инстанса = длина x ширина, размер >= `point_min_px` в вершинном
  шейдере). Один проход по снапшоту; уровень хранится на слот (`byte[]`), гистерезис 10%; лимиты и обратная связь порогов по §3.3.
- Числа - из `content/render-budgets.json` (`RenderBudgets.Load`, `KindBudget.LodDistancesM/FarDistanceM`, пресет `high` по умолчанию,
  `--render-preset low`); при неудачной загрузке - дефолты §3.1/§3.3 (`LodConfig`).
- `SetRenderView` = AABB следа фрустума, обрезанный квадратом вокруг проекции камеры с радиусом `sqrt(R_точек^2 - h_камеры^2)`; если камера выше
  дистанции точек - пустой вид (нулевой прямоугольник), не «всё». Побочный эффект до V5: пешеходы берут тот же снапшот и тоже обрезаются.
- Раздувание `VehicleScaleDistance` удалено. До V4 (heatmap в шейдере) на общем плане s1k (камера 3.3 км) машин нет: дальше 2 500 м они не
  рисуются по решению владельца, а heatmap дорог пока только по F1 (пересборка меша).
- `BoxBatch`: ёмкость и `InstanceCount` привязаны к числу инстансов (кратно 256, запас 25%, сжатие при заполнении < 50%); в движок уходит весь
  буфер ёмкости (`MultimeshSetBuffer` требует размер = `InstanceCount x stride`), `VisibleInstanceCount` = записанное.

## Реализация V4 (дороги и тротуары чанками, heatmap в шейдере, 2026-10-26, агент 117)
- `RoadMesh` (один меш на карту, перекраска вершин и `ClearSurfaces` раз в 0.5 с) удалён. `RoadChunks.cs`: ближние чанки 250 м - LOD0 (ленты по полосам и connector'ам, как раньше) и LOD1
  (лента на направление сегмента по полилинии крайней правой полосы, упрощение Douglas-Peucker 0.4 м, квадрат узла) и дальние чанки 2 000 м (лента по сегменту, упрощение 6 м, y = -0.10 под дорогой).
  Каждый чанк - `MeshInstance3D` с точным AABB, уровни - `visibility_range` без fade (+ `_margin` 10%). Привязка к чанку - по сегменту/узлу, а не по полосе: все представления сегмента в одном чанке.
- `visibility_range` движка считается до центра AABB чанка, поэтому: пороги ближних уровней сдвинуты на полудиагональ ячейки 177 м (`NearHalfDiag`: LOD0 до 250+177, LOD1 до дальней границы +1 240);
  дальняя лента начинается с 1 000 м (`road.lod_distances_m[1]`), а ближний LOD1 держится до 2 240 м (`FarOverlap` = полудиагональ дальней ячейки минус ближней) - иначе у края дальнего чанка дыры.
  Дальняя лента начинается не с 0, иначе она (ниже дороги) заполняла бы зазоры между полосами LOD0.
- Верхней границы дальней ленты нет (в бюджете `far_distance_m` = 6 000): на общем плане s10k камера на ~8 км, а это единственное, что видно (отсекает `Camera.Far`).
- Heatmap: `HeatTexture` (`HeatTextures.cs`) - `RGBA8` шириной 4 096, дороги: R = `SpeedRatio`, G = `Density/120`, B = `Count > 0`; рёбра пешеходов: R = плотность (на 20 м ребра, /4), B = есть пешеходы.
  Обновление 2 Гц над одним `byte[]` + `Image.SetData` + `ImageTexture.Update`; меши не трогаются. Индекс (сегмент / ребро) - в `CUSTOM0.x` (RFloat; у тротуаров RgFloat, `y` = 1 у перехода).
  Шейдеры `road.gdshader`, `sidewalk.gdshader` (+ `heat.gdshaderinc`): `heat_mix = smoothstep(0.9P, P, d)`, `P` = 2 500 м (ТС) / 900 м (пешеходы); `heat_force` = 1 (F1 / `--ped-mode heat`), -1 (`agents`).
  Непрозрачные, без `ALPHA` (прозрачного прохода нет). Палитра - только `HeatPalette.cs` (плейсхолдер: зелёный-жёлтый-красный у дорог, голубой-жёлтый-красный у пешеходов), вид - за владельцем.
- `PedChunks.cs`: тротуары (ширина = `SidewalkWidthM`, y 0.06), ленты переходов (только для heatmap: в шейдере отбрасываются ближе ~810 м) и зебры (ближние чанки до 900 м + 177). `CrosswalkMesh` остался только для маркеров и очередей.
- `RenderStats`: блок `static_chunks` (`chunk_nodes`, `surface_builds_total`, `surface_builds_after_first_frame` = 0 в кадрах без изменений сети). Перестройка при изменении сети (ADR-0023) - пока не реализована (инструментов игрока ещё нет).
- Не сделано: профиль дороги 1 м с текстурой и два материала (LOD0 - те же плоские ленты по полосам, без разметки), `PedEdgeCounts` для тротуаров, добавленных после старта.

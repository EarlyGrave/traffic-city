# Режимы «Новой игры», каркас сценариев и сценарий «Юрьев-Польский» (спецификация YS, ADR-0038)

Статус: черновик на подтверждение владельцу (агент L84, 2026-10-29). Основание — решение владельца «2026-10-29 (2)»
в `docs/plan/next-ui-f5-and-yuryev.md`. Опирается на `new-game-scratch.md` (ADR-0037, задачи Y3–Y7) и не противоречит им.
Пометки: [Факт] — прочитано в коде или в отчёте с замером, [Оценка] — расчёт без прогона, [Старт] — стартовое значение для калибровки.
Замеров в этой спеке нет.

## 0. Идея в трёх абзацах

1. **Меню «Новая игра» — две вкладки.** «Пустая карта» — рельеф и одна подведённая дорога, свободная игра (это режим Y2–Y6, Юрьев 6×6 км —
   первая карта в списке). «Сценарий» — готовый город со своими стартовыми условиями, испытанием и условиями победы и поражения.
   Нынешний «готовый город» (`game-city.json`) становится первым сценарием в этом списке, отдельного режима больше нет.
2. **Каркас сценариев — данные, а не код.** В JSON сценария появляется секция `goals`: список условий победы (все сразу) и поражения
   (любое), каждое из небольшого набора типов: население ≥ N, население < N, казна < 0 дольше N суток, показатель KPI, престиж, срок.
   Ядро проверяет условия раз в игровой час (на сдвиге кольца KPI, вне горячего цикла), в целых числах, состояние лежит в сейве.
   Клиент показывает панель цели и экраны победы и поражения. Испытание (челлендж) — это обычные ключи сценария плюс одна новая
   механика «отток и престиж», включаемая отдельной секцией.
3. **Юрьев-Польский.** Новый вырез рельефа ≈ 10×10 км, генератор строит город «по мотивам» на ≈ 19 тыс. жителей (кремль с валом и парком,
   Колокша, трассы на Москву и Владимир), никаких OSM и реальных домов. Работающие жители медленно уезжают насовсем в Москву и Владимир;
   **престиж** города (из уже существующих показателей: время до работы, занятость, довольство, парки, автобус, казна) гасит отток.
   Победа — 100 тыс. жителей, поражение — меньше 10 тыс. Главный риск — производительность на 100 тыс. жителей (§6).

## 1. Меню «Новая игра»

### 1.1 Что видит игрок
- Главное меню → «Новая игра» → экран с двумя вкладками: **«Пустая карта»** и **«Сценарий»**.
- **Пустая карта:** список карточек карт. На карточке — название, размер карты, превью (миникарта высот, рисует клиент из `.r16`),
  тип подведённой дороги: «Въезд с края» (одна дорога, как Юрьев 6×6 из Y1) или «Сквозное шоссе» (дорога проходит карту насквозь,
  два узла `outside`). Старт — без подготовки, как в Y6 (`new-game-scratch.md` §4).
- **Сценарий:** список карточек сценариев. На карточке — название, одна строка о сюжете, стартовое население, **цель** и **условие
  поражения** простым текстом («Победа: 100 000 жителей. Поражение: меньше 10 000»), сложность (метка из JSON). Старт — с полосой
  подготовки (`ReadyCity`), как сейчас у готового города.
- Под карточками — «Дополнительно» (свёрнуто): seed. Общее для обеих вкладок.

### 1.2 Откуда список (метаданные в сценарии)
Новая необязательная секция `meta` верхнего уровня (только `Sim.Scenarios`, в ядро не идёт, на хэш и сейв не влияет):
```jsonc
"meta": {
  "mode": "scenario",          // "empty_map" | "scenario"; нет секции — сценарий не показывается в меню (все тестовые s1k/s10k…)
  "title": "Юрьев-Польский",   // строки пока по-русски; ключи локализации — когда появится локализация
  "summary": "Молодёжь уезжает в Москву. Сделайте город, из которого не хочется уезжать.",
  "difficulty": 3,             // 1..5, только метка
  "order": 20                  // порядок карточек
}
```
- Каталог — `ScenarioLocator` перебирает `scenarios/*.json` и читает только `meta` (без загрузки сети). Отдельного файла-каталога нет:
  новый сценарий = новый файл.
- Для `empty_map` клиент вызывает обычный старт (Y6), для `scenario` — `ReadyCity.TryPrepare`.

### 1.3 Судьба режима «Готовый город» — рекомендация
`game-city.json` получает `meta` (`mode: scenario`, «Город у колена сети», сложность 1) и мягкие `goals`: победы нет (свободная игра),
поражение — банкротство (казна ниже кредитного лимита дольше 10 суток, §2.2). Код `ReadyCity` остаётся — он же готовит Юрьев.
Отдельной кнопки «Готовый город» больше нет. Это вопрос В1 (§8).

## 2. Каркас сценариев

### 2.1 Что относится к «стартовым условиям» и «челленджу»
- **Стартовые условия** — существующие ключи, ничего нового: `residents.initial_fill` (население), `economy.initial_city_balance`
  (абсолютная казна, Y4) или `initial_city_balance_per_resident`, `calendar.start_hour` (Y4), `progression` (вехи, замки, области),
  `tools.world_bounds`, `outside` (Y3).
- **Модификаторы испытания** — тоже обычные ключи (налоги, `max_immigrants_per_day`, `credit_days`, цены) плюс **одна новая механика**
  `outflow` (отток и престиж, §4). Других модификаторов сейчас не вводим (Парето): каждый следующий — своя секция, когда понадобится сценарию.

### 2.2 Секция `goals` (новая, необязательная; только при `demand.model = "residents"`)
```jsonc
"goals": {
  "grace_days": 2,                 // поражение не проверяется первые N суток от старта (город после подготовки ещё «оседает»)
  "win":  [ { "kind": "population_ge", "value": 100000 } ],                 // все условия одновременно (И)
  "lose": [ { "kind": "population_lt", "value": 10000, "for_hours": 24 },   // любое условие (ИЛИ)
            { "kind": "insolvent", "for_days": 10 } ],
  "after_win": "continue"          // "continue" — играть дальше свободно; "end" — экран итогов без продолжения
}
```

| `kind` | Значение | Источник [Факт, если не помечено] |
|---|---|---|
| `population_ge` / `population_lt` | живые жители | `CityStats.Population` |
| `treasury_lt` | баланс казны < `value` | `CityBudget` (баланс) |
| `insolvent` | флаг мягкого банкротства | `progression.md` §5 |
| `kpi_le` / `kpi_ge` | показатель `kpi` (`travel_min`, `work_min`, `idle_pct`, `bus_share_pct`, `satisfaction_pct`) за 24 ч, ×10 | кольцо `CKPI`, те же `KpiKind`, что у ворот вех |
| `prestige_ge` | престиж ‰ | §4 (только при `outflow`) |
| `milestone` | достигнута веха с индексом `value` | `progression` |
| `day_ge` | наступили сутки № `value` (срок; в `lose` — «не успели») | календарь |

- Модификаторы условия: `for_hours` или `for_days` — условие должно держаться подряд столько времени (по умолчанию 0 — сразу).
- До 8 условий в `win` и 8 в `lose`. Неизвестный `kind` или ключ — ошибка загрузчика с JSON-путём.
- Вне режима `residents` секция запрещена.

### 2.3 Ядро
- POD (FFI, фиксированный размер): `GoalCondDesc { byte Kind; byte Kpi; short R; int Value; int HoldHours; }` (12 Б),
  `GoalsDesc { int GraceHours; byte AfterWin; byte WinCount, LoseCount; GoalCondDesc W0..W7, L0..L7 }`. Сутки переводятся в часы загрузчиком.
- **Где считается:** фаза 9r, на сдвиге часа KPI (`(tick + 1) % HourTicks == 0`, `CityPhase.Periodic`), после KPI и прогрессии. Раз в
  игровой час, O(16), 0 Б. Горячий цикл не трогается.
- **Состояние** (`City/Goals.cs`, класс в `CityWorld`, `null` без секции): `int[16] HeldHours` (сколько часов подряд условие истинно),
  `byte Outcome` (0 — идёт, 1 — победа, 2 — поражение), `long OutcomeTick`, `byte LoseIndex`.
  Порядок: сначала поражение (если `tick ≥ grace`), потом победа; в один час — поражение важнее. После исхода условия больше не
  проверяются; при `after_win = continue` симуляция идёт дальше, при поражении — тоже идёт (клиент решает, что показать).
- **Сейв и хэш:** блок `GOAL` только при секции; раздел хэша — новый номер, только при секции. `world_version` — следующий свободный после
  Y3 (по плану Y3 — 13, значит 14), миграция «секции нет». Без секции поведение, хэш и сейв побитово прежние.
- **Детерминизм:** только целые, источники — уже детерминированные счётчики; от числа потоков не зависит (фаза 9r однопоточная).
- **API** (`Api/Simulation.Goals.cs`): `bool TryGetGoals(out GoalsInfo)` — `{ Outcome, OutcomeTick, LoseIndex, WinCount, LoseCount }` и
  `GoalCondInfo GetGoalCond(int i)` — `{ Kind, Value, Current, HeldHours, HoldHours, Met }` для панели. Событие `SimEvent`
  `ScenarioOutcome` (A = исход, B = индекс условия).

### 2.4 Клиент
- **Панель цели** (вкладка в панели «Город» или отдельная плашка в верхней полосе — решает исполнитель UI по `ui-spec.md`): цель
  с прогресс-баром (19 400 / 100 000), рядом — угроза поражения с запасом («до поражения: 9 400 жителей»), при `for_hours` — таймер.
- **Экран победы**: итог (сутки, население, престиж, графики населения и престижа по суткам), кнопки «Играть дальше» / «В меню».
- **Экран поражения**: причина одной строкой, те же графики, кнопки «Загрузить сохранение» / «В меню».
- Предупреждение заранее: тост, когда условие поражения начало выполняться (`HeldHours` > 0) и когда до порога < 10 %.

## 3. Сценарий «Юрьев-Польский»: карта и город

### 3.1 Рельеф 10×10 км (новый вырез)
- `tools/dem/` (Y1) уже умеет вырезать окно; новый вырез — ≈ 10 240 м вокруг того же центра, шаг 32 м (≈ 321×321 отсчёт) в файл
  `scenarios/terrain/yuryev-10k-32m.r16`. Файлы Y1 (6 км) не трогаем: пустая карта 6×6 остаётся как есть.
- Память рельефа при шаге 8 м: ≈ 1 281² ≈ 1.64 млн отсчётов, ≈ 10 МБ по формуле §2.3 `terrain.md` [Оценка] — между s10k (6.2 МБ) и s100k (27.9 МБ).
- **Колокша и вал — наши полилинии** (`terrain.md` §1, §9.4): вал — то же кольцо (якорь «центр кремля»), реку надо **продлить** от краёв
  окна 6 км до краёв 10 км (ещё ≈ 2 км на севере и юге), тоже от руки, с подбором по дну долины тем же скриптом. Владелец подтверждает на глаз.
- Внутри вала — парк (`landuse` Park по полилинии вала), генератор там кварталы не ставит.

### 3.2 Город «по мотивам» (генератор, вариант В)
- Генератор `CityGenerator` с рельефом (`terrain.md` §9.3) уже умеет: план решётки, удаление узлов в воде, мосты артерий, релаксацию уклона.
- **Новое (минимум):**
  1. **Область застройки меньше карты.** Город ≈ 19 тыс. жителей занимает только центр (сторона ≈ 4.5–5 км [Оценка: s10k-res даёт 11 тыс. на 6 км
     при `initial_fill` 0.07, плотность настраивается]), остальная карта пустая — под рост до 100 тыс. Ключ `city.extent_m` (размер области
     генератора) и `city.center` — если генератор сейчас берёт размер из `size_m` карты, разделить. Проверить в YS4.
  2. **Запретные полигоны генератора:** парк кремля уже даст `landuse` Park; убедиться, что генератор не кладёт туда улицы.
  3. **Подведённые трассы:** две-три «наши» полилинии артерий от края карты к центру — на Москву (юго-запад, через Кольчугино), на Владимир
     (юго-восток), на Гаврилов Посад (север, по желанию) — эмитятся как артерии поверх плана, их концы у края — узлы `outside` (Y3).
     Это и есть «сквозное шоссе» для пустых карт, если позже понадобится.
- **Ограничения** (честно): генератор строит регулярную решётку с джиттером; «радиальный» центр с кремлём будет похож на Юрьев лишь
  рекой, валом, парком и трассами. Радиальная планировка — не в этой волне (вопрос В6).

### 3.3 Стартовые условия [Старт]
| Что | Значение | Откуда |
|---|---|---|
| Население | ≈ 19 000 (±5 %) | `initial_fill` подбирает YS5 |
| Казна | ≈ 300 000 | `economy.initial_city_balance` (Y4) |
| Время старта | 06:00 суток 1 после подготовки | `ReadyCity` (как у готового города) |
| Вехи | M0 = старт, далее 30 / 45 / 65 / 85 тыс.; гранты; области карты расширяются к краям | `progression` (механика прежняя) |
| Открыто на старте | всё, что открыто у готового города на M0 + зонирование кистью | `progression` |
| `outside` | узлы «Москва» и «Владимир» на трассах: `jobs` небольшие (маятниковые поездки), `immigrant_share` 0.5/0.5 | Y3 |

## 4. Отток и престиж (новая механика, секция `outflow`)

### 4.1 Что видит игрок
- В панели «Город»: **Престиж 0–100** и расшифровка из 5–6 строк («Время до работы: плохо, −12»), график по суткам.
- В строке населения: «уехало за сутки в Москву и Владимир: 140» отдельно от обычного отъезда (нет работы, снос дома).
- Тост раз в сутки, если отток вырос: «Престиж падает — молодёжь уезжает. Главная причина: долгая дорога на работу».

### 4.2 Престиж (`City/Prestige.cs`)
Престиж `P` в ‰ (0–1000) — взвешенная сумма компонент. Каждая компонента — линейная шкала между порогами «плохо» и «хорошо» (0 и 1000),
обрезанная по краям. Все входы — **уже существующие** показатели, нового учёта нет (Парето).

| Компонента | Вход [Факт — источник есть] | «Плохо» / «хорошо» [Старт] | Вес [Старт] |
|---|---|---|---|
| Дорога на работу | K1a `WorkMin` за 24 ч | 150 / 60 игровых мин | 30 % |
| Работа есть | `1 − ищущие / рабочая сила` (счётчики рынка работы) | 85 % / 98 % | 25 % |
| Довольство | K4 `SatisfactionPct` | 85 % / 99 % | 15 % |
| Парки | площадь `landuse` Park (включая кремль) на жителя | 2 / 15 м² | 10 % |
| Автобус | K2 `BusSharePct` | 0 % / 15 % | 10 % |
| Казна | баланс ≥ 0 и ставка налога на зарплату ≤ дефолта | долг или налог +50 % / без долга и налог дефолтный | 10 % |

- Пороги и веса — в JSON (`outflow.prestige`), калибровка YS5. Значения ×10, как у ворот вех.
- **Сглаживание:** `P` пересчитывается раз в час (тот же сдвиг KPI), отток использует суточное среднее — чтобы одна пробка не обваливала город.
- «Сервисов» (школы, больницы) в игре нет; когда появятся — новая компонента. Пока компонента «Автобус» играет роль «город удобен без машины».
- Парки: учесть только Park, который игрок может создавать. Есть ли у игрока инструмент «парк» сейчас — проверить в YS2; если нет —
  компонента считает только кремль и стартовые парки, и тогда она бесполезна для игрока → вес 0 до инструмента (вопрос В5).

### 4.3 Отток
- Раз в сутки (дневной проход; при `zoning.growth_step = hour` из Y4 — раз в час с лимитом /24) число уезжающих:
  `out = floor(labour · base_rate · (1000 − P) / 1000)`, где `labour` — жители с флагом `Labour` («работающее население», возраста в модели нет),
  `base_rate` [Старт] 1.0 % в сутки при нулевом престиже. Остаток дроби копится в целом счётчике (без `float`).
- **Кто уезжает:** обход жителей по возрастанию индекса, житель с флагом `Labour` отбирается, если `XxHash64(seed, day, r) mod 2^16 < p_Q16`
  (без нового потока PRNG — не сдвигает остальные; так же сделан шум рельефа). Отобранный получает флаг `Leaving` и уезжает при следующем
  `AtHome` существующим `Market.Emigrate` (тот же путь, что отъезд по дедлайну). Баланс — на `External`, поток `FlowKind.Emigration` (есть).
- Учёт: счётчик `OutflowToday` отдельно от прочего отъезда (для UI и калибровки).
- Въезд не меняется (Y4/Y3: спрос R, `max_immigrants_per_day`, пол въезда). Влияет ли престиж и на въезд — вопрос В5.
- 0 Б/тик: флаг в существующем байте флагов жителя, счётчики — поля класса. Детерминизм: только целые и хэш от (seed, сутки, индекс).

### 4.4 Данные
```jsonc
"outflow": {
  "base_rate_pct_day": 1.0,           // отток при престиже 0, % рабочей силы в сутки
  "destinations": ["moscow", "vladimir"], // только подпись в UI (id из outside); машин отъезда нет (В4)
  "prestige": {
    "work_min":        { "bad": 150, "good": 60,  "w": 300 },
    "employment_pct":  { "bad": 85,  "good": 98,  "w": 250 },
    "satisfaction_pct":{ "bad": 85,  "good": 99,  "w": 150 },
    "park_m2_per_res": { "bad": 2,   "good": 15,  "w": 100 },
    "bus_share_pct":   { "bad": 0,   "good": 15,  "w": 100 },
    "treasury":        { "w": 100 }
  }
}
```
Сумма весов = 1000 (проверка загрузчика). Сейв: `P`, часовое кольцо 24 значений `P`, остаток дроби, `OutflowToday`, флаг `Leaving` (в байте жителя) —
в том же блоке `GOAL` или своём `PRST` (решает YS1/YS2, одна `world_version` на волну).

### 4.5 Темп партии — честная оценка [Оценка]
- От 19 тыс. до 100 тыс. — рост в 5.3 раза. Даже при максимальном чистом приросте 3 % в сутки (потолок въезда `game-city`) это
  `ln 5.3 / ln 1.03 ≈ 56` игровых суток. При `day_s = 3600` это ≈ 56 ч реального времени на ×1, ≈ 28 ч на ×2.
- Поражение без игрока: при чистом оттоке ≈ 1 % в сутки от 19 тыс. до 10 тыс. — ≈ 64 суток. Слишком долго, чтобы чувствовалось давление.
- Значит, темп — решение владельца (вопрос В2): короче сутки, выше потолок въезда, ниже цель, или «длинная партия» как в CS.

## 5. Как это работает вместе (одна игровая сутки)
1. Каждый час (фаза 9r): KPI сдвигаются → прогрессия → престиж → условия `goals`.
2. Раз в сутки (или в час при `growth_step = hour`): рынок работы, рост, въезд (Y3/Y4), **отток** (§4.3).
3. Клиент читает `GetCityKpi`, `TryGetGoals`, престиж — 1–4 Гц, как сейчас.

## 6. Производительность: 100 тыс. жителей

Известные цифры [Факт]:
- `s10k-res` (≈ 11 тыс. жителей, карта 6 км): готовый город — tick p95 1.03–1.17 мс на 1 потоке в загруженном облаке (PG6);
  0.62–0.67 мс на ПК разработчика (L46). Агент 151 до клапана: пик 10.7 тыс. машин, p95 3.06 мс при 2 потоках.
- `s10k-res-overload`: 102 тыс. жителей на сети s10k — спрос ≈ в 3 раза выше ёмкости, без клапана город не восстанавливается (ADR-0035).
- s100k (100 тыс. машин без жителей): p95 **26.94 мс** при 4 потоках, цель этапа 4 (15 мс) не выполнена (`REPORT-stage4.md`).
- Бюджет этапа 3 у владельца: s10k + 20 тыс. пешеходов — p95 ≤ 4 мс при 4 потоках. Для 100 тыс. жителей бюджета нет.

Что из этого следует [Оценка]:
- 100 тыс. жителей ≈ в 9 раз больше s10k-res. Если пик одновременных машин растёт пропорционально — десятки тысяч машин на сети,
  то есть масштаб между s10k и s100k по тику. По цифрам s100k (≈ 27 мс на 100 тыс. машин) это скорее 5–15 мс, чем 1–4 мс — **не играется
  на ×2–×4 без мер**. Цифра условная: реальную даёт задача YS0.
- Карта 10 км ≈ в 2.7 раза больше по площади, чем 6 км, сеть растёт пропорционально только если игрок её строит. Если игрок дорог не строит,
  город упрётся в ёмкость (как overload) — это и есть игра, клапан ADR-0035 не даст «заклинить».
- Подготовка `ReadyCity` для 19 тыс.: ≈ 45 с × 1.7 ≈ 75–80 с на 3 потоках [Оценка от PG6] — на грани терпения; полоса загрузки обязательна.

Меры (по порядку цены, решение — по замеру YS0, вопрос В3):
1. Ничего не делать до 30–40 тыс. жителей: путь от 19 тыс. до них, скорее всего, в бюджете.
2. **«Одна машина = k ног»** (`res-congestion.md` вариант A): агентом идёт доля машинных ног, остальное — агрегатом с весом в нагрузке.
   Код агрегата и скимов уже есть; меняются хэши `*-res` — значит, только для сценариев с ключом. Отдельная спека и ADR.
3. LOD/meso для окраин (`lod` уже заложен этапом 2) — дороже, отдельная волна.

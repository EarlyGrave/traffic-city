# Рендер: бюджеты кадра, LOD, батчи, проверки (этап 3.3)

Решение — ADR-0014. Здесь числа, правила, формат `content/render-budgets.json` 2, метрики и задачи V1–V10 для sonnet.
Визуальный стиль (форма и цвет машин, палитра heatmap, небо, свет «по настроению») — **не здесь**: это владелец. Здесь — только технические бюджеты и пайплайн.
Стык: `modding.md` §4.2–4.3 (валидатор glTF, M6; клиент моделей, M7), ADR-0013 / `sim-lod.md` §11 п. 1 (точки → heatmap),
`core-api.md` §5.2–5.3 (`SetRenderView`, `SegmentLoads`), `pedestrians.md` §10 (`PedEdgeCounts`), ADR-0018 (панель узла).

## 0. Сводка правил
1. Бюджет кадра — два пресета под два класса GPU (§1), один набор ассетов.
2. У каждого присланного ассета ≥ 3 LOD (дорога — 2, §4.4), пределы треугольников/поверхностей/текстур на уровень; дальнее представление строит клиент.
3. Машины: LOD0–LOD2 → точка → нет машин (heatmap на дорогах). Пешеходы: LOD0–LOD1 → точка → heatmap.
4. Батчи: динамика — `MultiMesh` на (тип, LOD) + один на точки; статика — чанки 250/2 000 м, `visibility_range` движка.
5. Тени — только у крупных ближних уровней. Occlusion/GI — нет.
6. В облаке меряем детерминированные счётчики (draw calls, примитивы, объекты, память), FPS llvmpipe — справочно.

## 1. Целевое железо и бюджет кадра

### 1.1 Классы GPU (ноутбук среднего класса, `CLAUDE.md` «Бюджеты»)
| | `low`: интегрированная | `high`: мобильная дискретная |
|---|---|---|
| Примеры | Intel Iris Xe (96 EU), Radeon 680M/780M, Intel Arc 130V/140V | RTX 3050 / 4050 / 4060 Laptop |
| Память | общая с CPU (LPDDR5/DDR5, пропускная способность — главное ограничение: fill rate и overdraw) | 4–8 ГБ GDDR6 |
| Слабое место | заливка (прозрачность, overdraw, тени высокого разрешения), CPU-цена draw call в драйвере | редко GPU; чаще главный поток (подготовка кадра) |
| Разрешение | 1080p, `scaling_3d_mode = FSR` 0.75 | 1080p, 1.0 |
| Цель | 30 FPS (33.3 мс), p95 кадра ≤ 40 мс | 60 FPS (16.7 мс), p95 ≤ 20 мс |

Путь рендера — **Forward+** (Vulkan/D3D12). Compatibility (OpenGL) — fallback для слабых iGPU и облака (llvmpipe): должен работать, бюджеты
по нему не считаются. Отсюда запреты для шейдеров базы: без compute, без SDFGI/VoxelGI/объёмного тумана, без `SCREEN_TEXTURE` в материалах мира.

### 1.2 Бюджет на кадр
Худший вид = общий план s100k (камера ≈ 5 км, наклон 55°) или крупный план плотного центра (≈ 150 м). Числа — проектные (оценка по классу), не замер.

| Метрика | `low` | `high` |
|---|---|---|
| Треугольники, основной проход | ≤ 2.0 M | ≤ 5.0 M |
| Треугольники, тени (все сплиты) | ≤ 0.5 M | ≤ 1.5 M |
| Draw calls, все проходы | ≤ 1 000 | ≤ 2 000 |
| из них тени | ≤ 250 | ≤ 600 |
| Объекты в кадре (`OBJECTS_IN_FRAME`) | ≤ 1 500 | ≤ 3 000 |
| Текстуры в VRAM | ≤ 512 МБ | ≤ 1.5 ГБ |
| Вся видеопамять (`VIDEO_MEM_USED`) | ≤ 1.5 ГБ | ≤ 3 ГБ |
| Главный поток клиента без шага ядра | ≤ 6 мс | ≤ 4 мс |
| Прозрачные поверхности на весь экран | 0 (только UI и выделение) | ≤ 1 слой |

### 1.3 Раскладка по слоям (`low`, основной проход; `high` ≈ ×2–2.5 лимитами пресета)
| Слой | Draw calls | Треугольники | Как держится |
|---|---|---|---|
| ТС | ≤ 3·T + 1 (T — видимые типы; ≤ 60) | ≤ 0.66 M | лимиты инстансов §3.3 |
| Пешеходы | ≤ 3 | ≤ 0.13 M | лимиты §3.3 |
| Дороги, тротуары, разметка | ≤ 150 | ≤ 0.30 M | чанки §5.2, упрощение дальней ленты |
| Здания | ≤ 250 | ≤ 0.75 M | архетипы только в ближнем кольце, LOD2/импостор в мешах чанков |
| Пропы | ≤ 100 | ≤ 0.10 M | как здания |
| Оверлеи (маршрут, сигналы, маркеры, выделение) | ≤ 40 | ≤ 0.05 M | — |
| UI (HUD, панели) | ≤ 60 | — | §9 |
| Тени | ≤ 250 | ≤ 0.50 M | §6 |

Не влезли на железе владельца — уменьшаем `lod_scale` и лимиты пресета, а не пределы ассетов (ассеты одни на оба пресета).

## 2. Что льёт кадр сейчас (P5, агент 104; разбор агента 108)

### 2.1 Замер (llvmpipe, 4 vCPU, 1280×720, `--warmup-ticks 2400`, 300 кадров, камера по умолчанию `Focus` ≈ 3.3 км, `scripts/godot-shot.sh fps`)
| Прогон | FPS | Кадр, мс |
|---|---|---|
| s1k (без пешеходов) | 21.1 | 47.4 |
| s1k-peds `--ped-mode auto` (вдали → heatmap пешеходов) | 18.8 | 53.2 |
| s1k-peds `--ped-mode heat` | 16.5 | 60.6 |
| s1k-peds `--ped-mode agents` (капсулы, тротуары, зебры) | 9.7 | 103.1 |

Крупный план (P5): 33 FPS ≈ 30 мс — это нижняя граница llvmpipe для сцены. Один прогон на точку, шум облака ±25–40%: годится для порядка величин.

### 2.2 Разбор по коду `game/`
1. **Раздувание по дистанции** (`SimHost.VehicleScaleDistance = 500`, `PedScaleDistance = 70`): на 3.3 км машина ×6.6 (бокс ≈ 30×10×12 м),
   пешеход ×47 (капсула ≈ 26 м в диаметре, 80 м высотой). В режиме `agents` до 2 600 капсул закрывают экран слоями — +56 мс к s1k.
   Это главный перерасход: стоимость растёт с числом агентов, а не с числом пикселей. → точки фиксированного экранного размера (§3.4).
2. **Heatmap пешеходов** (`CrosswalkMesh.Heat`): ленты 14 м по всем рёбрам тротуаров и переходов, `Transparency = Alpha`, без записи глубины,
   по обе стороны каждой улицы — перекрываются; +6…13 мс к s1k. → непрозрачные ленты в шейдере чанка с текстурой данных (§3.5).
3. **Heatmap машин** (`RoadMesh.Refresh`, F1): пересборка всего `ArrayMesh` дорог (`ClearSurfaces` + `AddSurfaceFromArrays` всех вершин) раз в 0.5 с —
   пик кадра и выгрузка всего буфера; на s100k/s1m — десятки МБ раз в 0.5 с. → цвет из текстуры данных, меш не трогаем.
4. **Дороги**: один меш на всю карту, полосы — отдельные ленты 3.1 м с наложением (`CullMode.Disabled`), connector'ы поверх. На общем плане
   полоса ≈ 1 px — тысячи субпиксельных треугольников (дорого для любого растеризатора). Куллинга нет (один AABB на карту). → чанки, лента
   на сегмент (а не на полосу) вдали, упрощение полилинии (§5.2).
5. **Батчи** (`BoxBatch`): `CustomAabb` 200 км (куллинг движка выключен — для динамики это верно, отбор делает `SetRenderView`); `Buffer = _buf`
   отправляет весь буфер ёмкости, а не `count` инстансов — при росте ёмкости до 100k это 6.4 МБ за кадр на тип. → буфер по `VisibleInstanceCount`
   (ёмкость кратная 1 024, перевыделение редко), см. V3.
6. Шаг ядра — в `_Process` на главном потоке. s1k ≈ 0.5 мс/тик не виден, но s100k p95 15 мс при 30 FPS = кадры по 2 тика → 30 мс только на ядро.
   Это вне бюджета §1.2 — открытый вопрос §11 Т1.

## 3. LOD: уровни, дистанции, точки, heatmap

### 3.1 Дистанции (база = `high`; `low` умножает на `lod_scale` = 0.7). `d` — расстояние камеры до центра объекта (для чанка — до центра AABB)
| Вид | LOD0 до | LOD1 до | LOD2 до | Дальнее представление до | Дальше |
|---|---|---|---|---|---|
| ТС | 60 м | 200 м | 600 м | точка, 2 500 м | не рисуется; дороги — heatmap `SegmentLoads` |
| Пешеход (клиентская модель) | 40 м | 150 м | — | точка, 900 м | heatmap `PedEdgeCounts` |
| Здание | 150 м | 500 м | 1 500 м | бокс-импостор, 6 000 м | не рисуется |
| Проп | 40 м | 120 м | 400 м | — | не рисуется |
| Дорога (профиль) | 250 м | 1 000 м | лента (клиент), 6 000 м | — | — |

Пиксельное обоснование: 1080p, FOV 60° → 1 px ≈ 0.00107·`d` м. Машина 4.5 м: 70 px на 60 м, 21 px на 200 м, 7 px на 600 м, 2 px на 2 100 м.
Пешеход 0.5 м: 3 px на 150 м. `MaxViewRange` клиента = 6 000 м (как сейчас).

Гистерезис: переход вверх по детальности при `d < 0.9·порог`, вниз при `d > порог` (на агента хранится текущий уровень, `byte[]` по слоту).
Fade (`visibility_range_fade_mode`) не используется: он переводит объект в прозрачный проход.

### 3.2 Ассеты и пределы на уровень (`render-budgets.json`, §4)
| Вид | Треугольники LOD0 / 1 / 2 | Поверхностей LOD0 / 1 / 2 | Текстура, сторона | Особое |
|---|---|---|---|---|
| ТС | 1 200 / 300 / 60 | 2 / 1 / 1 | ≤ 512 | — |
| Здание | 5 000 / 1 000 / 200 | 3 / 1 / 1 | ≤ 1 024 | LOD2 без текстур |
| Проп | 500 / 100 / 20 | 1 / 1 / 1 | ≤ 256 | LOD2 без текстур |
| Дорога (плитка 1 м) | 48 / 16 | 2 / 1 | ≤ 1 024 (тайлится по Z) | 2 уровня, третий — лента клиента |
| Пешеход (клиент, не ассет) | 300 / 12 | 1 / 1 | — | процедурный, моды пешеходов — позже |

Поверхность (primitive с отдельным материалом) = отдельный draw call на каждый батч, поэтому ограничена. «Без текстур» = материал без
`baseColorTexture`/`normalTexture`/`metallicRoughnessTexture`/`occlusionTexture`/`emissiveTexture`; цвет — `baseColorFactor` или `COLOR_0`.
Только так клиент сливает LOD2 разных архетипов в один меш чанка с одним материалом. Скины и morph targets — по-прежнему `GltfFeature`
(анимация пешеходов/ТС — отдельный ADR, когда появятся модели).

### 3.3 Лимиты инстансов на кадр (пресет)
| | `low` LOD0 / LOD1 / LOD2 / точки | `high` |
|---|---|---|
| ТС | 100 / 800 / 4 000 / 30 000 | 200 / 2 000 / 8 000 / 60 000 |
| Пешеходы | 200 / 2 000 / — / 20 000 | 500 / 5 000 / — / 40 000 |
| Здания (ближнее кольцо, `MultiMesh`) | 50 / 300 / — / — | 120 / 800 / — / — |

`low` ТС: 100·1200 + 800·300 + 4000·60 + 30000·2 = 0.66 M треугольников (§1.3). Переполнение уровня `k` — **обратная связь без сортировки**:
порог `k` на следующий кадр ×0.9; если заполнение < 0.8 лимита и порог ниже базового — ×1.05 до базового. Лишние инстансы этого кадра уходят на
уровень грубее. Порог не ниже 0.25 базового.

### 3.4 Точки (решение владельца: «машины точками до порога»)
- Один `MultiMesh` на вид агента (ТС, пешеходы): горизонтальный квад (2 треугольника) по курсу, цвет инстанса (флаги — как сейчас: выделение,
  stuck, тип), материал unshaded, без теней.
- Размер — в вершинном шейдере: `world = max(истинный размер, k_px · 0.00107 · d · (1080 / высота вьюпорта))`, `k_px = 2` (параметр пресета).
  Так «точка» не меньше 2 px и не больше машины вблизи порога — без раздутой геометрии.
- Позиции — из того же снапшота (`Vehicles`/`PreviousVehicles`, интерполяция prev/curr), т. е. ядро не меняется.
- **Прямоугольник вида** (`SetRenderView`) = AABB следа фрустума на земле, обрезанный кругом радиуса «точки до» (2 500 м; `low` 1 750) вокруг
  проекции камеры. Машины за ним ядро не пишет — клиент их и не рисует. Пешеходы — то же для 900 м.
- Ядро (core-api §5.2, «второй прямоугольник раз в 4 тика») **не трогаем**, пока V9 не покажет фазу 10 > 1 мс на s100k с этим прямоугольником;
  тогда — отдельная задача ядра (последовательно с P3/3.1c, не параллельно).

### 3.5 Heatmap (решение владельца: «дальше — heatmap»)
- Машины: у вершины дороги атрибут `CUSTOM0.x` = индекс сегмента (float точен до 2^24). Текстура данных `RGBA8` ширины 4 096, высоты
  `ceil(MaxSegments / 4096)`: R = `SpeedRatio`, G = `Density/120`, B = `Count > 0`. Обновление 2 Гц из `SegmentLoads` (`Image.SetData` над
  переиспользуемым `byte[]` + `ImageTexture.Update`, без новых объектов).
- Шейдер дороги: `heat_mix = max(F1 ? 1 : 0, smoothstep(0.9·P, P, d))`, где `P` — дистанция точек ТС. Цвет из `R/G/B` — палитра задаётся
  владельцем (uniform-градиент, по умолчанию как сейчас `RoadMesh.HeatColor`).
- Пешеходы: то же для `PedEdgeCounts` (индекс ребра в `CUSTOM0.y` у тротуаров/переходов), ленты **непрозрачные**, ширина = ширина тротуара,
  на 0.05 м выше дороги, в мешах чанков. Прозрачный проход для heatmap запрещён (§1.2).
- `RoadMesh.Refresh`/`CrosswalkMesh.RebuildHeat` (пересборка меша) удаляются. Меш дороги пересобирается только при изменении сети (инструменты
  игрока, ADR-0023), и только затронутые чанки.

## 4. Ассеты: `content/render-budgets.json` формат 2 и валидатор

### 4.1 Формат
```json
{
  "format_version": 2,
  "kinds": {
    "vehicle":  { "min_lods": 3, "max_tris": [1200, 300, 60], "max_surfaces": [2, 1, 1], "max_texture_side": 512,
                  "lod_distances_m": [60, 200, 600], "far": "points", "far_distance_m": 2500 },
    "building": { "min_lods": 3, "max_tris": [5000, 1000, 200], "max_surfaces": [3, 1, 1], "max_texture_side": 1024,
                  "untextured_from_lod": 2, "lod_distances_m": [150, 500, 1500], "far": "impostor_box", "far_distance_m": 6000 },
    "prop":     { "min_lods": 3, "max_tris": [500, 100, 20], "max_surfaces": [1, 1, 1], "max_texture_side": 256,
                  "untextured_from_lod": 2, "lod_distances_m": [40, 120, 400], "far": "none" },
    "road":     { "min_lods": 2, "max_tris": [48, 16], "max_surfaces": [2, 1], "max_texture_side": 1024,
                  "profile_tile_m": 1.0, "lod_distances_m": [250, 1000], "far": "flat_ribbon", "far_distance_m": 6000 }
  },
  "pedestrian": { "lod_distances_m": [40, 150], "far": "points", "far_distance_m": 900 },
  "presets": {
    "low":  { "lod_scale": 0.7, "point_min_px": 2, "scaling_3d": 0.75,
              "shadow": { "distance_m": 300, "splits": 2, "atlas": 2048 },
              "caps": { "vehicle": [100, 800, 4000, 30000], "pedestrian": [200, 2000, 0, 20000], "building": [50, 300, 0, 0] } },
    "high": { "lod_scale": 1.0, "point_min_px": 2, "scaling_3d": 1.0,
              "shadow": { "distance_m": 800, "splits": 4, "atlas": 4096 },
              "caps": { "vehicle": [200, 2000, 8000, 60000], "pedestrian": [500, 5000, 0, 40000], "building": [120, 800, 0, 0] } }
  }
}
```
- Поля вида: `min_lods` 1..8; `max_tris`, `max_surfaces` — массивы длины ≥ `min_lods` (`null` = не проверять; уровни сверх длины — по последнему
  элементу); `max_texture_side` — степень двойки ≤ `ModLimits.MaxTextureSide` (4 096); `untextured_from_lod` — с этого уровня текстуры запрещены;
  `profile_tile_m` — только у `road`; `lod_distances_m` строго возрастают, длина = `min_lods`; `far` ∈ `points|impostor_box|flat_ribbon|none`;
  `far_distance_m` > последней дистанции (у `none` не задаётся).
- `pedestrian` и `presets` читает только клиент; валидатор проверяет форму (числа > 0, `caps` — 4 элемента, `splits` ∈ {1, 2, 4}).
- Формат 1 (`min_lods` + `max_tris`) читается как раньше; отсутствующие поля формата 2 = «не проверять», клиент берёт дефолты из этой таблицы.
  `content_format` (modding.md §8) не поднимается: файл бюджетов — свой `format_version`, в таблице `render-budgets 2`.
- Пропы: своя запись `prop` (раньше брали запись `building`; правило «проп без записи → здание» в `RenderBudgets.For` остаётся для формата 1).

### 4.2 Проверки валидатора (`src/Sim.Scenarios/Mods/Gltf/`)
| Код | Когда | Сообщение (пример) |
|---|---|---|
| `LodMissing` (есть) | нет `LOD0..LODn` / дырка / меньше `min_lods` | `2 LOD levels, at least 3 required` |
| `LodOrder` (есть) | треугольники растут с уровнем | — |
| `LodOverBudget` (есть, теперь с числами) | `tris[k] > max_tris[k]` | `LOD1 has 412 triangles, budget 300` |
| `LodSurfaces` (новый) | примитивов с разными материалами в поддереве `LODk` > `max_surfaces[k]` | `LOD0 has 3 surfaces, budget 2` |
| `LodTextured` (новый) | материал примитива уровня ≥ `untextured_from_lod` ссылается на текстуру | `LOD2 material 1 uses baseColorTexture` |
| `TextureOverBudget` (новый) | изображение, на которое ссылается материал ассета, больше `max_texture_side` вида | `PNG 1024x1024, budget 512` |
| `ProfileBounds` (новый) | у `road`: протяжённость `POSITION` (min/max аксессора) по Z вне `[0.95, 1.05]·profile_tile_m` или по X > 64 м | `LOD0 Z extent 4.0 m, tile 1.0 m` |

- Поверхности считаются по уникальным `material` примитивов поддерева (примитив без материала = материал по умолчанию, тоже одна поверхность).
- `TextureOverBudget` — по виду ассета, который ссылается на файл; общий файл двумя видами проверяется по строжайшему.
- Предупреждение `TextureMemory` (не ошибка): оценка VRAM пакета Σ `w·h·bpp·4/3` (PNG/JPEG → 1 Б/px как BC7 после сжатия клиентом, KTX2 — по
  формату) > 128 МБ. Печатается сводкой `validate-package`.
- Числа — только из файла; в коде — дефолты формата 1 (заглушка `StubBudget`) и `TODO(ADR-0014)` удаляются.
- CI: шаг `validate-package content/base --game` уже есть (ci.yml); V2 добавляет фикстуры-отказы (тесты), чтобы правило «ассет без LOD / сверх
  бюджета отклоняется» было закреплено тестом, а не только шагом CI. Клиент проверяет моды тем же кодом при загрузке; отказ → заглушка «?» (M7).

### 4.3 Дальнее представление (строит клиент)
- ТС, пешеходы — точка (§3.4).
- Здание — **бокс-импостор**: AABB LOD2, 10 треугольников (без дна), цвет = средний `baseColorFactor`/`COLOR_0` LOD2 по площади; слит в меш дальнего
  чанка 2 000 м. Запечённые и октаэдрические импосторы отвергнуты (ADR-0014).
- Дорога — лента по полилинии сегмента (не полосы) шириной профиля, полилиния упрощена (Дуглас–Пекер, 1 м на 250-м чанках, 4 м на 2 000-м).

### 4.4 Почему дорога — 2 уровня (спорное место M6/ADR-0015)
Профиль тянется вдоль оси, поэтому его «LOD2» — всегда плоская лента шириной профиля: клиент строит её одинаково для всех дорог, а моддер не
добавил бы ничего, кроме лишней работы и риска несоответствия ширины. Число треугольников профиля зависит от длины дороги, поэтому бюджет —
на плитку 1 м (`ProfileBounds` проверяет, что модель — именно плитка). Цена: правило «3 LOD» для дорог читается как «2 LOD + лента клиента».

## 5. Батчи и куллинг (R2: штатные средства, своё — по замеру)

### 5.1 Динамика (ТС, пешеходы)
- Слой `VehicleLayer`: на тип ТС × LOD — `MultiMeshInstance3D` (мешей LOD у процедурного бокса — один бокс на все три уровня, пока нет моделей;
  у модели — меши `LOD0..2`, по поверхности — подповерхность того же `Mesh`). Плюс один батч точек на все типы.
- Отбор: снапшот уже ограничен прямоугольником вида (§3.4); за кадр — один проход по `Vehicles[..HighWater]`: дистанция → уровень (гистерезис,
  лимиты) → запись в буфер батча. Движковый куллинг у этих батчей выключен (`CustomAabb`), движковый LOD/`visibility_range` не используется
  (действует на весь `MultiMesh`).
- Буфер: `float[]` ёмкости (кратно 1 024, растёт ×1.5), в движок — только `count·stride` (`RenderingServer.MultimeshSetBuffer` + `VisibleInstanceCount`);
  0 аллокаций управляемой памяти за кадр в стационаре (кроме строк HUD).
- Тени: только батчи LOD0 ТС (`CastShadow = On`), остальные `Off`.

### 5.2 Статика (дороги, тротуары, здания, пропы)
- Сетка чанков: **ближняя** 250 м (дорога LOD0/LOD1, тротуары, здания LOD2 слиты, пропы LOD2 слиты), **дальняя** 2 000 м = 2×2 LOD-ячейки
  ADR-0013 (лента дороги, импосторы). Каждый чанк — `MeshInstance3D` с точным AABB → frustum culling движка; уровни чанка — отдельные узлы с
  `visibility_range_begin/end` (+ `_margin` = 10% для гистерезиса), без fade.
- Здания LOD0/LOD1 и пропы LOD0/LOD1 — `MultiMesh` на (архетип, LOD) в кольце ≤ дистанции LOD1, перераспределяются при сдвиге камеры > 25 м
  (не каждый кадр), с лимитами §3.3. Дальше — только меши чанков.
- Один материал на слой (дороги, тротуары, здания-дальние) — атрибуты в вершинах; текстуры дорог — общий атлас/`Texture2DArray` профилей.
- Пересборка чанка — при изменении сети/застройки, не больше 1 чанка за кадр (очередь), в фоне строится массив, на главном — только
  `AddSurfaceFromArrays`.
- Draw calls: общий план s1m (18×18 км) — дальних чанков 81 × 2 слоя = 162; ближних в кадре ≤ ~40 × 3 слоя = 120 → ≤ 300 с запасом под §1.3.

### 5.3 Не делаем на этапе 3
Occlusion culling (`OccluderInstance3D`, нет в Compatibility, при виде сверху почти ничего не перекрыто), SDFGI/VoxelGI/LightmapGI, объёмный туман,
автоматический mesh LOD Godot для `MultiMesh` (выбирается по AABB батча), свои системы куллинга на GPU. Вернуть — ADR с замером «до/после».

## 6. Тени и свет (технически; вид неба и света — владелец)
- Один `DirectionalLight3D`, PSSM: `low` 2 сплита, `directional_shadow_max_distance` 300 м, атлас 2 048; `high` 4 сплита, 800 м, 4 096.
  Мягкость фильтра — `low` минимальная, `high` средняя. Остальные источники — без теней (фонари — позже, отдельным бюджетом).
- Отбрасывают тень: ТС LOD0, здания LOD0–LOD1, пропы LOD0, при высоте AABB ≥ 1 м (`shadow_min_height_m`). Никогда: точки, ленты, дороги,
  тротуары, heatmap, импосторы, оверлеи, пешеходы на `low` (на `high` — LOD0).
- Окружение: `ambient` + небо (процедурное или панорама ≤ 2 048×1 024 — выбор вида за владельцем). SSAO — только `high`; SSR, glow, DOF — выключены
  (включение — по замеру V9 на железе владельца). MSAA: `low` выкл., `high` 2×.

## 7. Текстуры и память
- Раскладка `low` (≤ 512 МБ): ТС ≤ 64 МБ, здания ≤ 256 МБ, дороги ≤ 32 МБ, пропы ≤ 64 МБ, остальное (небо, UI, данные heatmap) ≤ 96 МБ.
- В VRAM — только сжатые форматы с мипами (BC7/BC1 на ПК; Compatibility — S3TC/ETC2). PNG/JPEG из glTF (`GLTFDocument`) грузятся
  несжатыми RGBA8 (×4 к BC7): клиент сжимает их при загрузке и кэширует (`user://cache/tex/<sha256>.res`), KTX2/BasisU (`KHR_texture_basisu`)
  транскодирует напрямую. До V7 модели с текстурами — только в тестовых модах.
- Буферы: `MultiMesh` 64 Б/инстанс (100k = 6.4 МБ), данные heatmap ≤ 1 МБ; меши статики s1m — оценка в V8 (`BUFFER_MEM_USED`).

## 8. Метрики и проверки

### 8.1 Что мерить в облаке (llvmpipe ≠ GPU)
| Метрика | Источник в Godot 4.7 | Детерминирована | Использование |
|---|---|---|---|
| Draw calls, примитивы, объекты — основной проход | `Viewport.GetRenderInfo(Visible, DrawCallsInFrame / PrimitivesInFrame / ObjectsInFrame)` | да (при §8.2) | гейт бюджета и регрессии |
| То же — тени | `Viewport.GetRenderInfo(Shadow, …)` | да | гейт |
| Сумма | `Performance.RenderTotalDrawCallsInFrame / RenderTotalPrimitivesInFrame / RenderTotalObjectsInFrame` | да | сверка |
| Память | `Performance.RenderVideoMemUsed / RenderTextureMemUsed / RenderBufferMemUsed` | да | гейт §1.2 |
| Инстансы по слоям и LOD | свои счётчики слоёв | да | гейт лимитов §3.3 |
| Время главного потока по слоям, шаг ядра отдельно | `Time.GetTicksUsec` вокруг `Update*`/`Step` | нет (CPU, шумит) | справочно, регрессия > 25% — предупреждение |
| `TimeProcess`, FPS | `Performance.TimeProcess`, `Engine.GetFramesPerSecond` | нет | только «до/после» на одной машине |
| GPU-время кадра | `RenderingServer.ViewportSetMeasureRenderTime` + `ViewportGetMeasuredRenderTimeGpu` | — | только на реальном GPU (владелец) |

Если Compatibility не заполняет какой-то счётчик (проверить в V1) — фолбэк: сумма по своим батчам (`VisibleInstanceCount × поверхности` = draw
calls батчей, `count × треугольники меша`).

### 8.2 Детерминизм замера
`--fixed-fps 20` (дельта кадра = 1 тик ядра) + `--warmup-ticks N` + поза камеры `--pose overview|mid|close` (фиксированные `--cam` от размеров карты)
+ `--render-stats <json> --stats-frame K` (снять на кадре K и выйти). Одинаковые аргументы → побитово одинаковые счётчики детерминированных метрик.

### 8.3 Гейт и где он живёт
- `scripts/godot-shot.sh stats <scenario>` — 3 позы × сценарий (пресет `low` по умолчанию, `PRESET=high`), JSON `stats-<сценарий>-<поза>-<пресет>.json` в `perf/results/godot/`; `scripts/godot-shot.sh gate` (каталог `perf/results/render/`) — набор `SCENARIOS` (по умолчанию `s1k-peds s10k`) + `render-compare`. Сценарии: s1k-peds, s10k, s100k (на рампе
  `--warmup-ticks 6000`).
- `Sim.Headless render-compare --result <dir> --budget content/render-budgets.json --baseline perf/render-baseline.json` (бюджеты кадра - `presets.*.frame` в `render-budgets.json`; ключ записи baseline `сценарий/поза/пресет`; другое окружение `driver/method/resolution` - exit 2): превышение бюджета §1.2
  (`low`) по детерминированным счётчикам → exit 1; рост > 10% к baseline клиента → exit 1; время/FPS — только печать.
  Baseline клиента — по окружению (как ADR-0007), обновляется только `render-update-baseline` (тот же порядок, что `perf/baseline.json`).
- CI: отдельная job `render` (Godot 4.7.2 mono с зеркала SourceForge, sha512, кэш actions) — сначала `workflow_dispatch` + раз в сутки,
  обязательной после 5 зелёных прогонов подряд. Отказ ассета без LOD — job `build` (`validate-package` + тесты V2), Godot не нужен.
- Владелец на своём ноутбуке: та же команда клиента с `--rendering-driver vulkan` (Windows: `godot --path game -- …`), JSON с FPS, p50/p95/p99
  кадра и GPU-временем → таблица в отчёт этапа (чек-лист §10 V9).

## 9. Панель узла по клику (ADR-0018)
- Пик: луч камеры → плоскость земли `y = 0` → ближайший узел в радиусе `max(12 м, 0.01·d)` по сетке узлов 200 м (строится из `NetworkView` один

  чек-лист владельцу.
- **Зависимости:** V3 (SimHost), ADR-0018 принят.

## 11. Открытые вопросы

### Технические (решает оркестратор/архитектор; рекомендация + трейдофф)
- **Т1. Шаг ядра вне главного потока.** **Решено ADR-0024** (поток симуляции, копия видимого за тик, +1 тик лага; задачи `scale.md` S8–S10).
  s100k p95 15 мс на главном потоке ломает §1.2 на обоих пресетах. Рекомендация была: отдельный ADR —
  поток симуляции + копия «видимого» снапшота (только слоты вида, ≤ 32 Б × 20k = 640 КБ) на главный поток раз в тик. Трейдофф: меняет контракт
  «спаны валидны до следующего Step» (core-api §5.2) и задержку ввода на 1 тик (50 мс); без этого бюджеты выше s10k — только на бумаге.
- **Т2. «Второй прямоугольник» ядра для точек.** Рекомендация: не делать, пока V9 не покажет фазу 10 > 1 мс на s100k с прямоугольником 2 500 м.
  Трейдофф: при больших видах снапшот пишет все машины в круге каждый тик (оценка ≈ 10–20k машин × ~0.1 мкс = 1–2 мс на тик на s100k-центре — проверить).
- **Т3. Профиль дороги — 2 уровня** (§4.4). Рекомендация: да. Трейдофф: правило «3 LOD» не единообразно; зато нет фиктивного третьего уровня у моддера.
- **Т4. LOD2 зданий/пропов без текстур.** Рекомендация: да (иначе слияние чанков требует общего атласа/`Texture2DArray` и единых размеров
  текстур у всех модов). Трейдофф: на 500–1 500 м здания только цветом; если владелец захочет «текстурный» дальний план — атлас-массив, +V-задача.
- **Т5. CI-job `render` обязательна?** Рекомендация: после 5 зелёных прогонов подряд — да. Трейдофф: +105 МБ загрузки (кэш) и ≈ 3–5 мин на прогон.
- **Т6. Forward+ как основной путь.** Рекомендация: да, Compatibility — fallback. Трейдофф: облако меряет другой путь (нет depth prepass, другие
  счётчики) — baseline клиента по окружению, бюджет §1.2 подтверждает только прогон владельца.

### Визуальные (решает владелец; здесь — что от них зависит технически)
- **В1. Вид точек вдали:** цвет (по типу / по скорости / одноцветные), размер 2 px или больше. Технически любое — 1 draw call.
- **В2. Палитра heatmap и плавность перехода «точки → heatmap»** (ширина смешения 10% по дистанции — можно шире). Технически — uniform шейдера.
- **В3. Свет и небо** (процедурное/панорама, время суток), включать ли SSAO/glow на `high`. Бюджет §6 оставляет место только под SSAO.
- **В4. Дальность прорисовки зданий** (6 000 м импостор) и «туман» на краю вида вместо резкого обреза. Туман глубины дешёвый (не объёмный).
- **В5. Тени у пешеходов на `high`** — да/нет (±0.05 M треугольников теней).

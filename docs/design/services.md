Статус: спека, 2026-10-30 (агент L97), на утверждение владельцу. Решения владельца — `docs/plan/global-topics.md` тема 5 (два рода

## 2. Модель
### 2.1 Режим
**`city.services`** — секция сценария, требует `city.lifecycle` (BL). Без секции ЖКХ работает как в BL (встроенная запись `utility`,
§2.2), болезни, пожаров, медицины нет. Включается в игровых сценариях (`game-city`, `yuryev-*`, `ys0-*`, новая игра) и в новых
`s1k-res-sr`, `s10k-res-sr`. Эталоны `*-res`, `*-res-bl`, s1k/s10k, Rust — не сдвигаются (§5).

### 2.2 Служба = запись данных
Новый вид контента пакета `services.json` (`content.services`, `format_version: 1`), предел `ModLimits.MaxServices` 32. Здания уровней —
обычные типы `buildings.json` с `kind: "service"`, машины — типы `vehicles.json` класса `special`. Поведение задают **перечисления кода**:
роли, виды вызовов, поводы визита, эффекты апгрейдов. Новая служба на существующих механизмах = только JSON; новый повод
(школа по возрасту, мусор по накоплению) = код + запись.

| Поле записи | Смысл |
|---|---|
| `id`, `rev`, `title` | `<пакет>:service/<имя>` |
| `fund` | `city` (казна) \| `utility` (фонд ЖКХ, BL) |
| `levels[]` | `type` (id здания), `role[]` ⊂ {`repair`, `light`, `inpatient`, `critical`, `fire`}, `lot_min` [фасад, глубина] клеток, `build_cost`, `upkeep_day`, `milestone`, `visit` {`capacity_day`, `beds`, `icu`, `open_slot`, `close_slot`, `stay_slots`}, `dispatch` {`vehicle`, `units`, `per_unit_day`}, `upgrades[]` |
| `upgrades[]` | `id`, `cost`, `upkeep_day`, `milestone`, `effect` ∈ {`units`, `visit_capacity`, `beds`, `icu`, `onsite_pct`}, `value` |
| `calls[]` (выездные) | `kind` ∈ {`repair`, `critical`, `fire`}, `urgent`, `on_call` (приоритет VC на выезде), `on_call_return`, `onsite_s`, `deadline_s`, `per_call` |
| `visits[]` («к ним ходят») | `reason` ∈ {`light`, `inpatient`}, `min_role`, `per_visit`, `max_cost_s` (дальше не поедет) |

Правила валидатора: `on_call: true` у `repair` запрещён (решение владельца, VC §9.2); машина — только класс `special`; эффекта «в обход
сети» в перечислении нет и не будет без решения владельца (вертолёт — дорогой, поздний, лимитированный, отдельной спекой); уровни 1–4,
роли уровня ⊇ роли предыдущего; `deadline_s ≥ onsite_s`. Ошибки — `ModError` как у прочего контента.

### 2.3 «Они выезжают»: общий диспетчер
Обобщение BL §2.10 без смены машины состояний. **Станция** (`SiteStore`, SoA, ёмкость `max_service_sites` 256): здание + поколение,
`Svc` (запись), `Level`, `UpgradeMask` (`byte`), `UnitsMax`, `Duty`, `BedsUsed`, `BedRelease[16]`, `IcuUsed`, `IcuRelease[16]`,
счётчики суток. Депо ЖКХ BL — станция записи `utility`.
- **Вызов** (`CallStore`, 24 Б: `Kind, Svc, Target+Gen, Ref+RefGen, Tick`): `Ref` — житель (скорая) или пожар (§2.7); ссылок у жителя
  и здания на вызов нет. Очереди — два кольца на запись: срочные (`urgent`) и обычные, FIFO внутри; ёмкость — `max_calls` (по
  умолчанию `max_buildings / 8`, мин. 256). BL `RepairQueue` = обычное кольцо записи `utility`, флаг `Requested` BL прежний.
- **Выезд** (фаза 9r, после прибытий, BL): до `max_dispatch_per_tick` (4) за тик — сначала все срочные кольца по индексу записи, затем
  обычные. Голова кольца: проверка поколения цели → выбор станции → поездка. Нет свободной машины ни на одной станции записи в
  компоненте — вызов остаётся головой (перегруз, §2.3.1), диспетчер идёт к следующему кольцу.
- **Выбор станции — по оценке времени в пути с пробками** (рекомендация §10.2): среди станций записи с ролью вызова, той же `RoadComp`,
  со свободной машиной на линии — минимум `Est = Skims.Get(cellS, cellT, Car, period)`; пусто или одна ячейка — манхэттен ×1.3 / 8 м/с
  + 60 с (формула `TravelSlots`). Равенство — меньший индекс станции. O(станций записи) обращений к скиму, без поиска пути.
- **Машина** — BL `CrewStore` (`Idle/ToSite/Working/Return` + новое `OffDuty`) с полем `Site` вместо `Depot`; связь машины
  `Resident = −2 − unit`, кольцо `CrewArrivals`, таймауты, агрегат (`DueTick` по скиму) — без изменений.
- **Приоритет:** при постановке в `ToSite` для вызова с `on_call` — `SetOnCall(vehicle, true)` (VC §2.4: выделенки, красный ≤ 15 км/ч);
  снимается на прибытии; на `Return` — только при `on_call_return` (скорая с пациентом). ЖКХ — никогда. В агрегате флаг не нужен.
- **На месте:** `Working` на `onsite_s · onsite_q` (апгрейды и ползунок, §2.4); затем действие вызова (`repair` — ремонт BL, `critical`
  — пациент на борту, `fire` — тушение §2.7) и `Return` на свою станцию. Скорая доставляет на **свою** станцию (база = медцентр, роль
  `critical` ⇒ есть `icu`): на прибытии `Return` — приём в реанимацию.
- **Отклик** — `arrive − call.Tick` (тики): счётчики записи `CallsDone, RespTicksTotal, CallsLate` (позже `deadline_s`), EWMA по клетке
  128 м (охват, §2.9).

#### 2.3.1 Перегруз
Очередь растёт, вызов ждёт свободную машину любой станции — «скорая из дальней станции» получается сама (ближайшая свободная). Сверх
`deadline_s` у ждущего или едущего вызова — последствия вызова: `critical` — §2.5, `fire` — горит дальше (§2.7), `repair` — без срока
(износ BL). Без очереди событий: проверка срока — при взятии головы и при прибытии машины.

### 2.4 Бюджет службы 50–150 % и расходы
`SetServiceBudget {Svc, Pct}` — ожидающий, применяется на границе суток (как `SetBudgetPolicy`), шаг 10 %, дефолт 100.
- **Машины на линии:** `UnitsMax = units + upgrades + ceil(units/2)` (гараж под 150 %); `Duty = clamp(round(units' · pct / 100), 1, UnitsMax)`,
  `units'` — с апгрейдами. 50 % → половина, 150 % → +50 %. Лишние после смены — доезжают вызов и уходят в `OffDuty`.
- **Скорость работы:** `onsite_q = 100 / pct` × эффект `onsite_pct` апгрейдов (быстрее на месте при 150 %, медленнее при 50 %).
- **Визиты:** `capacity_day`, `beds`, `icu` × `pct / 100` (часы персонала). Приоритет вызовов от ползунка не зависит — только `urgent`.
- **Расход станции в сутки** (стадия «здания», при проходе её здания):
  `cost = (upkeep_day + Σ upkeep апгрейдов + per_unit_day · Duty) · pct / 100 + Σ per_call · вызовов_вчера + Σ per_visit · визитов_вчера`.
  Поток `ServiceUpkeep` (следующий свободный `FlowKind`, сейчас 22) со счёта `fund` записи на `External`; разбивка по записям —
  `SvcCostDay[svc·2 + day&1]` для панели бюджета. Ремонт BL (`Repair`) остаётся своим потоком.
- **Фонд ЖКХ** — правило BL §9.4 А (рекомендация): нет денег в `Utility` — заявка не выезжает. Для `fund: city` казна в минусе ничего не
  останавливает (мягкое банкротство `progression.md` §5): экономить можно только ползунком.

### 2.5 Болезнь
- **Байт жителя `Ill`:** биты 0–4 — дней осталось (0–31), 5–6 — тяжесть (1 лёгкая, 2 стационар, 3 критическая), 7 — `Treated`. 0 — здоров.
- **Где бросается:** в `DayPlanner.Build` (житель дома, раз в сутки), без PRNG-потока: `u = Mix64(seed ^ day·K1 ^ r·K2 ^ gen) mod 10⁶`
  (финализатор SplitMix, как `Util/FixedHashMap.cs:134`). Не зависит от порядка и числа потоков, в сейве ничего не добавляет.
  Пороги ppm на жителя в сутки (**стартовые**): критическая 300, стационар 600, лёгкая 3 000; × `disorder_ill_pct` 125 % при
  `Disorder > 0` в 3×3 (BL). **Крючок RA:** `incidence_ppm` — таблица по возрастной группе, v1 — одна строка `adult` (индекс 0); строки `child` (1),
  `elderly` (2) и их стартовые значения — `age-groups.md` §2.6 (действуют только в режиме `city.age`).
- **Длительность:** лёгкая 1 сутки, стационар 3, критическая 5. Без лечения в сутки болезни — `+1` день (до ×2 от исходной): «дольше болеют».
  Раз в сутки в `Build` больной: `days−−`; 0 → здоров.
- **Выпадение из экономики** — без новых путей: больной не получает рабочего и магазинных туров, значит фирма не платит смену и
  не считает выработку (`Economy.cs:42-50`), город не берёт налог с зарплаты. Работу житель не теряет.
- **Лёгкая и стационар** — житель едет сам (тур «к ним ходят», §2.6). **Критическая** — вызов `critical` к дому, житель дома без туров:
  - скорая на месте до `deadline_s` (600 с ≈ 4 игровых часа) → `Treated`, на станции — `IcuUsed++`, `IcuRelease[(day+days)&15]++`;
    нет места — всё равно принят, `days ×2`, счётчик `IcuOverflow`;
  - не успела (или некому: нет медцентра в компоненте) — последствие §10.3/§10.4: по рекомендации житель уезжает из города
    (`Leaving`), случай K4 и жалоба `NoAmbulance` у дома; вызов снят, машина в пути возвращается.
- **Связь житель ↔ больница не хранится:** койки — счётчик станции и кольцо выписки по дням (16 суток); вызов держит ссылку на
  жителя, пока жив. Стационар v1 — койка-счётчик: житель физически дома, но занимает место (туры не переходят через полночь, §1).

### 2.6 «К ним ходят»: тур к службе
- **Новый вид тура `TourKind.Care = 3`.** В `Build` нелеченный больной лёгкой/стационарной тяжести вместо всех туров получает один:
  желаемое прибытие 09:00 (слот 108) `+ seq % 24`, длительность `stay_slots` станции. Способ — прежний `Choice.TryChooseMode` (пешком,
  автобус, машина; пешая нога — обычный пешеход, `pedestrians.md`).
- **Выбор станции — без logit и PRNG:** все станции записей с поводом (`visits.reason`) и ролью `≥ min_role`, открытые к прибытию, в
  `RoadComp` дома (или пешей компоненте при `Walk`); стоимость — `Choice.LegCost` (`Choice.cs:314`) лучшего доступного способа; берётся
  минимальная среди тех, где **запись** `VisitsDay[сегодня] < capacity_day · pct / 100` (и `BedsUsed < beds'` для стационара). Запись —
  `VisitsDay++` при планировании (счётчик BL/C уже есть у здания). O(станций) на больного раз в сутки.
- **Мест нет / дальше `max_cost_s`:** тура нет, житель дома, `Treated` не ставится → болезнь длиннее (§2.5), завтра попытка снова;
  второй отказ подряд — жалоба `NoCare` у дома и случай K4. Это решение владельца «перегруз — очереди, дольше болеют».
- **Прибытие** (`CompleteLeg`, ветка `Care`): станция жива → `Treated`; стационар — `BedsUsed++`, `BedRelease[(day+days)&15]++`. Станции
  нет (снесли в пути) — как отказ. Счётчик `CareVisits`, стоимость ноги → EWMA клетки (охват).
- **Спрос не перекалибровывается:** туры к службам появляются только у больных (≈ 0.4 % жителей в сутки); выбор магазинов, частоты,
  скимы — прежние. В индекс `CellShopCap` станции не входят. Пик утром задаёт `open_slot` и желаемое прибытие.

### 2.7 Пожар
- **Возгорание** — стадия «здания» BL, тот же хэш-бросок по зданию и суткам: ppm в сутки `fire_ppm` типа (жильё 40, торговля 60,
  промышленность 150; **стартовые**) × `(100 + fire_risk_pct · min(FR₃ₓ₃, 20)) / 100` (`FireRisk` BL, `fire_risk_pct` 10) × 2 при
  `Cond < 50 %`. Момент — случайный тик суток из того же хэша (иначе все пожары в одном проходе курсора).
- **Пожар** (`FireStore`, пул `max_fires` 256, полон — пожар не начинается, счётчик): здание + поколение, `StartTick`, `Unit`. Бит
  `LifeFlags.Burning 64` (BL). Вызов `fire` (срочный) — в момент начала.
- **Стадии** (раз в секунду, вместе с таймерами бригад): тление `smolder_s` 120 с — `Cond −= 5 bp/с`; огонь — `−15 bp/с` (с 94 % до 0 за
  ≈ 10 мин симуляции). При входе в огонь — случаи K4 `Occupants` и жалоба `Fire`. `Cond < 50 %` — BL `Abandon` (жители выселены),
  `Cond = 0` — рассыпание BL (бесплатное удаление, вред соседям по стадиям BL до того).
- **Тушение:** пожарная на месте → `Working` `60 + горело_с / 4` (≤ 300 с) × `onsite_q` → огонь потушен, `Burning` снят, `Ceil −= ущерб/2`
  (до капремонта BL выше не поднимется). Одна машина на пожар (v1), крупное здание тушится дольше через `горело_с`.
- **Распространения нет** (рекомендация §10.1); здание с огнём даёт `FireRisk` клетке, как H3 BL.
- **Цена игнорирования:** без станции здание с `Cond` 100 % сгорает целиком: потеря жителей/фирмы, земли, налогов, вред квартала по
  стадиям BL. Проверка баланса — тест 6 §8.

### 2.8 Уровни, апгрейд на месте, пристройки
- **Постройка** — `BuildService {Lot, Type}` BL, тип — любой уровень записи с открытым `milestone` (цена — сумма `build_cost` уровней до
  него: строить сразу медцентр дороже, чем вырастить). Одна запись — одна станция на участке.
- **Апгрейд на месте** — `UpgradeService {Building, Annex[≤ 3]}` → уровень +1: машины, визиты, роли сохраняются, слоты машин
  добавляются. Участок проверяется по `lot_min` (`CellsF × CellsD`); мал — игрок указывает до 3 **соседних участков** той же стороны
  того же сегмента подряд по `S`: они становятся пристройкой (`LotFlags.Annex 4`, `Lots.Building[annex] = станция`). Занятые соседи
  выкупаются: цена `annex_buy_pct` 150 % от земли участка + снос BL (`demolish_cost`, разовое недовольство значимого, `heritage_loss_*`).
  Памятник выкупить нельзя (BL §9.5 Б). Реализатор грепает все чтения `Lots.Building[`: пристройка не участок роста. LP (полигоны)
  может заменить пристройки слиянием участков — модель службы от этого не меняется.
- **Локальные апгрейды** — `SetServiceUpgrade {Building, Id, On}`: бит в `UpgradeMask` (до 8 на уровень), эффект из перечисления §2.2.
  Снятие — без возврата денег, кроме окна `undo_refund_s`.
- **Снос** станции — `DemolishBuilding` BL: машины в пути доезжают и исчезают, вызовы возвращаются в голову очереди.

### 2.9 Охват на карте
Не круг, а факт: поля `RespEwma[rec, cell]` (секунды отклика, выездные записи) и `CareEwma[cell]` (стоимость ноги к службе) на сетке
BL 128 м, `ushort`, EWMA `>> 3` на каждом событии в клетке; 0 — «нет данных». API `GetServiceCoverage(svc, Span<ushort>)` заполняет
пустые клетки оценкой `Est` от ближайшей станции (вне тика, O(клеток · станций)). Клиент красит клетки, шкала — минуты.
*Реализация SR2:* пустые клетки — запасная формула `Est` (манхэттен ×1.3 на 8 м/с + 60 с) от ближайшей станции, без обращения к
скимам вне тика (их `Prepare` трогает производные кэши); выбор станции в тике — `Skims.Get` по ячейкам участков.

## 8. Тесты и приёмка
Модульные (`tests/Sim.Core.Tests/City/Services*`, малый город фикстуры BL):
1. **SR1 без изменения поведения:** `s1k-res-bl`, `s10k-res-bl` — хэш на тиках 0…N (N ≥ 2 суток) до и после рефакторинга равен;
   ЖКХ из записи `utility` ≡ ЖКХ BL; без `city.services` ни одного нового байта в хэше.
2. Загрузчик записей: схема, ссылки на типы, `on_call` у `repair` → ошибка, роли уровней, лимиты, моды.
3. **Отклик растёт с пробками:** тот же город и вызов, добавочная OD-нагрузка по маршруту станция → цель — `RespTicks` строго больше.
4. **Приоритет скорой:** выделенка + красный по пути — отклик скорой (`on_call`) меньше, чем той же машины без флага; ЖКХ флага не
   получает никогда; на `Return` флаг только при `on_call_return`.
5. **Перегруз:** вызовов больше, чем машин — очередь, срочные раньше обычных, выезд с дальней станции, `deadline_s` → последствия;
   ползунок 50 % — `Duty` вдвое меньше, отклик хуже; 150 % — наоборот, расход по формуле §2.4.
6. **Пожар:** стадии, тушение, `Ceil`; **баланс** — два прогона одного seed (с пожарной частью / без) за 10 суток: потери казны без
   части ≥ 1.5 × расход части за период в типовом квартале (подбор `fire_ppm` в SR6).
7. **Болезнь:** частота бросков ≈ ppm (10⁵ жителе-суток, допуск 10 %); больной без работы и покупок — у фирмы меньше смен и экспорта,
   налог с зарплаты ниже; лёгкий → тур к ближайшей станции с местом; мест нет → дольше болеет, жалоба на 2-й день; стационар занимает
   койку на `days`; критический → скорая → реанимация; не успела → `Leaving`.
8. Пристройки и апгрейд: `lot_min`, выкуп соседей (цена, снос BL, недовольство), памятник нельзя; апгрейды и их эффекты; undo в окне.
9. Детерминизм: `s10k-res-sr` хэш при 1/2/3 потоках; сейв на каждом тике вокруг выезда, приёма, пожара, апгрейда (шаблон
   `WorldSaveMomentsTests`); 0 Б/тик (`AllocationProbe`) с машинами служб в пути; агрегат ≡ те же события по таймерам.
10. Без режима: хэши `*-res`, s1k/s10k, Rust — прежние.

Приёмка (SR6, облако): `bench-gate` s1k без регрессии; `s10k-res-sr` tick p95 — справочно. В отчёте: вызовов и туров к врачу в
сутки, средний и p95 отклик по записям, доля опозданий, загрузка коек, пожаров/сгоревших, расход служб в доле дохода казны.

## 10. Вопросы владельцу (закрыты, см. §10.0)
## 10.0 Решения владельца (2026-10-30)
- **10.1 Пожар — вариант Б:** перекидывается на дом в той же клетке 128 м с шансом в минуту огня (+1 день в SR4, калибровка цепочек; пул пожаров и очередь не должны расти лавиной — потолок на число очагов).
- **10.2 Станция — вариант А:** по оценке времени в пути (статистика поездок). ЖКХ BL тоже переходит на неё — эталоны `*-res-bl` пересобираются в SR2.
- **10.3 Без медцентра:** критический больной **спустя время умирает** (не вариант Б). Нужны кладбища и крематории. Смерть и ритуальные службы — отдельная задача **SR7** после SR6: кладбище/крематорий — записи «к ним ходят/вывозят», тело — очередь вывоза, вместимость кладбища конечна, необслуженная очередь = жалобы и вред району. В SR1–SR6 исход критического — заглушка «уезжает» (как 10.4), поле исхода — точка расширения.
- **10.4 Не успела скорая — вариант А:** житель уезжает из города + недовольство района; в SR7 при включённой смерти — умирает (поведение данными).

### 10.1 Распространяется ли пожар на соседей в первой версии
**Что это.** Пожар начинается в одном здании (чаще — у ветхих и рядом с заброшками). Вопрос — может ли огонь перекинуться на соседний дом,
пока пожарные едут. Игрок увидит это как «сгорел один дом» или «сгорел квартал».

| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. Не распространяется** (рекомендую) | горит один дом; не приехали — он сгорает | просто объяснить; цена игнорирования уже есть (дом, жители, вред району) | нет «катастрофы квартала» | 0 |
| Б. Перекидывается на дом в той же клетке 128 м с шансом в минуту огня | опоздали — горит соседний дом, иногда два-три | драма, пожарные важнее в плотной застройке | цепочки трудно калибровать; пул пожаров и очередь растут лавиной при перегрузе | +1 день в SR4, калибровка |
| В. Б + ветер и материал зданий | городские пожары | максимум реализма | новые поля, сложно балансировать | +3 дня |

Рекомендация — А: в v1 главное — связка «пробка → опоздание → потеря», Б можно добавить параметром позже без смены модели.

**Вопрос:** пожар в v1 — только в одном здании (А), перекидывается на соседей (Б) или с ветром (В)?

### 10.2 Откуда выезжает машина: ближайшая по прямой или по времени в пути
**Что это.** На вызов едет свободная машина одной из станций. Выбрать станцию можно по расстоянию по прямой (как BL для ЖКХ) или по
оценке времени в пути с учётом пробок (по накопленной статистике поездок). Разница видна у реки, железной дороги, вечной пробки:
по прямой близко, а ехать далеко.

| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. По времени в пути (оценка по статистике поездок)** (рекомендую) | скорая едет из той станции, откуда реально быстрее; станция за рекой не «ловит» вызовы | честно к пробкам (решение темы 5); почти бесплатно — одно чтение таблицы на станцию | оценка грубая внутри 1 км; ЖКХ BL меняет поведение (пересборка эталонов `*-res-bl` в SR2) | 0 |
| Б. По прямой | иногда машина едет в объезд через весь город | просто, как ЖКХ BL | противоречит «отклик по реальному трафику»: размещение станций обманчиво | 0 |
| В. Точный поиск пути от каждой станции | всегда лучшая станция | точно | поиск пути на каждую станцию на вызов — заметная нагрузка на s100k | +1 день, бюджет тика |

Рекомендация — А: точность почти как у В при цене Б.

**Вопрос:** станция для вызова — по оценке времени в пути (А), по прямой (Б) или точным поиском (В)?

### 10.3 Критический больной, пока в городе нет медцентра
**Что это.** Скорые базируются только в медцентре (роль уровня, решение владельца), а он открывается не сразу (стартово M3). До него
критических случаев ≈ 3 в сутки на 11 тыс. жителей.

| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| А. Скорой нет — житель теряется (как §10.4) | ранний город теряет жителей и злится, пока нет медцентра | сильный стимул к медицине | наказание без возможности ответа на ранних вехах | 0 |
| **Б. До первого медцентра критический лечится как стационар (едет в больницу сам, дольше болеет) + жалоба «нет скорой»** (рекомендую) | проблема видна и растёт, но не убивает до вехи | «удивить, но не убить молча» (тема 3); роль медцентра остаётся | слабее стимул | +0.5 дня |
| В. Медпункт с одной скорой | скорая есть сразу | просто | ломает роли уровней (решение владельца) | 0 |

Рекомендация — Б: проблема заметна с начала, а ответ открывается вместе с вехой.

**Вопрос:** критический больной без медцентра — теряется (А), лечится сам с жалобой (Б) или у медпункта есть скорая (В)?

### 10.4 Что, если скорая не успела
**Что это.** Критический вызов ждёт или едет дольше срока (стартово 600 с симуляции ≈ 4 игровых часа). Это главная «цена» пробок и
урезанного бюджета медицины. Смерти и демографии в ядре пока нет (RA — позже).

| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. Житель уезжает из города + недовольство района** (рекомендую) | опоздания стоят жителей и налогов; видно в отчёте «потеряно без скорой» | ощутимо, без новой механики смерти | «уехал» вместо «умер» — условность | 0 |
| Б. Только дольше болеет ×2 + недовольство | мягко | без потерь населения | экономия на медицине почти ничего не стоит — против «экономить всегда — пожар дороже» | 0 |

Рекомендация — А: цена ошибки ощутима, и её можно поменять на «смерть» в RA без смены модели.

**Вопрос:** скорая не успела — житель уезжает (А) или дольше болеет (Б)?

### 10.5 Приняты по умолчанию (поменять — словом владельца)
- SR — режим `city.services` поверх BL; без него — ЖКХ как в BL, эталоны `*-res`, `*-res-bl` не меняются.
- BL §9 — по рекомендациям BL (фонд ЖКХ пуст — ремонт ждёт; буст — вариант Б, условие охвата службами SR можно добавить данными).
- Ползунок 50–150 % шагом 10 %, с границы суток; меняет машины на линии, скорость работы и вместимость; приоритет вызовов — только по виду.
- Скорая везёт пациента в свою базу (медцентр); одна пожарная машина на пожар.
- Болезнь бросается при составлении плана дня, без PRNG-потока; стационар — койка-счётчик, житель дома; работу больной не теряет.
- Нет мест у врача — ждёт дома и пробует завтра, болеет дольше; дальше `max_cost_s` не едет.
- Пристройки — до 3 соседних участков на той же стороне улицы, выкуп 150 % земли + снос BL; памятник не выкупается.
- Первые уровни всех служб — M0; больница — M2; медцентр и пожарная часть — M3 (стартово). Вертолётов и иных обходов сети нет.

# Конвейер ассетов: здания, жители, ТС, деревья из кусков по seed (блок AP, этап 7)

Статус: спека, 2026-10-30 (агент L101), на утверждение владельцу. Решения владельца — `docs/plan/global-topics.md` тема 2 (сборка в клиенте
из кусков по seed; ручные модели — уникальным зданиям; стиль города + эпоха постройки + кисть района), тема 4 (парк — запись службы, аллея —
профиль дороги, кисть — декор, деревья — одна инстансная сетка с LOD), тема 6 (фигуры без лиц, тело + куски по группе и занятию, один скелет,
3–5 анимаций в текстуре, инстансы, ~20 тыс.), тема 7 (кузова и цвета внутри класса по seed, набор по стилю). Решение по рендеру и анимации —
ADR-0045. AP почти целиком клиентский; ядру — одна малая задача (§3). Вход от соседей: LP (полигон, пятно, `MainEdge`), FR (13 вариантов,
`floors`, бит `Podium`), BL (`R0` = состояние, `R1` = памятник/снос/стадия вреда), RA (группа в `PedRenderFlags` биты 3–4), VC (класс, `OnCall`).

## 1. Как сейчас
- **Здания — боксы.** `ChunkBuilder.TryBox` (`game/Scripts/ChunkBuilder.cs:54-102`): габарит из таблицы `_dims[зона, плотность]` (`:36-42`),
  плотность — чётность `Type` (`:63`), разброс и тон — хэш от `X, Z` (`:65-69`, `:115-123`), цвет — `Palette` по зоне/состоянию (`:76-81`).
  Три представления (`BuildingLayer.cs:11-12`): кольцо `MultiMesh` до LOD1 с тенями (`:193-232`), LOD2 — меши чанков 250 м, импосторы — 1 000 м
  (`:185-191`); перестройка слоя целиком по `BuildingsVersion` (`Api/Simulation.City.cs:85`). Участок здания — через `TryGetBuildingInfo`
  (`BuildingLayer.cs:168`, `Simulation.City.cs:421`).
- **Снапшот здания** — `BuildingRenderData` 24 Б (`Api/CityInfo.cs:59-71`): `X, Z, Heading, Type, Kind, State, FillPct, R0, R1, Gen`. `R0/R1`
  заняты BL (`building-lifecycle.md` §8: `R0` = `Cond` %, `R1` — 6 бит) и FR (`freight.md` §6: биты `Shortage`, `Podium`). Свободного байта нет.
  Эпохи, стиля, этажей в API нет; у типа этажи появятся с FR (`floors`), у участка — `Floors` крафта с LP (`lots-polygons.md` §3).
- **ТС** — процедурный бокс на тип × LOD (`VehicleLayer.cs:58-66`), автобус выше (`:63`); цвет легковой — `slot % 5` (`:282`, `Palette.cs:130`),
  при переиспользовании слота машина «перекрашивается». `VehicleRenderData` 32 Б без свободных байтов (`Api/Snapshots.cs:8-19`), все 8 бит
  `Flags` заняты (`:21-33`, `Meso` ставится в `Api/SnapshotPhase.cs:93,138`). `OnCall` — бит `VehicleFlags` ядра, в снапшот не идёт (VC §6).
  Headless-кадр: `Sim.Headless/Render/FrameRenderer.cs:148-160` — цвет по `Bus`.
- **Пешеходы** — капсула LOD0 / бокс LOD1 / точки (`PedMesh.cs:3-8`), цвет по `PedState`. `PedestrianRenderData` 24 Б (`Api/PedInfo.cs:36-46`),
  `Flags` биты 0–2 заняты, 3–4 — группа RA; **5–7 свободны**. Скорости и жителя в снапшоте нет.
- **Батчи** — `BoxBatch`: `Transform3D` + цвет, шаг 16 float (`BoxBatch.cs:17,45-46`), без custom data. Шейдеры — `game/Shaders/*`, рёбра по UV
  грани (`visual-style.md` §3). Путь рендера — Forward+, фолбэк Compatibility (`render.md` §1).
- **Деревьев нет.** Парки — полигоны `LandUse` (`visual-style.md` §8). Элемент профиля `verge` — только ширина; `RoadElemData.R0` (ushort)
  свободен (`Api/RoadProfileDesc.cs:270-278`).
- **Моды:** `visual.model` у типов ТС/зданий/пропов (`modding.md` §4.1), glTF-валидатор и бюджеты формата 2 (`render.md` §4).

## 2. Модель: три слоя данных
1. **Ядро знает смысл:** вид и вариант (тип), этажи при постройке, эпоху, стиль-индекс, состояние; класс ТС и «на вызове»; группу и род занятий
   пешехода; где аллея. Всё — байты, без влияния на симуляцию.
2. **Стиль — данные пакета** (`styles/<id>.json`, §4): эпохи, палитры, куски, правила сборки, растительность, кузова ТС, одежда.
3. **Клиент собирает** детерминированно: `(вход ядра, стиль, seed) → список кусков → геометрия`. Сборщик — чистый C# без Godot
   (новая библиотека `src/Sim.Assets`, net8.0, не в `Sim.Core`): тестируется xUnit и headless-валидатором, Godot только заворачивает массивы
   в `ArrayMesh`.

**Seed — производный, не хранится** (0 новых PRNG-бросков, эталоны не сдвигаются):
| Объект | Seed | Почему |
|---|---|---|
| Здание | `Mix32(slot, Gen)` из `BuildingRenderData` | новое здание на месте старого — новый облик; переживает сейв (пул в `BLDG`) |
| Участок (подложка, деревья во дворе) | индекс участка (LP §6) | облик участка не зависит от застройки |
| ТС | `Mix32(Index, Generation)` | машина держит цвет всю жизнь (вместо `slot % 5`) |
| Пешеход | `Mix32(Index, Generation)` | одежда на поездку; житель в снапшоте не виден — принято (§10.5) |
| Дерево | `Mix32(сегмент/полигон, номер посадки)` | — |
`Mix32` — SplitMix32 в `Sim.Assets/Hash.cs`; выбор из списка — `h % Σweight` целыми, без float и `System.Random`.

## 3. Ядро: задача AP1 (малая)
**Режим `city.look`** (секция `city`, необязательная): без неё код AP1 не исполняется, хэш и сейв побитово прежние.
```json
"look": { "style": "base:ru", "start_year": 1955, "years_per_day_x100": 100, "pre_years": 60 }
```
Загрузчик находит стиль в каталоге пакетов и копирует в `CityDesc.Look` только числа: `EraFromYear[]` (≤ 4, по возрастанию) — ядро файлов
стиля не читает. Стиль на новую игру — выбор на экране новой игры (клиент пишет `look.style`); сценарий задаёт свой.

**Поля и правила:**
| Где | Поле | Тип | Правило |
|---|---|---|---|
| `Buildings` | `Era` | byte | при `Place`: год `Y = start_year + Day · years_per_day_x100 / 100` (целые), `Era = max e: EraFromYear[e] ≤ Y`; потом не меняется |
| `Buildings` | `Floors` | byte | этажи, по которым считан `Cap` при постройке (LP §2.7: `Floors` участка, иначе типа); если LP/FR уже пишут — не дублировать |
| `Buildings` | `Style` | byte | v1 всегда 0 (стиль города); кисть района (§7.3) — позже |
| Генератор (`CityInit`) | `Era` стартовой застройки | — | синтетический год `Y = start_year − pre_years · (R − r) / R`, `r` — расстояние центроида до центра города, `R` — полуразмер; целые мм, без PRNG → центр исторический |
| `PedRenderFlags` | `WorkShift = 5` (биты 5–6) | 2 бита | род занятий из варианта зоны места работы: 0 нет, 1 офис/торговля, 2 промышленность/склады, 3 службы; пишется в проходе снапшота (одно чтение `Work → Type → Zone` на видимого пешехода, как RA) |
| Снапшот ТС | `OnCallVehicles` | `ReadOnlySpan<int>` | слоты машин с `OnCall` в прямоугольнике вида; заполняется в том же проходе `SnapshotPhase`, буфер `max_on_call` (256, стартовое) рядом с `Vehicles` (двойная буферизация как у них); переполнение → без мигалок, счётчик |
| Каталог профилей | `RoadElemData.R0` у `verge` | ushort | шаг деревьев аллеи, дм; 0 — без деревьев (§6) |

- **API:** `GetBuildingLooks(Span<BuildingLook>)`, `BuildingLook { byte Era, Style, Floors, R; }` 4 Б, индекс = слот здания, читается по
  `BuildingsVersion` (статический канал, как `GetLotGeometry` у LP). `BuildingRenderData`, `VehicleRenderData`, `PedestrianRenderData` — размеры
  прежние. `Simulation.Look` — копия `CityDesc.Look` для клиента (год для UI: «построен в 1978»).
- **Хэш:** `Era`, `Floors`, `Style` — в `CityHash` только при режиме. Список `OnCallVehicles` и биты `WorkShift` — снапшот, не состояние.
- **Сейв:** `world_version` — следующий свободный на момент захвата AP1 (ожидается ≥ 21: VC 16, BL 17, SR 18, FR/LP/RA дальше). Режим
  прототипа: без миграции, корпус пересобирается. `BLDG`: `Era`, `Floors`, `Style`; `PARM`: `LookStartYear`, `LookYearsX100`, `LookPreYears`,
  `LookEraFrom0..3`; `RPRF`: столбец `R0` элементов, если ещё не пишется. Строковый id стиля — **`MANI` вид 6** (хост, как вид 2 для визуала
  зданий): ядро хранит запись, клиент по ней находит пакет; нет пакета → стиль `base:ru` + `AssetNotice`.
- **Аллеи в каталоге:** ключ `"trees": {"spacing_m": 8}` у `verge` (валидатор: 4–30 м, `verge` ≥ 2 м). Два новых профиля в
  `scenarios/road-profiles.json`: `street_2_alley` (24 м: verge 5.25 по сторонам) и `arterial_4_alley` (32 м). Стоимость — по ширине (как все
  профили), участкам теснее — автоматически (LP режет от кромки). Ядро знает, где аллея: `ProfileElems[...].R0 > 0` — точка привязки шума (тема 4).
- **0 Б/тик и бюджет:** `Era/Floors` — при `Place`, вне тика; `WorkShift` и `OnCallVehicles` — одна ветвь на видимый объект в снапшоте.

## 5. Сборка здания (детерминированно)
Вход: вариант и роль (тип), `Floors`, пятно (полигон LP, `MainEdge`; до LP — прямоугольник `TryBox`), стиль, `Era`, seed, `Podium`.
1. **Кит** = `kits[вариант, эпоха]`; если у типа есть `whole`/`visual` — ручная модель, конец.
2. **Стены:** экструзия пятна на `ground_h + (Floors−1) · floor_h`. Каждое ребро пятна делится на пролёты: `n = max(1, round(len / w_m))`,
   ширина пролёта `len / n` (масштаб куска по X 0.8–1.25; вне — пролёт `bay_blank`). Дуги LP — цепочка коротких рёбер, у ребра < 2 м — глухая
   стена без кусков (скругление держит экструзия).
3. **Выбор кусков:** на ребро — один кусок `body` по `Mix32(seed, ребро)` (вертикальная «тема» фасада, как у реальных домов), на этаж —
   тот же; углы — `rules.corner`; `ground` — по роли (`podium` → витрины), вход — на `MainEdge` в середине. Детали — бросок на пролёт
   `Mix32(seed, ребро, этаж, пролёт) < p`.
4. **Крыша:** `gable` только при 4 вершинах, близких к прямоугольнику, и пролёте ≤ `max_span_m`; иначе плоская с парапетом
   (экструзия кромки 0.4 м внутрь). Технический короб — деталь крыши.
5. **Цвета:** по одному индексу палитры на здание для `wall`, `roof`, `trim` (`Mix32(seed, 1..3)`); тон ±4 % (как `BuildingToneJitter`).
6. **Выход:** `PartList` (целые: id кусков, ребро, этаж, пролёт, индексы цветов) → `MeshArrays` LOD0 (все куски), LOD1 (экструзия + крыша +
   полосы окон цветом в вершинах, ≤ 300 тр.), LOD2 = нынешний бокс (≤ 10–12 тр., чанк), импостор — прежний.
- **Бюджет LOD0** (стартовое): ≤ 1 500 тр. на здание до 6 этажей, ≤ 3 000 выше (предел ассета 5 000 сохраняется). Пролёт ≤ 40 тр., деталь ≤ 24.
  Валидатор считает бюджет на эталонных пятнах (§8 п. 2).
- **Состояние без новых мешей (v1):** строится — тот же меш, срез по высоте в шейдере (`y > H · FillPct`) + цвет `BuildingConstructing`;
  износ — затемнение/обесцвечивание по `R0` (`Cond`); заброшено — стёкла в тёмный, тон `BuildingAbandoned`; стадия вреда — штриховка
  (BL C1); памятник — без смены геометрии (значок — BL C1). Всё через **текстуру данных зданий** (RGBA8, ширина 4 096, по слоту: R = `Cond`,
  G = прогресс, B = биты состояния; 2 Гц, шаблон `HeatTextures`), индекс слота — `CUSTOM0.x` вершин чанка. Смена состояния не пересобирает меш.

### 6.2 ТС
- Кузова — параметрические (как куски, §4): `car` 5 (седан, хэтчбек, универсал, SUV, малолитражка), `van` 2, `truck` 1 (тягач + прицеп по
  длине типа), `bus` 1 (длина по типу), `special` 3 (скорая на базе фургона, пожарная на базе фуры-шасси, ЖКХ — фургон с кузовом-будкой).
  LOD0 ≤ 400 тр. (предел 1 200), LOD1 ≤ 60 (два бокса), LOD2 и точки — как сейчас. Габарит — длина/ширина типа (`VehicleLayer.cs:58-66`).
- Батчи: `MultiMesh` на (тип × кузов × LOD); DC ≈ 3 · Σкузовов + 1 ≈ 40 ≤ `3·T+1` при T ≤ 13 (`render.md` §1.3). Кузов и цвет —
  `Mix32(Index, Generation)` по весам стиля; спецмашины — цвет ливреи стиля (кузов + полоса цветом вершин).
- **Мигалки:** у LOD0/LOD1 спецмашин бокс-маячок; слоты из `OnCallVehicles` (§3) → custom data инстанса `x = 1`, шейдер мигает
  (`fract(TIME · 2)`, два цвета ливреи, unshaded, умножается на `light_tint`); без ядра AP1 — маячок не горит. Точки ТС на вызове — цвет маячка.
- `FrameRenderer` (headless) — цвет по классу из `VehicleTypes[Type].Category`; кузова не рисует.

### 6.3 Жители
- **Скелет один**, 12 костей (таз, корпус, голова, плечо/предплечье ×2, бедро/голень ×2, ступни — в голени). **Жёсткая привязка:** вершина —
  одна кость (индекс в `CUSTOM1.x`); для низкополигональных фигур без лиц достаточно.
- **Тела** — 3 меша по группе (ребёнок — пропорции + масштаб инстанса 0.65, взрослый, пожилой — сутулость в позе покоя), каждый с **полным
  набором аксессуаров** (пальто, сумка, трость, рюкзак, каска, кепка); маска частей в custom data инстанса, лишние вершины шейдер схлопывает.
  LOD0 видимых ≤ 300 тр., меш с аксессуарами ≤ 450. LOD1 — фигура 12–16 тр. цветом верха, точки — как сейчас.
- **Анимация — текстура матриц костей** (bone animation texture, разновидность VAT): `RGBA16F`, ширина = 12 костей × 3 текселя, высота =
  кадры всех клипов (30 к/с). **Клипы — параметрические** (данные стиля/базы: амплитуды бедра, колена, рук, подскок, наклон), запекаются
  в клиенте при загрузке (< 50 мс): `walk` (1.0 с, цикл), `wait` (2.0 с, переминание), `board` (0.8 с, шаг вверх). Всего ≈ 114 кадров →
  текстура 36 × 114 ≈ 33 КБ. Офлайн-инструмента и Blender нет; моды анимаций — позже (glTF `skins` пока `GltfFeature`, `modding.md` §4.2).
- **Клип и фаза:** `Walking/Crossing` → `walk`, фаза = пройденное расстояние / длина шага (скорость — из prev/curr снапшота); остальные
  состояния → `wait`, фаза со сдвигом по seed. `board`: пешеход был `AtStop` и пропал из снапшота (`OnBus`) → клиент 0.8 с проигрывает
  «призрака» на последней позиции (пул 256, без ядра).
- **Custom data инстанса** (4 float, точные целые до 2²⁴): `x` = клип (2 бита) + фаза (16 бит); `y` = палитра верх/низ/аксессуар/кожа
  (4 × 4 бита); `z` = маска аксессуаров (≤ 16 бит); `w` = резерв (выделение). `MultiMesh`: `Transform3D` + цвет + custom = 20 float.
- **Выбор частей:** группа — `PedRenderFlags` биты 3–4 (RA), занятие — биты 5–6 (AP1), остальное — seed по весам `people` стиля. Без RA/AP1 —
  все взрослые без рабочей одежды.
- **Бюджет 20 тыс.** (оценка, `low`): LOD0 200 × 300 = 60 тыс. тр., LOD1 2 000 × 16 = 32 тыс., точки 20 000 × 2 = 40 тыс. → ≈ 0.13 M (как
  `render.md` §1.3). DC: 3 тела LOD0 + 1 LOD1 + 1 точки = 5, тени — 3 (только LOD0) → **пешеходам ≤ 5 DC вместо ≤ 3** (правка `render.md`
  §1.3 в AP5). Дистанции — нынешние 40/150/900 м (`render.md` §4.1 `pedestrian`), подбор замером AP7.

### 6.4 Деревья
- **Одна сетка на вид** (`broadleaf`, `conifer`, `shrub`, параметрические): LOD0 ≤ 48 тр., LOD1 ≤ 8 (октаэдр-крона + ствол), дальше нет
  (парк виден цветом земли). `MultiMesh` на (вид × LOD) = 6 DC, тени — LOD0. Лимиты (стартовые, `low`): LOD0 800, LOD1 8 000 →
  ≈ 0.1 M тр. — укладываются в «пропы» `render.md` §1.3. Цвет кроны — `greens` стиля по seed; масштаб 0.8–1.2, поворот — seed.
- **Где:** аллеи — вдоль осей сегментов с `verge.R0 > 0`, по центру газона, шаг `R0`, сдвиг фазы — seed сегмента; пропуск ≤ 12 м до узла,
  у переходов и остановок (`Crossings`, `BusStops`). Парки — `LandUse` `Park` и записи службы «парк» (SR, тема 4): решётка 12 м с джиттером
  по seed, без пруда. Кисть декора — §7.4. Пересборка — по `Network.Version` / `LandUseVersion` / смене парков, по чанкам 250 м.
- Ядро о деревьях знает только `R0` аллеи; парк — запись SR. Оценка s100k (справочно): ≈ 25 тыс. деревьев аллей при 100 км аллей + парки.

## 7. Стиль, эпохи, кисти
### 7.1 Стиль города
Выбор на экране новой игры (список стилей пакетов; v1 — один, §10.3), пишется в `city.look.style`, `MANI` вид 6. Сменить стиль у живого города
нельзя (облик фиксирован при постройке).
### 7.2 Эпохи
Таблица `eras.from_year` стиля; год постройки — по календарю `look` (§3; стартовое: 1955 + 1 год за игровые сутки → «modern» с 1985 = 30-е
сутки). Стартовая застройка генератора — по кольцам (центр — исторический). Снос и новая постройка — новая эпоха (и новый seed); `RestoreBuilding`
(BL) эпоху не меняет. Эпоха и `Cond` независимы: старый дом может быть отремонтирован, новый — изношен.
### 7.3 Кисть стиля района (крафт)
Место данных зарезервировано: столбец участка `LOTS.Style` (byte, 0 = стиль города), команда `SetLotStyle` по области — **ядро** (сейв, хэш,
отмена, как прочий крафт LP), `BuildingLook.Style` = стиль участка на момент чтения (кисть перекрашивает и существующие дома — смысл «перекрасить
район»). Только вместе с ≥ 2 стилями. **Вопрос владельцу §10.4.**
### 7.4 Кисть декора (деревья, кусты)
Чистый клиент, ядро не знает (тема 4). Хранение — непрозрачный блок сейва `DECO` (ядро пишет/читает байты, не в хэше, ≤ 1 МиБ; формат —
клиента: список посадок `x, z` в см + вид). Задача AP8, после v1.

## 10. Вопросы владельцу
### 10.1 Здания: «запечь» куски в общие меши кварталов или рисовать каждый кусок инстансом
**Что это.** В теме 2 записано «куски рисуются инстансами». Инстанс — одна модель, нарисованная тысячи раз одной командой видеокарте.
Для людей, машин и деревьев это лучший путь. Но дом теперь стоит на участке-полигоне (LP): дуга, скошенный угол, уступ. Окно-кусок 3 м,
поставленное инстансом, не обрезать по дуге — будут щели и наложения. «Запечь» — сборщик склеивает куски дома в один меш квартала в фоне,
видеокарта рисует квартал одной командой. Игрок видит одно и то же; разница — в качестве углов и в цене пересборки.
| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. Запекание в меши кварталов** (рекомендую) | дома точно по пятну, скруглённые углы без щелей | как нынешние дальние чанки; ≈ 120–200 DC; один материал | пересборка квартала при новой постройке (в фоне, ≤ 1 чанк за кадр) | AP2 ≈ 3–4 дня |
| Б. Куски инстансами | на дугах и косых углах — щели, наложения окон | меньше памяти; смена дома без пересборки | ≈ 160 инстансов на дом; LP-облик теряется | AP2 ≈ 3 дня + доводка углов (неизвестно) |
| В. Готовые дома-архетипы + цвет | повтор одинаковых домов, не по форме участка | дёшево | противоречит LP и теме 2 (облик по кромке) | 2 дня |
Рекомендация — А: инстансы остаются там, где они выигрывают (люди, ТС, деревья, ручные модели), дома — по форме участка.
**Вопрос:** здания запекаем в меши кварталов (А), рисуем кусками-инстансами (Б) или архетипами (В)?

### 10.2 Откуда берутся куски: рисовать вручную или описывать числами
**Что это.** Куски (окно, балкон, крыша, кузов, пальто) нужно откуда-то взять. Вручную — в Blender (моделинг, экспорт glTF). Числами —
кусок описан в JSON как набор коробок и вырезов в метрах с цветом из палитры, как вёрстка в CSS; клиент строит его при загрузке, превью
показывает результат через секунду после сохранения файла. ИИ-генераторы 3D дают «грязные» сетки на тысячи треугольников и разный стиль.
| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. Параметрические куски в JSON + превью** (рекомендую) | чистый low-poly стиля B, ровные пропорции | правит владелец без 3D-пакета; моды — тем же JSON; бюджет считается автоматически | сложные формы (купола, лепнина) — только glTF | AP0 + AP3 ≈ 5–6 дней |
| Б. Ручной набор в Blender | богаче силуэты | любые формы | нужен 3D-художник или освоение Blender; каждая правка — экспорт | ≈ 2–3 недели художника |
| В. ИИ-генерация мешей | разнобой стиля, «мыльные» формы | быстро получить черновик | бюджет треугольников, чистка, лицензии | непредсказуемо |
Рекомендация — А: дешевле всего и в руках владельца; glTF остаётся для уникальных зданий и модов.
**Вопрос:** куски описываем числами в JSON (А), рисуем в Blender (Б) или генерируем ИИ (В)?

### 10.3 Сколько стилей в первом выпуске
**Что это.** Каждый стиль × эпоха — полный набор кусков на 13 вариантов застройки (≈ 15–20 кусков). Один стиль с двумя эпохами уже показывает
главное: центр старый, окраины новые.
| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. 1 стиль (российский) × 2 эпохи** (рекомендую) | исторический центр и современные окраины | проверяет весь конвейер; быстро до игры | выбор стиля на старте — пока из одного | AP3 ≈ 2–3 дня |
| Б. 3 стиля × 1 эпоха | разные города, внутри города однородно | выбор на старте сразу | эпохи (главная идея темы 2) не видны | ≈ 6 дней |
| В. 3 стиля × 2 эпохи | всё сразу | полный замысел | тройная работа до проверки конвейера на игроке | ≈ 10–12 дней |
Рекомендация — А: доказать конвейер на одном стиле, затем добавлять стили данными.
**Вопрос:** первый выпуск — 1 стиль × 2 эпохи (А), 3 × 1 (Б) или 3 × 2 (В)?

### 10.4 Кисть стиля района — в первой версии или позже
**Что это.** Кисть «перекрашивает» район в другой стиль. Имеет смысл, только когда стилей ≥ 2.
| Вариант | Что увидит игрок | Плюсы | Минусы и риски | Цена |
|---|---|---|---|---|
| **А. Позже, вместе со вторым стилем** (рекомендую) | v1 без кисти стиля | ничего лишнего; место в данных зарезервировано (§7.3) | — | 0 сейчас, ≈ 1.5 дня потом |
| Б. В v1 | кисть есть, но выбор из одного стиля и эпох | инструмент готов заранее | кистью нечего красить (при ответе А на §10.3) | +1.5 дня (ядро + клиент) |
Рекомендация — А.
**Вопрос:** кисть стиля района — позже со вторым стилем (А) или в v1 (Б)?

### 10.5 Приняты по умолчанию (поменять — словом владельца)
- Seed здания — слот + поколение (новый дом на месте старого — новый облик); участка — индекс участка (LP).

# Маршрутизация: граф, A*, кэш по парам зон, бюджет, движение по маршруту (спецификация, шаг 3)

Статус: принято (ADR-0005). Реализуется задачей J (`core-api.md` §14) в `Routing/` поверх `RoutePool`
(`core-api.md` §6.5), `RouteStep`/`RouteView` (§5.5), фазы 3 (§7). Перекрёстки — `intersections.md`.
Изменения в `core-api.md`, вызванные этой спекой, — §12.

**Этап 2 (ADR-0009):** кэш магистралей по парам зон (§4.1–4.3), `RoutePool`-арена и полный поиск при перемаршрутизации
заменяются иерархическим оверлеем ячеек и маршрутом «план + окно» — §9. Разделы §1, §2, §5, §6 остаются в силе.

Требования ТЗ: A* с весом = время в пути; кэш маршрутов по парам зон; бюджет запросов на тик;
машина появляется на краю/парковке и исчезает только по прибытии; метрики `pathfind_queries`,
`pathfind_ms_p95`; 0 B/тик; детерминизм.

## 0. Решения коротко

| Вопрос | Решение |
|--------|---------|
| Граф поиска | **направленные сегменты** (`DirSeg = segment·2 + dir`) + дуги-манёвры (есть хотя бы один connector между ними). Полосы раскладываются после поиска (§5). |
| Вес | статическое время: `Length / SpeedLimit` + штраф манёвра + штраф узла (светофор/знак). Текущая загрузка — этап 2 (§9). |
| Эвристика | евклидово расстояние до узла цели / `VMax` (максимальный лимит в сети) — допустимая и монотонная. |
| Кэш | по `(FromZone, ToZone)` хранится **магистраль** хаб(A) → хаб(B); маршрут машины = префикс + магистраль + суффикс, собирается в индивидуальную запись `RoutePool`. |
| Бюджет | `PathfindBudgetPerTick` запросов + предел раскрытий на тик; очередь — `PendingTrips` (маршрут строится **до** спавна) и кольцо перемаршрутизации. |
| Перемаршрутизация | только при промахе полосы (нужный connector недостижим); по времени — этап 2. |
| `pathfind_ms_p95` | меряет `Sim.Headless` через зонд `Simulation.OnPhaseEnd` (ядро wall-clock не трогает). |

## 1. Граф поиска

`DirSegCount = 2·SegmentCount`, `u = seg·2 + dir` (`dir` 0 = A→B, 1 = B→A). Направление без полос
(`LanesAB == 0`) существует как вершина, но без входящих/исходящих дуг. `EndNode(u)` — узел, в
который ведёт `u`; `StartNode(u)`.

CSR-смежность, перестраивается целиком в `Create` и после каждого применённого `BuildRoad`
(O(connector'ов); `BuildRoad` — редкая команда пользователя, инкрементальность — этап 2):

```csharp
namespace Sim.Core.Routing;

internal sealed class RouteGraph
{
    public int DirSegCount, ArcCount;
    public readonly int[]   ArcFirst;     // [2*MaxSegments + 1]
    public readonly int[]   ArcTo;        // [MaxConnectors]  целевой DirSeg
    public readonly float[] ArcCost;      // [MaxConnectors]  штраф манёвра + узла, с
    public readonly byte[]  ArcManeuver;  // [MaxConnectors]  Straight/Right/Left/UTurn (минимальный по штрафу среди connector'ов пары)
    public readonly float[] SegCost;      // [2*MaxSegments]  Length / SpeedLimit, с
    public readonly Vec2[]  EndPos;       // [2*MaxSegments]  позиция EndNode(u)
    public float VMax;                    // max SpeedLimit по сети
}
```

Дуга `u → w` существует, если есть connector с `FromLane ∈ lanes(u)`, `ToLane ∈ lanes(w)`; дубликаты
(несколько полос) схлопываются в одну дугу с минимальным штрафом. Дуги вершины упорядочены по `w`
(детерминированно). Дуг ≤ connector'ов.

### 1.1 Веса (секунды)

`cost(u → w) = SegCost[w] + ArcCost(u → w)`; стартовая вершина даёт `SegCost(u) · (1 − S/Length)`
(остаток текущего сегмента), целевая — `SegCost(goal) · DestS/Length` вместо полного (учитывается при
проверке цели, см. §2).

| Штраф | Значение |
|-------|----------|
| Манёвр: Straight / Right / Left / UTurn | 0 / 3 / 6 / 20 с |
| Узел `Signal` (любой режим `Fixed`) | `+ (Cycle − Green_моей_фазы)² / (2·Cycle)` — средняя задержка равномерного прибытия; при плане по умолчанию (56/24) ≈ 9 с; считается при построении графа из текущего плана |
| Узел `Signal`, `Adaptive` (2.5, ADR-0018) | та же формула с `g = (MinGreen + MaxGreen)/2`, `C = Σ(g + Yellow + AllRed)` (дефолт ≈ 7.1 с); в координации `C` и `g = C/2 − Yellow − AllRed` (72 с → 11.1 с). **Любой режим `Signal`**: измеренная задержка `ConnDelay` (EWMA среднего `WaitTicks` при допуске, пересчёт с весами раз в 30 с, ≥ 5 допусков) заменяет статику; клэмп 0…60 с — `intersections.md` §6.9 |
| Узел `Yield`/`Stop`, въезд с minor-рукава | + 6 / + 9 с |
| Узел `RightHandRule` (≥ 3 рукава) | + 3 с |
| Узел без ворот (`None`, ≤ 2 рукава) | 0 |

Константы — `internal static class RoutingCosts` (одно место; калибровка после шага 5, формат не
меняется). `SetSignalPlan`/`SetNodeControl` меняют штрафы дуг узла на месте (без полного rebuild) и не
инвалидируют кэш: маршруты остаются корректными, лишь слегка неоптимальными.

## 2. A*

Состояние поиска (выделяется в `Create`, живёт в `World`):

```csharp
internal sealed class AStarState
{
    public readonly float[] G;            // [DirSegCount]
    public readonly int[]   Parent;       // [DirSegCount]  предыдущий DirSeg или -1
    public readonly uint[]  SeenStamp;    // [DirSegCount]  == SearchId → G/Parent валидны
    public readonly uint[]  ClosedStamp;  // [DirSegCount]  == SearchId → раскрыт
    public readonly float[] HeapKey;      // [HeapCapacity] f
    public readonly int[]   HeapVal;      // [HeapCapacity] DirSeg
    public int HeapCount; public uint SearchId;
    public readonly int[]   Path;         // [DirSegCount] буфер восстановления пути (в обратном порядке)
}
```

- `SearchId++` на каждый поиск; штампы заменяют очистку массивов (O(1) старт). Переполнение `uint`
  (4·10⁹ поисков) — обнулить штампы один раз, допустимая O(N) операция.
- Куча — бинарная min-heap по `(HeapKey, HeapVal)` лексикографически (равные `f` → меньший `DirSeg`;
  это и есть детерминированный тай-брейк). **Ленивое обновление**: при улучшении `G` вершина
  добавляется повторно, устаревшая запись отбрасывается при извлечении (`G[v] + h(v) < key` или
  `Closed`). `HeapCapacity = MaxConnectors + 2·MaxSegments` (не больше одного добавления на ослабление
  дуги + старты); переполнение невозможно по построению, но проверяется → отказ поиска (`RouteFailed`).
- Эвристика `h(v) = |EndPos[v] − EndPos[goal]| / VMax`. Дуга `v → w` стоит ≥ `Length(w)/VMax ≥ (|EndPos[w] − EndPos[v]|)/VMax`
  (длина оси ≥ хорды) → монотонна, повторных раскрытий нет, `ClosedStamp` корректен.
- Цель: `DirSeg` целевой полосы (`DestLane`), либо множество целей для магистрали (§4).
  Многоисточниковый старт: все стартовые вершины кладутся в кучу с их `G`.
- Ограничения: `MaxExpansions` на поиск (`DirSegCount` для полного, `LocalExpansionCap = 512` для
  префикса/суффикса) и бюджет тика (§3). Превышение — отказ **этого** поиска с кодом.
- Восстановление пути: по `Parent` в `Path` (обратно), длина `k+1 ≤ DirSegCount`; затем раскладка на
  полосы (§5) пишет `RouteStep` прямо в арену.

Сложность: O((V + E) log V) в худшем случае; на s1k (≈ 1 700 вершин, ≈ 5 000 дуг) полный поиск
≈ 300–800 раскрытий ≈ 20–60 мкс; локальный ≤ 512 раскрытий. Память: 16 B/вершина + 8 B/запись кучи
(s1m: ≈ 660 k вершин → ≈ 11 MB + 24 MB).

## 3. Фаза 3: очередь и бюджет

Маршрут строится **до спавна**: `PendingTrip` получает поля `Route, RouteGen, DestLane, DestS`
(`core-api.md` §6.6). Фаза 2 ставит на дорогу только поездки с `Route != -1` (голова FIFO без
маршрута ждёт, порядок сохраняется). Поэтому машины с `Route == -1` на дороге появляются лишь после
промаха полосы (§6.3) и в этот момент **едут**, а не стоят.

Фаза 3 (`Routing/RoutePhase.cs`) каждый тик:

1. `ExpansionsThisTick = 0`, `Served = 0`.
2. **Перемаршрутизация** (кольцо `RerouteQueue[MaxVehicles]`, FIFO; машина кладётся в фазе 7 при
   промахе): пока очередь не пуста и `Served < PathfindBudgetPerTick` и `ExpansionsThisTick < ExpansionBudget`:
   `Build(StartLane = Lane[i], StartS = S[i], DestLane[i], DestS[i], FromZone = -1, ToZone = DestZone[i])`.
   Неуспех → машина остаётся без маршрута, едет по умолчанию, повторная заявка через `RerouteRetryTicks = 100`
   (хранится как `WaitTicks`-подобный счётчик в самой очереди: запись возвращается в хвост с меткой тика).
3. **Поездки**: обход `PendingTrips` от головы, не более `PathfindBudgetPerTick − Served` поездок без маршрута
   (по порядку очереди; поездки с маршрутом пропускаются без затрат). `Build(FromLane, FromS, DestLane, DestS, FromZone, ToZone)`.
   `RouteFailed` (нет пути) → поездка удаляется из очереди, `TripsDropped++`, `RouteFailed++`.
   Дефицит бюджета → `RouteDeferred++` за каждую необслуженную поездку с маршрутом `-1` в этом тике
   (одно значение на тик — считать как число ждущих, не суммировать по машинам в цикле).
4. Компактификация арены — только из `Build` при нехватке места (§4.3).

`ExpansionBudget = 256 · PathfindBudgetPerTick` раскрытий на тик (s1k: 8 192 ≈ 0.4 мс в худшем случае —
отказы по бюджету ждут следующего тика, это не ошибка). Проверяется **между** поисками; один поиск
не прерывается (иначе бессмысленно раскрытое тратится зря).

Ожидаемая нагрузка s1k: ≈ 1 000 машин / средняя поездка ≈ 6 мин ⇒ ≈ 3 спавна/с ⇒ 0.15 запроса/тик;
бюджет 32 нужен только на разгоне (`spawn_ramp`), где `PendingTrips` заполняется заранее.

## 4. Кэш по парам зон и сборка маршрута (удалено в H3 — заменено §9, итоги в §15)

### 4.1 Хаб зоны и магистраль

У каждой зоны `ZoneData.HubNode` — узел с воротами (или любой при их отсутствии), ближайший к центру
зоны (`ZoneGenerator` этап 2.2; при `city.enabled = false` — ближайший узел сети). **Магистраль**
`Trunk(A, B)` — путь `DirSeg[0..k]` от `HubNode(A)` до `HubNode(B)`: многоисточниковый старт (все `u` с
`StartNode(u) == HubNode(A)`, `G = SegCost(u)`), цель — любая `w` с `EndNode(w) == HubNode(B)`
(при `h` — расстояние до `HubNode(B)`). `HubNode(A) == HubNode(B)` → магистраль пуста, маршрут
строится прямым поиском.

Кэш — `FixedHashMap` открытой адресации (линейное пробирование, вместимость `2·MaxRoutes`, ключ
`from·MaxZones + to`, значение — индекс маршрута; удаление — backward-shift, без tombstone).
Запись `RoutePool`: `FromZone/ToZone` = ключ, `RefCount = 0` (магистраль никем не используется напрямую —
её **копируют**), `LastUsedTick` (новое поле), `NetworkVersion`.

### 4.2 `Build(start, dest, fromZone, toZone)` → `RouteHandle`

```
1. if fromZone >= 0 && toZone >= 0:
       t = Cache.Lookup(fromZone, toZone)
       if t != -1 && Pool.NetworkVersion[t] != Network.Version: Cache.Remove; Pool.Free(t); t = -1   // ленивая инвалидация
       if t == -1:
           Trunk search (полный A*, учитывается в бюджете раскрытий); при успехе — вставить в кэш (вытеснение §4.3);
           при отказе по бюджету → вернуть Deferred; при «нет пути» → перейти к прямому поиску (п. 3).
       else PathfindCacheHits++
       Pool.LastUsedTick[t] = Tick
   PathfindQueries++
2. if trunk:
       prefix = A*(start DirSeg → Trunk[0]) с LocalExpansionCap        // обычно ≤ 50 раскрытий: зона 500 м
       suffix = A*(Trunk[k] → dest DirSeg) с LocalExpansionCap
       если любой из них упёрся в cap или не нашёл пути → п. 3
       dirsegs = prefix ++ Trunk[1..k] ++ suffix[1..]                  // стыки без дублей
3. else: dirsegs = A*(start → dest) (полный)
4. LayoutLanes(dirsegs, startLane, destLane) → RouteStep[] в арену (§5); RefCount = 1; FromZone = ToZone = -1
```

Маршрут через хаб может быть длиннее прямого на ≤ ~2 стороны зоны; принято (цена кэша). Стартовая
полоса `StartLane` — та, где машина (или где появится); если её `DirSeg` уже лежит на магистрали,
префикс вырождается в один элемент.

### 4.3 Вместимость, вытеснение, компактификация

- Таблица/пул полны при вставке магистрали: среди 8 слотов пробного окна от хэша ключа выбирается
  магистраль (`RefCount == 0`, `FromZone ≥ 0`) с минимальным `LastUsedTick` → удаляется (O(1),
  детерминированно). Если окно без магистралей — маршрут не кэшируется (`RouteCacheSkips++`),
  машина всё равно получает индивидуальный маршрут.
- Пул `MaxRoutes` полон при выделении индивидуального маршрута → та же процедура вытеснения
  магистрали; если ни одной (все слоты — живые машины) → `Deferred`.
- Арена `Steps`: bump-аллокация; `Free` помечает слот мёртвым (`Count` сохраняется для прохода);
  при нехватке хвоста — компактификация: обход слотов пула по возрастанию индекса, живые
  переносятся вплотную (`First` обновляется; машины держат handle, не указатель, поэтому ничего не
  ломается), `RouteCompactions++`. O(StepsUsed) ≤ 262 k × 8 B для s1k ≈ 0.1 мс — редкий всплеск.
  Если и после компактификации места нет → `Deferred`.
- Размер: `max_routes ≥ max_vehicles + число используемых пар зон`; для s1k (64 зоны, `min_trip` 600 м
  ⇒ ≈ 3 000 пар + 1 280 машин) — **8 192** (правка примера в `scenario-format.md`); `max_route_steps`
  262 144 достаточно (магистраль ≈ 30 шагов, индивидуальный ≈ 50). На лестнице s10k+ пар больше, чем
  слотов, — кэш работает как LRU, промахи считаются в бюджет.
- `BuildRoad`: `Network.Version++`; магистрали инвалидируются лениво (п. 1), индивидуальные маршруты
  остаются валидными (сеть только растёт, индексы полос стабильны). Это снимает вопрос 2 из
  `core-api.md` §15.

## 5. Раскладка на полосы (`LayoutLanes`)

Вход: `DirSeg D[0..k]`, `StartLane` (на `D[0]`), `DestLane` (на `D[k]`). Выход: `RouteStep`
`[L0, C0, L1, C1, …, L_k]` (`2k + 1` шагов), где `L_j` — **целевая полоса** на `D[j]` (та, с которой
нужно уйти с сегмента), `C_j` — connector `L_j → ToLane(C_j) ∈ lanes(D[j+1])`.

Обратный проход, `L_k = DestLane`:

```
for j = k-1 .. 0:
    кандидаты = connector'ы из lanes(D[j]) в lanes(D[j+1])
    выбрать C_j с минимумом (|LaneNo(ToLane) − LaneNo(L_{j+1})|, индекс connector'а)   // меньше перестроений на D[j+1], детерминированно
    если |LaneNo(ToLane) − LaneNo(L_{j+1})| · LaneChangeDistance > Length(D[j+1]) и есть connector точно в L_{j+1} → взять его
    L_j = FromLane(C_j)
```

`LaneChangeDistance = 60 м` на одно перестроение (оценка для города). `RouteStep.Node`: для `L_j` —
`EndNode(D[j])`, для `C_j` — узел connector'а, для `L_k` — `-1`. Если `L_0 != StartLane`, машина
перестраивается на `D[0]`; спавнер выбирает `FromS ≤ Length − 60·|ΔLaneNo| − NoLaneChangeZone`, когда
может (иначе машина промахнётся и перепланируется — не ошибка).

## 6. Движение по маршруту

### 6.1 Курсор

`RouteCursor` указывает на шаг текущей полосы; на `Normal`-полосе `Steps[Cursor]` — шаг сегмента (целевая
полоса; `Lane[i]` может отличаться, пока машина не перестроилась), на connector'е — шаг connector'а.
`TargetLane(i) = Steps[Cursor].Lane` на `Normal`-полосе; при `Route == -1` — текущая полоса.

### 6.2 `NextConnector(i)` (O(NextCount) ≤ 4, вызывается воротами и фазой 7)

```
if Route == -1 or Cursor+1 >= Count: return LaneNext[FirstNext(Lane)]      // прямо по умолчанию; на последнем шаге не используется (прибытие раньше)
c = Steps[Cursor+1].Lane
if FromLane(c) == Lane: return c                                             // на целевой полосе
nextSeg = Segment(Steps[Cursor+2].Lane)
среди LaneNext(Lane): connector с Segment(ToLane) == nextSeg → вернуть (первый по порядку LaneNext)   // тот же сегмент, другая полоса
return LaneNext[FirstNext(Lane)]  с флагом Missed                           // промах
```

### 6.3 Фаза 7

- Переход `Normal → connector c`: если `c == Steps[Cursor+1].Lane` → `Cursor++`; иначе если `c` ведёт
  в `Segment(Steps[Cursor+2].Lane)` → `Cursor++` (маршрут продолжается, на следующем сегменте
  `Lane != TargetLane`, MOBIL доведёт); иначе (**промах**): `RefCount--`/`Free` маршрута, `Route = -1`,
  положить `i` в `RerouteQueue`, `Reroutes++`. `DestLane/DestS/DestZone` сохраняются.
- Переход `connector → Normal`: `Cursor++` если `Route != -1`.
- Прибытие (фаза 8): `Lane == DestLane && S ≥ DestS` → как в `core-api.md`. Машина без маршрута
  прибывает, если случайно оказалась на `DestLane`.

### 6.4 MOBIL: подготовка к повороту (контракт для `Rules/Mobil.cs`)

`d = Length − S` на текущей полосе, `Δ = LaneNo(TargetLane) − LaneNo(Lane)` (знак → направление),
срочность `u = clamp((D_prep − d) / (D_prep − NoLaneChangeZone), 0, 1)`, `D_prep = 150 м`,
`NoLaneChangeZone = 30 м` (`intersections.md` §7.1).

- К стимулу MOBIL в сторону цели прибавляется `+u·A_route`, в противоположную — `−u·A_route`,
  `A_route = 1.0 м/с²` (при `u = 0` — обычный MOBIL с `RightBias`).
- Критерий безопасности смягчается: `b_safe_eff = b_safe + 2·u` (до 6 м/с²).
- При `u > 0.5` MOBIL оценивается каждый тик (а не раз в `MobilEveryTicks`).
- При `u ≥ 0.8` и `Δ != 0` желаемая скорость ограничивается `v0_eff = max(3 м/с, v0·(1 − u))` — машина
  замедляется, чтобы найти зазор («вежливый поиск окна»); следующий сзади подстраивается IDM.
- В зоне `d < NoLaneChangeZone` смена запрещена; дальше работает §6.2/§6.3 (промах → перепланирование).
  Машина никогда не ждёт перестроения стоя — отсюда отсутствие тупиков по этой причине.

### 6.4.1 Промахи полосы на s10k: диагноз и бэклог (агент #91, 2026-10-25)

`lane_miss_share` (= `Reroutes` / завершённые поездки) на s10k: **0.32** (окно 12 000 тиков после 6 000 прогрева, seed по умолчанию),
0.34 / 0.33 / 0.34 на seed 11 / 12 / 13; s1k — 0.146. Диагностика — временные счётчики в копии (не в коммите), s10k, то же окно:

- Все промахи — на переходе «обычная полоса → connector» (`RouteNav.Advance`), машина **едет** (скорость < 1 м/с у 1 из 2 855), нужна **соседняя** полоса
  (|ΔLaneNo| = 1 у 2 852 из 2 855). Окна маршрута не причина: `RefillLate = 0`, 90% промахов — при возрасте маршрута > 15 с, то есть нужная
  полоса известна задолго до конца сегмента. Узлы/типы узлов не дифференцировали: промах — следствие невыполненной смены на длине сегмента.
- Потребность в смене впервые видна на остатке 120–200 м (2 697 из 2 855), т. е. сразу при въезде на сегмент 150–250 м; у 1 527 промахов
  ≥ 9 оценок MOBIL подряд (раз в 10 тиков) и ни одной подходящей. Вынужденных оценок 352 тыс., из них успешных 21.5 тыс. (6%).
  Причины отказа (доли оценок): `LaneEntryClearance` 25 м от начала полосы — 68% (структурно, на сегменте 150–250 м съедает 10–15% длины),
  зазор спереди на целевой полосе < `MinPhysicalGap` — 10%, торможение нового лидера/ведомого > `SafeDecel` — 5% + 5%, зазор сзади — 5%.
  Т. е. в плотном потоке на соседней полосе нет «дыры» длиной L + 2·0.5 м, а машина её не ищет: контракт §6.4 (срочность `u`,
  `b_safe_eff = b_safe + 2u`, оценка каждый тик при `u > 0.5`, «вежливый поиск окна» `v0_eff`) в `Mobil.Decide`/`BehaviourPhase` **не реализован**.
- Перемаршрутизации по времени (`TimedReroutes` ≈ 8.7 тыс. на 8.9 тыс. поездок) тут не виноваты: 20% промахов после них, остальные — после
  спавна и после предыдущего промаха (51% промахов — повторные: после промаха новый маршрут строится с середины сегмента на той же неудачной полосе).

Эксперименты (все на ядре без изменения схемы; сейвы/голдены перегенерировались бы, код откатан):

| Вариант | lane_miss_share s10k (12k тиков) | still ≥ 60 с (эпизоды) | вывод |
|---|---|---|---|
| база | 0.322 | 32 (seed 11/12/13: 25/29/102) | — |
| оценка каждый тик при остатке < 90 м + `SafeDecel + 2u` | 0.284 | 59 | почти без эффекта |
| + `v0_eff = max(3, v0·(1−u))` при `u ≥ 0.5` | 0.121 | 130 (15 эпизодов ≥ 120 с), completed −2% | отклонён: колонны за замедлившейся |
| + `v0_eff = max(5, v0·(1−0.5u))` | 0.223 (seed 11/12/13: 0.221/0.216/0.237) | 59 (26/33/27); при 30 000 тиков 777 против 601 базы, stuck на конец окна 37 против 14 | отклонён: рост ожиданий ≥ 60 с на длинном окне |
| + `v0_eff = max(7, v0·(1−0.3u))` | 0.252 | 794 против 601 на 30 000 тиков | отклонён |

Вывод: дешёвый локальный фикс (срочность + поиск окна) снижает долю на 30–60%, но поднимает ожидания ≥ 60 с (порог 0.15% на s10k на длинном
окне и так превышен базой: 601 эпизод ≈ 1.8%), поэтому код не менялся. s1k: 0.146 → 0.103 при том же stuck = 0 — на малой плотности помогает.

**Бэклог (по убыванию отдачи):**
1. Выбор полосы на въезде на сегмент с учётом следующего манёвра (посадка в нужную полосу на длинной части connector'а/в начале полосы, пока
   дыры есть; `LaneEntryClearance` для ведомого по connector'у снять или заменить проверкой списков предыдущей полосы), вместо ожидания
   оценок MOBIL на 25+ м.
2. Повторные промахи (51%): после промаха строить маршрут от текущей полосы с запретом/штрафом за немедленную потребность в смене (учёт «вынужденной»
   полосы в `Build`) либо выбирать connector, ведущий к цели, даже если он не по маршруту (запасной выход), вместо полного перепланирования.
3. Если вернуться к §6.4: поиск окна замедлением нужен только для машин, у которых соседняя полоса идёт быстрее (иначе колонна за ними), и должен
   сопровождаться проверкой ожиданий ≥ 60 с на окне ≥ 30 000 тиков, а не 12 000.

## 9. Иерархическая маршрутизация (этап 2, ADR-0009)

Заменяет кэш магистралей (§4.1–4.3), `RoutePool`-арену (§4.3, core-api §6.5) и полный поиск при перемаршрутизации. Остаются:
граф DirSeg и веса (§1, ADR-0006), A* с эвристикой `|Δpos| / VMax · 0.95` (§2), раскладка на полосы (§5), навигация (§6) —
она читает окно маршрута так же, как раньше `RouteStep`. Совместимость с этапом 1 не держим (ADR-0009, решение владельца).

### 9.0 Решения коротко

| Вопрос | Решение |
|--------|---------|
| Иерархия | многоуровневый оверлей ячеек (CRP): уровень 1 — квадраты `cell_m`, уровень ℓ+1 — `fanout × fanout` ячеек уровня ℓ; `levels` = 1..4 |
| Граничная вершина | DirSeg, начало и конец которого в разных ячейках уровня ℓ (`CutLevel(u) ≥ ℓ`) |
| Дуги оверлея | плотная матрица ячейки `вход × выход`: стоимость кратчайшего пути **внутри** ячейки |
| Веса загрузки | волна кастомизации «грязных» ячеек после `RecalcCosts`, размазана по тикам бюджетом работы |
| Запрос | однонаправленный A* по многоуровневому графу (правило уровня §9.4), индексная 4-арная куча; точный кратчайший |
| Хранение | план (стек граничных DirSeg с уровнем, ≈ 15–35 × 4 B) + окно ≤ `window_steps` полосовых шагов в фиксированном слоте |
| Развёртывание | лениво: дуга уровня q → поиск уровня q−1 внутри одной ячейки; дозаполнение окна заранее из очереди фазы 3 |
| Перемаршрутизация по времени | только при дрейфе остатка стоимости плана > `timed_drift` |
| Бюджет | единицы работы = релаксации (дуга / элемент матрицы); отдельные бюджеты запросов и кастомизации |
| `levels = 0` | тестовый эталон: одна ячейка на весь граф = плоский A*; в сценариях лестницы не используется |

### 9.1 Ячейки и граничные вершины

- Сетка уровня 1 строится в `Create` по bounding box узлов: `Nx1 = max(1, ceil(W / cell_m))`, `Nz1` аналогично, начало — min-угол.
  Узел → `(cx, cz) = clamp(floor((pos − origin) / cell_m), 0, N − 1)`. Узлы `BuildRoad` вне коробки зажимаются в крайние
  ячейки: корректность не зависит от геометрии ячеек, только от принадлежности.
- Уровень ℓ: `(cx, cz) / fanout^(ℓ−1)` (целочисленно), `Nxℓ = ceil(Nx1 / fanout^(ℓ−1))`. Вложенность гарантирована делением.
  Глобальный id ячейки `gc = CellBase[ℓ] + cz·Nxℓ + cx`; `CellBase[1] = 0`, далее по уровням подряд.
- `CutLevel(u)` (byte) = max ℓ, при котором `cell_ℓ(StartNode u) ≠ cell_ℓ(EndNode u)`, иначе 0. Направление без полос — 0.
- Ячейка C уровня ℓ: **входы** — `u` с `CutLevel(u) ≥ ℓ` и `EndNode(u) ∈ C`; **выходы** — `CutLevel(u) ≥ ℓ` и `StartNode(u) ∈ C`.
  Каждая граничная вершина — выход одной ячейки и вход соседней. Порядок входов/выходов в ячейке — по возрастанию DirSeg (в `Create`),
  новые от `BuildRoad` дописываются в конец (индексы старых стабильны).
- Стоимость дуги `e → x` ячейки C: кратчайший путь от «стоим в `EndNode(e)`» до конца `x` через вершины, **внутренние** для C
  (оба конца в C на уровне ℓ), с весами §1.1: `Σ (ArcCost + SegCost)` по пути, `SegCost(e)` не входит, `SegCost(x)` входит.
  Нет пути — `+∞`. Прямой поворот `e → x` в узле на границе — путь из одной дуги.

### 9.2 Структуры данных (`Routing/Overlay.cs`, плоские массивы, без ссылок между объектами)

```csharp
internal sealed class Overlay                     // всё выделяется в Create по ёмкостям; в Step и BuildRoad не аллоцирует
{
    public int Levels, Fanout; public float CellSize; public Vec2 Origin;
    public readonly int[]   LevelNx, LevelNz, CellBase;            // [Levels + 2]
    public readonly int[]   NodeCellX, NodeCellZ;                 // [MaxNodes]  ячейка уровня 1
    public readonly byte[]  CutLevel;                             // [DirSegCap]
    // ячейки всех уровней подряд, индекс gc
    public readonly int[]   EntryFirst, EntryCount, EntryCap;     // [CellCap] диапазон в Entries
    public readonly int[]   ExitFirst,  ExitCount,  ExitCap;      // [CellCap] диапазон в Exits
    public readonly int[]   MatrixFirst;                          // [CellCap] строка r, столбец c → Matrix[MatrixFirst + r·ExitCap + c]
    public readonly byte[]  Dirty;                                // [CellCap] 0/1: ждёт кастомизации
    public readonly int[]   Entries, Exits;                       // [BoundaryCap] DirSeg
    public readonly float[] Matrix;                               // [MatrixCap]   с, +∞ = нет пути
    public readonly int[]   EntryIdx, ExitIdx;                    // [Levels · DirSegCap] локальный индекс u в ячейке уровня ℓ или −1
    public readonly float[] CustomizedSegCost;                    // [DirSegCap] SegCost, по которому считана ячейка (порог грязи)
    public int WeightsVersion;                                    // как RouteGraph.WeightsVersion
}
```

- `EntryCap = Overlay.CapFor(EntryCount)` (так же выходы) — **канонический** запас под `BuildRoad` (save-format.md §13 п. 5): наименьшая ступенька лестницы
  4, 8, 12, 16, 20, …, 32, 40, …, 64, 80, … не меньшая `EntryCount + 4` (запас ≥ 4 строк, не больше `4 + max(4, count / 4)`); зависит только от числа
  входов/выходов, не от истории: раскладка живого мира после `BuildRoad` равна раскладке, построенной заново по той же сети. Новые строки/столбцы = `+∞` до
  кастомизации. `BoundaryCap`, `MatrixCap`, `CellCap` — из начальной сети × запас, считаются в `Create` (не из JSON).
- Индексы — `int` (порт на Rust: `u32`/`i32`, никаких указателей); `CutLevel`, `Dirty` — `u8`.
- План кодируется `int`: `DirSeg | (level << 28)` (DirSeg < 2²⁸ — проверка в `Create`).

### 9.3 Кастомизация

**Строка матрицы** `(C, e)` = один поиск Дейкстры (A* без цели, h = 0) из `e` с `G = 0`:
- уровень 1: по графу DirSeg, допускаются вершины, внутренние для C; выход C достигнут → записать `G`, дальше не раскрывать;
- уровень ℓ ≥ 2: вершина `v` (вход подъячейки `S = cell_{ℓ−1}(EndNode v)`), дуги — строка `v` матрицы S ко всем выходам `x` S;
  `x` — выход C (`CutLevel(x) ≥ ℓ`) → записать, иначе `x` — вход соседней подъячейки внутри C → продолжить.
- Ничьи — по меньшему DirSeg, сумма в фиксированном порядке; `+∞` для недостигнутых выходов.

**`Create`**: полная кастомизация всех ячеек по уровням снизу вверх (s1m — секунды, это время создания, не тика).

**Волна после пересчёта весов** (ADR-0006, раз в `cost_recalc_s`, по номеру тика):
1. `RecalcCosts` обновляет `SegCost` целиком (O(сегментов)). Сегмент, у которого `|SegCost − CustomizedSegCost| > customize_eps ·
   CustomizedSegCost` (дефолт 0.05), помечает `Dirty` ячейку уровня 1 обоих концов; предки грязных ячеек — тоже грязные.
2. Список заданий — грязные ячейки по `(уровень ↑, gc ↑)`, задание — одна строка. Курсор волны `(ℓ, gc, row)` живёт в `Overlay`.
3. Каждый тик в конце фазы 3 выполняются строки, пока работа волны < `customize_budget_per_tick` (проверка **между** строками).
   Ячейка закончена → `Dirty = 0`, `CustomizedSegCost` её внутренних вершин обновлён. Уровень ℓ+1 начинается только после ℓ.
4. Новый пересчёт весов при незаконченной волне откладывается до её конца (`CustomizeLagTicks += 1` за каждый тик ожидания).
Пока волна идёт, запросы видят смесь старых и новых матриц: пути остаются корректными (топология та же), лишь не строго оптимальными.

**`BuildRoad`** (core-api §4.2: сеть только растёт, новые сегменты — к новым/изолированным узлам): `RouteGraph.Rebuild`
(как сейчас), затем для новых узлов — ячейки, для новых DirSeg — `CutLevel`, новые входы/выходы дописываются в свои ячейки
всех уровней в пределах `Cap` (строки/столбцы `+∞`), ячейки с новыми вершинами и их предки → `Dirty`, задания этих ячеек
ставятся **в начало** текущей волны (или начинают волну). Не хватило `Cap`/`BoundaryCap`/`MatrixCap` → синхронная полная
перестройка оверлея (раскладка с новым запасом в тех же массивах + полная кастомизация, `OverlayRebuilds++`); не влезло и так →
оверлей выключается (`Levels` трактуется как 0, все запросы — плоский A*, `OverlayDisabled = 1`), команда не отклоняется.
Живые планы остаются валидны: хранят DirSeg, а не индексы матриц, старые пути не исчезают.

### 9.4 Запрос `Query(startLane, startS, destLane, destS)`

- `u0 = DirSeg(startLane)`, `g = DirSeg(destLane)`; `G(u0) = SegCost(u0)·(1 − startS/Length)` (как §4.2); `u0 == g` — как сейчас.
- Узлы привязки: `s = EndNode(u0)` (откуда машина продолжит), `t = StartNode(g)` (откуда въедет в цель). `sCell[ℓ]`, `tCell[ℓ]` — заранее.
- **Уровень вершины** `q(v)` = max ℓ ∈ [1..Levels], при котором `cell_ℓ(EndNode v) ∉ {sCell[ℓ], tCell[ℓ]}`, иначе 0
  (сверху вниз, O(Levels)). Раскрытие `v`:
  - `q = 0`: дуги графа DirSeg `v → w` (§1), как плоский A*;
  - `q ≥ 1`: `r = EntryIdx[q][v]`; для каждого выхода `x` ячейки `cell_q(EndNode v)`: `cost = Matrix[row r][ExitIdx[q][x]]`, `+∞` пропуск.
    `r == −1` (не должно случаться по построению, проверка) → раскрыть как `q = 0` (медленнее, но корректно).
- Цель — извлечение `g` из кучи. Эвристика `h(v) = |EndPos[v] − EndPos[g]| / VMax · 0.95` монотонна и на матричных дугах
  (дуга = сумма монотонных дуг). Ничьи — `(f, DirSeg)` лексикографически.
- Состояние поиска (`OverlaySearcher`): `G`, `Parent`, `ParentLevel` (byte), `Seen/Closed`-штампы `[DirSegCap]`, индексная 4-арная
  куча с decrease-key: `HeapPos[DirSegCap]`, `HeapKey/HeapVal[DirSegCap]` — переполнение невозможно, дубликатов нет.
- Результат: путь `[u0, …, g]` по `Parent` с уровнем дуги входа в каждую вершину → **план** (§9.5); `PlanCost = G(g)`.
  Единицы работы: +1 за каждую релаксацию (дуга или элемент матрицы). Предел работы одного запроса — `query_work_cap`
  (дефолт `4 · DirSegCount`) → отказ `NoPath` (не бывает при связной сети).
- **Развёртывание дуги** `a → b` уровня `q` (`unpack`): тот же поиск, ограниченный ячейкой `C = cell_q(EndNode a)` и уровнем `q − 1`
  (как строка кастомизации §9.3, но A* к цели `b`). Даёт `a, v1, …, b` с уровнем `q − 1` у каждой дуги. Пусто/не нашли → промах (§9.7).

### 9.5 Хранение: `RouteStore` (план + окно), вместо `RoutePool`

```csharp
internal sealed class RouteStore
{
    public readonly HandlePool Pool;                 // max_routes: машины + поездки с построенным маршрутом
    public readonly RouteStep[] Window;              // [max_routes · WindowSteps]; окно слота r: Window[r·W .. r·W + WinCount[r])
    public readonly byte[]  WinCount;                // ≤ WindowSteps (дефолт 16 → ≤ 8 DirSeg: 2k+1 ≤ 15)
    public readonly int[]   PlanFirst, PlanCount, PlanCap;  // стек плана в PlanArena; вершина стека = следующий элемент
    public readonly int[]   PlanArena;               // [max_plan_steps], bump + компактификация по First (как §13)
    public readonly float[] PlanCost;                // стоимость при построении, с
    public readonly long[]  PlanTick;                // тик построения
    public int PlanUsed;
}
```

- План — путь запроса **без** первых DirSeg, уже положенных в окно, в обратном порядке (стек): элемент `(v, q)` = «из конца окна
  перейти в `v` дугой уровня `q`». `PlanCap = PlanCount + 8·Levels` (запас под развёртывание); не хватает → блок переезжает в хвост
  арены (старый мёртв); нет места после компактификации → `Deferred`.
- **Материализация** следующего DirSeg: вершина стека `(v, q)`; `q = 0` → снять, `v` в буфер DirSeg; `q ≥ 1` → снять, `unpack(tail, v, q)`,
  положить результат в стек в обратном порядке, повторить. Глубина ≤ `Levels`, одно развёртывание ≤ `unpack_cap = 64` элементов
  (больше → промах).
- **Окно** = `LayoutLanes` (§5) по DirSeg `[текущий, …, до 8]`: `destLane` = `DestLane`, если план пуст, иначе `LaneNo 0` последнего DirSeg
  (уточнится при дозаполнении). Слот фиксирован → компактификации окон нет; `First` = `r·W`.
- **Дозаполнение** (`Refill`): при `Advance` (фаза 7) машина с непустым планом и ≤ `refill_ahead = 3` DirSeg впереди в окне ставится
  в `RefillQueue` (кольцо `[MaxVehicles]`, флаг `VehicleFlags.RefillQueued` против дублей). Фаза 3 следующего тика: шаги
  `[0..Cursor+1]` (текущая полоса и выбранный connector; на connector'е — он сам) сохраняются со сдвигом в начало, остальное
  перекладывается от `ToLane` этого connector'а по DirSeg «оставшиеся + новые из плана»; `RouteCursor` сдвигается на то же число,
  `NextConn` не меняется (воротам ничего не ломаем). Машина дошла до конца непустого окна без дозаполнения → промах,
  `RefillLate++` (должно быть 0).
- `RouteView` (core-api §5.5) отдаёт окно (`Steps` = окно, `Cursor`) — лента в клиенте ≤ 8 сегментов вперёд.
- `PendingTrip` хранит handle слота: план + первое окно строятся в фазе 3, спавн (фаза 2) — только поездки с маршрутом (как §3).
- Автобусы (`BusDispatch`, `BusStopPhase`) — тот же `Query`; маршрут от остановки к остановке обычно целиком помещается в окно.

### 9.6 Фаза 3: порядок и бюджеты

1. Дозаполнение окон из `RefillQueue` (по порядку очереди, **все** — оно нужно машинам на дороге; работа считается в метрике, но не
   ограничивается).
2. Промахи (`RerouteQueue`, kind = Miss), затем плановые по дрейфу (kind = Timed, доля `1/4`, как сейчас), затем `PendingTrips` —
   пока работа запросов < `work_budget_per_tick` и число запросов < `pathfind_budget_per_tick` (проверка между запросами;
   запрос не прерывается).
3. Пересчёт весов по номеру тика (`tick % CostRecalcTicks == 0` и нет активной волны) → старт волны.
4. Волна кастомизации в пределах `customize_budget_per_tick`.

Параллельный счёт запросов шага 2 на воркерах (пакет + последовательный повтор этого же порядка, хэш прежний): `routing-parallel.md`, ADR-0032.

### 9.7 Перемаршрутизация

- **Промах** (§6.3) и неудачное развёртывание: слот освобождается, машина в `RerouteQueue` → `Query` от текущей полосы (§14).
- **По времени** (ADR-0006, раз в 60 с, разнесено по индексу как сейчас): `RemainingCost` = Σ по окну от курсора (`SegCost + ArcCost`)
  + Σ по стеку плана (`q = 0`: `SegCost + ArcCost`; `q ≥ 1`: элемент матрицы, O(1)). Ожидаемый остаток
  `E = max(PlanCost − (Tick − PlanTick)·dt, 0)`. Запрос ставится, только если `RemainingCost > E·(1 + timed_drift) + timed_drift_abs_s`
  (дефолт 0.15 и 20 с). Новый план принимается, если дешевле `RemainingCost` хотя бы на `TimedGain` (10%); иначе слот нового
  освобождается. Проверка — O(окно + план) ≈ 50 операций, без поиска.

### 9.8 Детерминизм, хэш, 0 B/тик

- PRNG не используется. Порядок: очереди (Refill → Reroute → Trips), волна по `(ℓ, gc, row)`, ничьи по DirSeg, суммы скалярно
  в фиксированном порядке (без FMA/SIMD, core-api §9). Пересчёт весов — по номеру тика.
- Хэш (core-api §9, п. 8) дополняется: `RefillQueue` (индексы в порядке очереди), курсор волны `(ℓ, gc, row)`, `Overlay.WeightsVersion`,
  для живых слотов `RouteStore`: `WinCount`, `PlanCount`, `PlanCost`. Матрицы не хэшируются (производные от весов и курсора волны).
- Все массивы — в `Create` по ёмкостям; `Step`, волна, развёртывание, `BuildRoad` и полная перестройка оверлея не аллоцируют.
  Тест 0 B/тик (`AllocationProbe`) — с активной волной и дозаполнениями.

## 13. Уточнения по факту реализации R1-R3 (`Routing/`, фазы не подключены)

- Класс графа - `RouteGraph` (`Routing/RoutingGraph.cs`), A* - `AStarSearcher` (`AStar.cs`), кэш - `RouteCache`, сборка -
  `RouteBuilder` (`Build`, `LayoutLanes`). API `internal`, принимает `NetworkStore`/`RoutePool`/ёмкости, без `World`.
  Граф пересобирается автоматически в `Build`, если `Network.Version` != `BuiltVersion`.
- Вес дуги включает **время проезда connector'а** (`Length/min(SpeedLimit)`) - иначе эвристика неадмиссибельна
  (длина сегмента меряется между отступами от узлов). Эвристика дополнительно умножена на 0.95 (константа масштаба,
  монотонность сохраняется). Штраф `Signal` пока константа (план по умолчанию 56/24 = 9.1 с): планы светофоров в
  `NetworkStore` не хранятся, `SetSignalPlan` подключается вместе с фазами.
- Стоимость цели считается как полный `SegCost(goal)` (частичный `DestS/Length` не учитывается - не влияет на корректность).
  Старт и цель на одном `DirSeg` при `StartS > DestS` - `NoPath` (объезд круга не строится).
- Шаги магистрали в `RoutePool` хранят **DirSeg в поле `RouteStep.Lane`** (не полосу), `Node` = конечный узел.
- Компактификация арены идёт в порядке **расположения в арене** (сортировка по `First` во вспомогательных буферах пула),
  а не по индексу слота: перенос по индексу затёр бы ещё не перенесённые данные.
- Раскладка: при ничьей по `|ΔLaneNo|` на первом сегменте предпочтителен connector с входной полосы, ближайшей к стартовой.
  Отдельное правило `LaneChangeDistance` не нужно: минимум `|ΔLaneNo|` уже выбирает connector точно в целевую полосу, если он есть.
- Бюджет раскрытий: `ExpansionBudget = 256 * PathfindBudgetPerTick` (0 = без ограничения), `BeginTick()` сбрасывает счётчик,
  при исчерпании `Build` возвращает `Deferred`. Использованы существующие `MaxRoutes/MaxRouteSteps/PathfindBudgetPerTick`;
  `MaxZones` берётся из `SimCapacities`.
- Измерения (Release, BenchmarkDotNet short): A* случайная пара - s1k ~32 мкс (~310-380 раскрытий), s100k ~1.35 мс (~9 100 раскрытий);
  сборка маршрута с попаданием в кэш ~2 мкс. Для s100k нужна иерархия (раздел 9).

## 14. Уточнения по факту подключения R4/R5 (фаза 3 в `PhaseList`, спавн, движение по маршруту)

- **Фаза 3** - `Routing/RoutePhase.cs`; `World.Router` (`RouteBuilder`) и `World.Rerouting` (`RingBuffer<RerouteEntry>`, ёмкость `MaxVehicles`,
  запись = индекс + поколение + `ReadyTick`; мёртвые записи отбрасываются при просмотре, хэш содержит очередь). Бюджет `PathfindBudgetPerTick = 0`
  читается как «без ограничения запросов» (бюджет раскрытий `RouteBuilder` тогда тоже 0). Перемаршрутизация идёт раньше поездок; неудача
  (`NoPath`) возвращает запись в хвост с `ReadyTick = tick + RerouteRetryTicks (100)`; `Deferred` оставляет голову на месте и прекращает фазу.
  Счётчики построителя (`Queries/CacheHits/ExpandedNodes/Failed/Compactions/CacheSkips`) копируются в `SimCounters` в конце фазы;
  `RouteDeferred` = сумма по тикам числа поездок без маршрута, оставшихся из-за бюджета (тик-ожидания, а не число отложенных поездок).
- **`PendingTrip`**: `RouteGen != 0` означает «маршрут построен» (поколение живого слота нечётно и > 0, поэтому `default` = «нет маршрута»).
  `PendingTrips` ведёт счётчик `Unrouted`, чтобы фаза 3 не обходила очередь, когда в ней всё уже с маршрутом; нет пути - `RemoveAt` из
  середины очереди (`RingBuffer.RemoveAt`), `TripsDropped++`, `RouteFailed++`. Зона назначения без полос (явная сеть без `ZoneLanes`)
  точку прибытия не получает - поездка ждёт в очереди без затрат бюджета (как зона без полос спавна).
- **Точка прибытия** - `Routing/Destinations.cs`: случайная полоса спавна зоны (стрим `Spawn` при генерации; поездки из команд получают её в
  фазе 3 из стрима `Routing`), `DestLane` = `LaneNo 0` встречного направления того же сегмента, `DestS = 0.6 * Length` (с запасом на
  `LaneEntryClearance` и перестроение; у конца полосы прибытие не ловится в очереди на узел).
- **Спавнер** ставит машину только на полосу с тем же направленным сегментом, что и `FromLane` маршрута (соседние полосы зоны на других
  сегментах пропускаются). Поездка без маршрута при просмотре очереди уходит в хвост, не считаясь отложенной (`SpawnDeferredTicks` не растёт).
- **Навигация** - `RuleEnv.NextLane` (6.2) и `RouteNav.Advance/AssignConnectors` (6.3). Продвижение курсора: connector -> обычная полоса: `++`;
  обычная -> connector: `++`, если connector из маршрута либо ведёт в тот же `DirSeg`, что следующая обычная полоса маршрута; иначе
  `VehicleFlags.RouteMissed` (маршрут уже не используется), а в конце фазы 7 (`AssignConnectors`) маршрут освобождается, `Route = -1`,
  `Reroutes++`, машина встаёт в `Rerouting`. Конец маршрута без прибытия (проскочили `DestS`) тоже промах. Connector по умолчанию
  (`RuleEnv.DefaultConnector`) - первый по порядку `LaneNext` среди «не разворот и не тупик», затем «не разворот», затем любой; без PRNG.
  Перемаршрутизация со стартом на connector'е строит маршрут от полосы за ним, `RouteCursor = -1` (connector в маршрут не входит).
- **MOBIL** (`RuleEnv.RouteDesiredLane`): полоса, с которой маршрут входит в ближайший connector; на последнем сегменте - `DestLane`
  (иначе машина на соседней полосе не прибыла бы). Принудительная смена по-прежнему проверяет только безопасность (упрощение §6.4: без
  `A_route`/`D_prep`); если перестроиться не успели - обычный промах, машина не стоит.
- **stuck**: исключение `Route == -1` из §11 core-api не применяется - такая машина едет по умолчанию.
- **Ёмкости** (измерено на s1k/s10k/s100k, `gravity α=1`): средняя длина индивидуального маршрута 41 / 68 / 149 шагов (≈ 29·scale),
  магистрали 14 / 27 / 68 шагов; на s1k живо ≈ 100 k шагов (43 k машины + 34 k магистрали), пик занятых слотов 3 199 из 8 192. Формула
  в `scenario-format.md` §2.1.
- **Известное ограничение**: стоимость поиска без иерархии. На s100k магистраль стоит ≈ 9 k раскрытий, бюджет раскрытий
  `256·PathfindBudgetPerTick` пропускает ≈ 7 промахов кэша на тик - при нарастании 100 k машин за 600 с (≈ 8 поездок/тик) очередь маршрутов
  отстаёт (раздел 9). s1m при ≈ 470 шагах на маршрут требует ≈ 4 ГБ арены - нужны оконные маршруты либо иерархия.

- **Запас**: `EntryCap = CapFor(count)` — канонический (ступенька лестницы, см. §9.2; прежняя формула `count + max(4, count/4)` зависела от момента раскладки); дописывание новой строки идёт, пока после него остаётся `Cap >= Count + 4`, иначе — перестройка. Общие массивы `Entries/Exits/Matrix` — `1.5 × начальная сумма + добавка`
  (1024 / 1024 / 65 536 элементов): у малых сетей матрица растёт квадратично, `×1.25 + 256` исчерпывалось за 10 дорог. Перестройка
  раскладки пересчитывает запасы от текущих счётчиков и сортирует входы/выходы по DirSeg заново; не влезла — `Disabled` (запросы H2 пойдут

### Уточнения по факту реализации H2 (`Routing/OverlaySearcher.cs`)

- **Файл и API**: `OverlaySearcher(net, graph, overlay?)`; `overlay == null` или `Disabled` = плоский A* на тех же структурах (`levels = 0`, эталон тестов).
  `Query(startLane, startS, destLane, destS, plan, out len)` (семантика `RouteBuilder.Build`: стоимость старта, `u0 == goal`, не-нормальные полосы),
  `Search(u0, startG, goal, ...)`, `Unpack(a, b, q, out, len)`, `ExpandPlan(plan, path, out len)` (полное развёртывание стеком, без рекурсии),
  `Route(...)` = запрос + развёртывание + раскладка на полосы. План — `DirSeg | level << 28` от старта к цели (не стек: порядок «вперёд»; стек
  из него H3 получит разворотом), у первого элемента уровень 0. `RouteBuilder.LayoutLanes` получил статическую перегрузку (net, graph), её и зовёт `Route`.
- **Правило уровня уточнено**: `q(v) = max ℓ ≤ min(Levels, CutLevel(v))`, при котором ячейка конца `v` не содержит старт и цель. Без ограничения
  `CutLevel(v)` у вершины, чей конец лежит в ячейке выше её собственного уровня границы, нет входа в матрицу этого уровня (`EntryIdx = −1`); спека
  в таком случае раскрывала бы дугами графа (медленно). Ограничение даёт тот же результат быстрее; запасной вариант «`r == −1` → дуги графа» оставлен.
- **Развёртывание**: допустимы вершины `x == b` или `CutLevel(x) < q` (внутренние для ячейки `cell_q(EndNode a)`); другие выходы ячейки не раскрываются.
  Те же `IndexedHeap4`, штампы и эвристика, что в запросе; буфер результата `UnpackCap = 256` (спека: `unpack_cap = 64`, предел — решение H3).
  Стоимость развёрнутой дуги = клетка матрицы (тест на 4 310 дугах, допуск `1e-3·c + 0.01`). Ничья между равными путями может дать другую цепочку, чем у кастомизации.
- **Работа**: +1 за каждый просмотренный элемент (дуга графа или клетка матрицы, включая `+∞`); `WorkCap` (дефолт `4·DirSegCapacity`, свойство; в `RoutingDesc`
  добавит H3) → `SearchStatus.ExpansionCap`. Накопительные `Queries/TotalWork/TotalExpanded/Unpacks/UnpackWork` — для метрик H3. `TryCreate` отклоняет сети с `DirSegCapacity ≥ 2^28`.
- **Тесты** (`OverlaySearcherTests`, 1 000 пар полос, seed 2026/7, допуск `1e-3·cost + 0.01 с`): стоимость плана = стоимость развёрнутого пути (пересчёт по дугам графа) =
  независимый `AStarSearcher` этапа 1, статические веса и после `RecalcCosts` со случайным `SpeedRatio` + полная волна; конфигурации s10k L1 (cell 1000), s10k L3 (cell 300),
  s100k L2 (cell 1000) — все зелёные. Также: ленивое развёртывание = полное, плоский режим даёт то же число раскрытий, что A* этапа 1, побитовый детерминизм, 0 B на запрос+развёртывание+раскладку.
- **Замер** (Release, один прогон, 1 000 пар, `TC_QUERY_TIMING=1 dotnet test -c Release --filter Timing_OverlayVsFlat`; сеть из `scenarios/*.json`):

  | | запрос по оверлею, мс (медиана / p95) | + полное развёртывание | плоский на `IndexedHeap4` | плоский A* этапа 1 | раскрытий оверлей / плоский (медиана) | релаксаций оверлей / плоский (медиана) |
  |---|---|---|---|---|---|---|
  | s10k (DirSeg 5 876, L1, cell 1000) | 0.079 / 0.217 | 0.084 / 0.233 | 0.149 / 0.712 | 0.131 / 0.615 | 317 / 964 | 3 182 / 2 602 |
  | s100k (DirSeg 36 006, L2, cell 1000) | 0.342 / 0.854 | 0.391 / 1.004 | 1.058 / 4.966 | 0.850 / 4.209 | 668 / 5 524 | 18 703 / 14 899 |

  Критерий «работа запроса на s100k ≥ 3× меньше плоского»: по раскрытиям выполнен (8.3× по медиане, 17× по p95), по релаксациям — **нет** (оверлей ≈ 1.26× больше):
  строка матрицы просматривается целиком (до 96 выходов уровня 2, большая часть `+∞` или дальних), тогда как у плоского ≈ 2.7 дуги на вершину. Выигрыш по времени
  (медиана ×3.1 к IndexedHeap4 и ×2.5 к A* этапа 1 на s100k, p95 ×5.8 / ×4.9; s10k ×1.9 / ×1.7) даёт короткая куча (раскрытия дороже релаксаций). Это вход для H4 (рёбра
  с `+∞` можно пропускать списком достижимых выходов строки; ALT на верхнем уровне).

Совместимость с этапом 1 не держится: удалены `RoutePool`, `RouteCache`, `RouteBuilder` (магистрали, `GetTrunk`, `ComposeViaTrunk`), `ZoneData.HubNode`

счётчики `PathfindCacheHits/RouteCompactions/RouteCacheSkips` и `SimStats.PathfindCacheHitRate`. §3 (кэш по парам зон), §4.1-4.3 и бюджет раскрытий
в §3 заменены §9; `AStarSearcher` (`AStar.cs`) остался только как независимый эталон тестов (`levels = 0` — `OverlaySearcher` без оверлея).

- **Файлы**: `Routing/RouteStore.cs` (слоты, окна, арена плана), `Routing/Router.cs` (`Build`, `Refill`, `RemainingCost`, `SyncGraph`; метрики пишет прямо
  в `World.Counters`, потому что запросы идут и из фаз 2b/8b — автобусы), `Routing/RouteLayout.cs` (`LayoutLanes`, перенесён из `RouteBuilder`),
  `RoutePhase.cs` (фаза 3), `RouteNav.cs` (`QueueRefill`, `RefillLate`). `World`: `Routes: RouteStore`, `Graph: RouteGraph`, `Router`, `Overlay?`, `RefillQueue`.
  `Router` создаётся в `WorldBuilder.BuildOverlay` после оверлея (поисковику нужна ссылка на него); без оверлея (`levels = 0`) — плоский поиск.
- **Пределы из H2 приняты**: `UnpackCap = 256` — константа буфера развёртывания (`OverlaySearcher.UnpackCap`), а не `unpack_cap = 64` из §9.5: на уровне 3
  (ячейка 16 км, ~100 сегментов) 64 дало бы ложные промахи; больше 256 → `PathTooLong` → промах. `WorkCap` вынесен в `RoutingDesc.QueryWorkCap`
  (JSON `routing.query_work_cap`, 0 = `4 · DirSegCapacity`, значение H2 по умолчанию); превышение — `NoPath`.
- **Окно**: `WindowSteps = 16` → ≤ 8 DirSeg (`maxDirs = (W + 1) / 2`), раскладка `2k − 1` шагов. Начальное окно: запрос → план → стек в обратном порядке →
  `Materialize` снимает элементы, пока в буфере не `maxDirs` DirSeg (элементы уровня q > 0 разворачиваются `Unpack` от последнего DirSeg буфера);
  `LayoutLanes` (цель — `DestLane`, если стек пуст, иначе первая полоса последнего DirSeg), остаток стека → `SetPlan`.
- **Дозаполнение** (`Router.Refill`): сохраняется префикс — `[Cursor, Cursor+1]` (текущая обычная полоса и connector), для курсора на connector'е — один
  `[Cursor]`, для `Cursor = -1` — пусто; остальные шаги заново раскладываются из «DirSeg оставшихся нормальных шагов окна + новые из стека» до заполнения
  слота. Курсор после дозаполнения 0 (или −1), поэтому для машин на connector'е нормальные полосы окна стоят на **нечётных** индексах: проверки вида
  `(Cursor & 1) == 0` неверны (убрана из `Step3.CheckRoutes`). Повторная раскладка может поменять connector'ы дальше `Cursor+1` — машина их ещё не выбрала,
  а `NextConn` (индекс полосы, не шага) не трогается; несовпадение `Steps[Cursor+2]` и `ToLane` connector'а допустимо и раньше (§14).
  Окно, в которое нечего добавлять (уже `capDirs`), — успех без изменений; курсор на последнем шаге, развёртывание не удалось или нет места под план →
  `false` → `RouteMissed` (маршрут освободит `AssignConnectors`, машина встаёт в `Rerouting`).
- **Очередь дозаполнения**: ставит `RouteNav.QueueRefill` из `AssignConnectors` (конец фазы 7, обход всех машин и так есть), а не из `Advance` (там нет `World`):
  `PlanCount > 0` и впереди ≤ `RefillAhead = 3` нормальных шагов окна. `RefillQueue` — `RingBuffer<RefillEntry>` (индекс + поколение) на `MaxVehicles`,
  флаг `VehicleFlags.RefillQueued` исключает дубли и поэтому переполнения быть не может. Фаза 3 обрабатывает всю очередь первой, затем обнуляет
  `Router.WorkThisTick` — дозаполнения в бюджет запросов не входят.
- **`RefillLate`**: считается в `ProcessMiss`, если у маршрута непустой план и курсор на последнем шаге окна (`Cursor ≥ WinCount − 1`) — то есть машина дошла до
  конца окна без дозаполнения. Промах с другой причиной (неудавшееся развёртывание, нет места) на другом шаге в `RefillLate` не попадает, но даёт `Reroutes++`.
- **`RuleEnv`**: `RouteAccess` = (`WinCount`, `PlanCount`, `Window`, `Width`), индекс шага `r · Width + c`; `RouteDesiredLane` на последнем шаге окна при
  `PlanCount > 0` возвращает −1 (полосу прибытия не навязываем). Остальная навигация (`NextLane`, `Advance`) не менялась.
- **Бюджеты** (`RoutePhase.Budget`): запрос допускается, если `Served < pathfind_budget_per_tick` и `WorkThisTick < work_budget_per_tick`; 0 в `RoutingDesc` = без
  ограничения. Проверка между запросами, первый запрос тика всегда выполняется. Работа запроса = релаксации поиска + релаксации его развёртываний.
  Плановые запросы (дрейф) ограничены долей `1/TimedBudgetDivisor = 1/4` и от числа запросов, и от `work_budget_per_tick` (2.4a: без лимита по работе на s100k
  запрос стоит 17-23 тыс. релаксаций, плановые съедали ~половину бюджета 400 тыс. и поездки голодали, рампа не завершалась; `RouteDeferred` - сумма по
  тикам числа ждущих поездок, он только показывал очередь).
  Порядок фазы: дозаполнения → проверка дрейфа → промахи → плановые (доля 1/4) → поездки → пересчёт весов → волна. Пересчёт весов теперь **после** запросов
  (в §9.6 так и записано; на этапе 1 стоял в начале фазы): запросы тика видят веса прошлого пересчёта.
- **Дрейф** (§9.7): `EnqueueTimed` каждый тик берёт машины `i % 1200 == Tick % 1200` (как раньше), пропускает машины не на обычной полосе, с `Cursor < 0`, без
  `DestLane` и с остатком сегмента < 80 м, затем (`TimedChecks++`) считает `Router.RemainingCost` — остаток текущего сегмента + окно от курсора + стек плана
  (`q = 0`: `SegCost + ArcCost`, `q ≥ 1`: `Overlay.ArcCostAt`, клетка матрицы O(1)) — и сравнивает с `max(PlanCost − (Tick − PlanTick)·dt, 0)·(1 + timed_drift) +
  timed_drift_abs`. Порог `TimedMinRemaining = 1000 м` этапа 1 убран (его заменяет абсолютная добавка 20 с). Превышение → запись `Kind = Timed` (`TimedTriggered++`).
  Обработка записи: запрос от текущей позиции; принимается, если `PlanCost` нового < остатка·0.9 (`TimedReroutes++`), иначе слот нового освобождается, а у старого
  `PlanCost/PlanTick` переустанавливаются на текущий остаток (**расхождение со спекой**: без этого повторная проверка срабатывала бы каждые 60 с на
  том же дрейфе). Остаток включает долю текущего сегмента, потому что `PlanCost` содержит `SegCost(u0)·(1 − s/L)`.
- **Автобусы**: `BusDispatch`/`BusStopPhase` зовут тот же `Router.Build` (без зон и тика кэша); маршрут от остановки к остановке почти всегда целиком в окне
  (`PlanCount = 0`).
- **`BuildRoad`**: `GrowOverlay` теперь всегда пересобирает граф и возвращает веса по загрузке (`Rebuild` + `RecalcCosts`), не только при оверлее; `Router.SyncGraph`

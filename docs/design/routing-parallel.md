# Параллельные запросы фазы 3 (задача 5.2, ADR-0032)

- Статус: спецификация, 2026-10-28 (агент 169, архитектор). Блок `docs/plan/stage5-plan.md` §5.2, резерв `scale.md` §7.
- Опирается на: ADR-0009 и `routing.md` §9.4–9.8 (оверлей, запрос, `RouteStore`, фаза 3), ADR-0017 (`WorkerPool`, контракт параллельной фазы),
  `scale.md` §2, §8 (модель на 4 потоках, правила детерминизма), заметки агентов 159 и 165 (`agents.md`).
- Решения владельца: до 4 потоков симуляции; хэш не зависит от числа потоков; 0 B/тик; Парето, ≤ 2 итераций подбора на задачу.
- Кода в `src/` эта спецификация не меняет; задачи — §8.

## 0. Коротко

**Идея: «спекулятивный пакет + последовательный повтор».** Запросы маршрутов тика собираются в пакет кандидатов в порядке очередей
(как сейчас). Поиски пакета считаются параллельно на воркерах, каждый в своём scratch. Затем идёт **тот же** последовательный цикл
фазы 3, что и сейчас. Только вместо вызова `Router.Build` он берёт готовый результат кандидата. Бюджет, `Deferred`, выделение слотов,
счётчики и `route_deferred` считаются в этом цикле по фактической работе зафиксированных запросов. Значит, выбор тот же, что у
последовательного кода, побитово. Посчитанное сверх бюджета отбрасывается.

| Вопрос | Решение |
|---|---|
| Что параллельно | `OverlaySearcher.Query` + `Materialize` (развёртывание первых DirSeg) + `RouteLayout.LayoutLanes`: чистая функция от входа запроса, графа и оверлея |
| Что последовательно | дозаполнение окон, `EnqueueTimed`, сбор пакета, фиксация (слоты `RouteStore`, арена плана, поля машин, поездки, счётчики), пересчёт весов, волна кастомизации |
| Порядок фиксации | FIFO: порядок обхода `Rerouting`, затем `PendingTrips`, ровно как в нынешнем `RoutePhase` |
| Бюджет | проверяется в цикле фиксации по `LastWork` зафиксированных (как сейчас между запросами); лишнее отбрасывается |
| Нет результата для кандидата | цикл фиксации считает его сам, на scratch воркера 0. Результат не зависит от размера пакета и числа потоков |
| Хэш | побитово прежний: все golden и корпуса сейвов без пересъёма |
| Память | ≈ 37 Б × `DirSegCapacity` на воркер: s100k ≈ 2.4 МБ, s1m ≈ 24 МБ на воркер |
| Ожидаемо (s100k, 4 потока) | фаза 3 mean 4.76 → ≈ 2.0–2.3 мс; tick p95 −3…−3.5 мс. **K1 (15 мс) этим не берётся**: §7 |

## 3. Схема фазы 3 после изменения

```
3.1  RefillWindows                      последовательно, как сейчас (все, без бюджета)
3.2  WorkThisTick = 0; EnqueueTimed     последовательно, как сейчас
3.3  Collect  (A)                       последовательно: кандидаты в порядке обхода, без изменения очередей
3.4  Compute  (B)                       WorkerPool: по кандидату на элемент (чанк 1), свой RouteScratch на воркер
3.5  Replay   (C)                       нынешние RerouteVehicles + RouteTrips; Build -> Commit(результат кандидата)
3.6  RouteDeferred, RecalcWeights, RunCustomizeWave, PlanCompactions   как сейчас
```

### 3.1 Разделение `Router.Build` (задача P1)

- `static RouteCompute.Run(in RouteQuery q, NetworkStore net, RouteGraph g, Overlay? ov, RouteScratch s, ref QueryResult r)` — чистая
  функция. Делает `Query`, `Materialize(_maxDirs)`, `LayoutLanes` в буферы `s`. Пишет только `s` и `r`. Мира (`World`) не получает,
  поэтому до счётчиков и хранилища дотянуться не может. Это и есть проверяемый контракт ADR-0017 п. 2, и прямой аналог
  `fn compute(&Graph, &Overlay, &mut Scratch) -> QueryResult` в Rust.
- `RouteQuery`: `StartLane`, `StartS`, `DestLane`, `DestS` (вход `Build`, ровно как сейчас).
- `QueryResult` (SoA-массивы по номеру кандидата): `Stage` (`QueryFail` | `MaterializeFail` | `LayoutFail` | `Found` | `Overflow`),
  `Cost` (`Searcher.PlanCost`), `QueryWork`, `Expanded`, `Unpacks`, `UnpackWork`, `StepCount`, шаги окна в
  `Steps[j·(WindowSteps+2) ..]`, стек плана — `(Worker, PlanOff, PlanLen)` в арене плана воркера.
  `Overflow`: стек не влез в остаток арены воркера. Фиксация считает такой запрос сама (§4.2).
- `Router.Commit(in RouteQuery q, ref QueryResult r, long tick, out RouteHandle h)` повторяет хвост нынешнего `Build`.
  Шаги по порядку:
  1. `SyncGraph()`: no-op после §4.5.
  2. Пул полон (`AliveCount >= Capacity`) → `Deferred`, без счётчиков и работы (как сейчас до запроса).
  3. `PathfindQueries++`, `PathfindWork += QueryWork`, `PathfindExpandedNodes += Expanded`, `WorkThisTick += QueryWork`.
  4. `PlanUnpacks += Unpacks`, `UnpackWork += UnpackWork`, `WorkThisTick += UnpackWork`.
  5. `Stage != Found` → `RouteFailed++`, `NoPath`.
  6. `TryAllocate`, затем `SetPlan`, копия окна, `PlanCost`, `PlanTick`. Неудача → `Deferred`, как сейчас.
- `Router.Build` = `RouteCompute.Run` на scratch воркера 0 + `Commit`. Автобусы и тесты не меняются.
  Счётчики при частичном `Materialize` нужно сохранить как сейчас: сюда входят развёртывания до сбоя.

### 3.2 Сбор пакета (A)

Обход повторяет фильтры нынешнего цикла **до вызова `Build`**. Состояние при этом не меняется.

- `Rerouting`, `k ∈ [0, q.Count)` через `q.At(k)`:
  - **Timed**: живой, `Route ≥ 0`, обычная полоса, без `RouteMissed`, не просрочен (`TimedExpiryTicks`), до конца сегмента
    ≥ `TimedMinSegmentRemaining`, курсор в окне. Кандидат: `(Lane, S, DestLane, DestS)`. Не больше `timedCap` по числу.
    Доля работы `timedWorkCap` при сборе не известна: её решает повтор.
  - **Miss**: живой, `Route < 0`, `Lane ≥ 0`, `ReadyTick ≤ Tick`. Старт — как в `RerouteVehicles` (на connector'е — `ToLane`, `S = 0`).
    `ToLane < 0` — не кандидат.
- `PendingTrips` в порядке очереди (`!HasRoute`):
  - Точка прибытия — `Destinations.Pick` на **копии** `w.RngRouting`. Это struct `Pcg32`, 0 Б.
  - Старт — `OpenZoneLane(fromZone, (Tick + ToZone) % count)`, как сейчас. Зоны без полос пропускаются.
- Предел числа кандидатов: `K = min(MaxCandidates, MaxQueries, Kwork)` (Timed среди них — не больше `timedCap`), где:
  - `Kwork = ⌈1.25 · MaxWork / avgWork⌉ + Workers`;
  - `avgWork` — скользящее среднее работы зафиксированного запроса (производное, вне хэша и сейва; при `MaxWork = ∞` предела нет);
  - `MaxCandidates` — константа ядра 256 (`RouteBatch.MaxCandidates`, тестовый хук).
  - `K` влияет только на скорость, не на результат (§4.2).
- Пакет пуст → B и C не нужны: идёт нынешний цикл (он увидит пустые очереди или неготовые записи).

### 3.3 Счёт (B)

- `RouteQueryJob : IRangeJob` предвыделен в `Create`. Элемент — позиция в массиве порядка `Order[0..K)`. Воркер `w` берёт `RouteScratch[w]`.
- Порядок раздачи — **по убыванию оценки цены**: евклидово расстояние старт–цель (`EndPos`), ничьи по номеру кандидата
  (LPT, меньше хвост ожидания). Порядок раздачи на результат не влияет: результат кандидата не зависит ни от воркера, ни от соседей.
- Нужен `WorkerPool.Run(job, count, chunkSize)` с `chunkSize = 1`. Сейчас `ChunkSize` = 256 — константа. При 11 запросах в тик
  весь пакет ушёл бы на один воркер (lessons: «`ChunkSize` пула — 256 элементов»). Без пула (`threads = 1`) — последовательно на воркере 0.

### 3.4 Повтор и фиксация (C)

Нынешние `RerouteVehicles`, `TimedReroute`, `RouteTrips` без изменений логики. Каждое место `rt.Build(...)` заменяется на
`rt.BuildFromBatch(in q, ...)`:

1. Следующий кандидат пакета `j` (курсор идёт по порядку сбора) совпадает с `q` по ключу (`StartLane`, `StartS`, `DestLane`, `DestS`,
   побитово) и его `Stage ≠ Overflow` → `Commit(q, result[j])`.
2. Иначе (кандидат пропущен, пакет кончился, `Overflow`, ключ разошёлся) → `RouteCompute.Run` на scratch воркера 0, затем `Commit`.
   Счётчик `BatchInline++` — диагностика вне хэша.
3. Кандидаты, которые повтор прошёл, не взяв (Timed ушёл в хвост по `timedWorkCap`, запись отброшена, бюджет кончился), — `BatchDiscarded`.

## 4. Детерминизм

### 4.1 Почему хэш тот же
1. Результат `RouteCompute.Run` — функция от `(RouteQuery, граф, оверлей, сеть)`. Граф, оверлей и сеть между 3.3 и концом 3.5 не
   меняются (§4.5, §6). Scratch воркера влияет только на скорость. Всё, что читается, сначала перезаписывается: штамп `_searchId`,
   `Clear` кучи. Вещественная арифметика одна и та же на любом потоке (core-api §9, без FMA; то же допущение, что в ADR-0017).
2. Повтор (C) — тот же последовательный код в том же порядке, с теми же проверками бюджета. Он подставляет результат, равный тому,
   что вернул бы `Build` в этой точке: ключ совпал, вход тот же. Значит, состояние после фазы 3 побитово равно нынешнему.
3. Всё, что зависит от порядка, делается только в (C): слоты `HandlePool` (free-list), арена плана и `Compact`, `Free` старого маршрута
   при `TimedReroute`, `RemoveAt` поездок, `RngRouting`, счётчики.

Отсюда: хэш не зависит **ни от числа потоков, ни от `K`, ни от `MaxCandidates`, ни от порядка раздачи**.
Тест — сравнение с режимом «пакет выключен» (`MaxCandidates = 0`: каждый запрос считается в (C), это ровно нынешний код).

### 4.2 Бюджет и лишняя работа
- Бюджет (`Budget.Has`: `Served < MaxQueries && WorkThisTick < MaxWork`, доли Timed `timedCap`/`timedWorkCap`) проверяется в (C)
  до каждого кандидата, а `WorkThisTick` растёт на `QueryWork + UnpackWork` зафиксированных. Это ровно нынешняя семантика
  «проверка между запросами, запрос не прерывается».
- Если (C) остановился (`Stopped`), посчитанное за точкой остановки **отбрасывается**. Перенос на следующий тик не делается (P4, §8).
  На s100k при полной загрузке бюджет не ограничивает (спрос 258 k < 400 k), лишней работы ≈ 0. Лишняя работа появляется на рампе
  и на s1m. Её ограничивает `Kwork` (`avgWork` × 1.25).
- Пакет кончился, а бюджет ещё открыт → (C) досчитывает сам, на главном потоке (§3.4 п. 2). Результат прежний, теряется только
  параллельность. Если `BatchInline` > 10% работы (замер P3), нужны раунды (P4): A–B–C повторяется от точки, где (C) встал.

### 4.3 Порядок фиксации и `route_deferred`
- Фиксация — в порядке FIFO очередей: `Rerouting` (Miss и Timed вперемешку, как стоят), потом `PendingTrips`. Номера слотов
  `RouteStore` выдаются в этом порядке. Освобождение старого маршрута в `TimedReroute` происходит до следующего `TryAllocate`, как сейчас.
- `Deferred` (пул полон или `SetPlan` не нашёл места): (C) ставит `Stopped`, запись остаётся головой очереди, остальные результаты
  отбрасываются. `RouteDeferred += Trips.Unrouted` — без изменений.
- `NoPath`: Miss → в хвост с `RerouteRetryTicks`; поездка → `RemoveAt`, `TripsDropped`, `TripLegs.OnTripDropped`. Как сейчас.

### 4.4 PRNG
`Destinations.Pick` в (A) вызывается на копии `w.RngRouting`. Последовательность вызовов `Pick` в (C) та же: те же поездки, тот же порядок,
`Rerouting` PRNG не трогает. Поэтому значения совпадают, и ключ кандидата совпадает. Реальный `w.RngRouting` двигается только в (C).
Если (A) и (C) разошлись (ошибка фильтра), это не ошибка результата: ключ не совпадёт, запрос посчитается в (C). Debug-проверка
`BatchMismatch == 0` на тестовых сценариях ловит такое расхождение.

### 4.5 Граф до пакета
`Build` начинается с `SyncGraph` (перестройка графа после `BuildRoad`). Последовательный код делает её при первом вызове `Build`
в тике. В новом коде (A) вызывает `rt.SyncGraph()`, если собрал хотя бы одного кандидата. Первый кандидат (A) — это и есть первый
вызов `Build` последовательного кода, потому что фильтры (A) повторяют условия до `Build`. Значит, момент синхронизации тот же.
`Commit` вызывает `SyncGraph()` — это no-op. Пересчёт весов (`RecalcWeights`) и волна идут после (C), как сейчас.

## 5. 0 B/тик и память

- Всё выделяется в `Create` (и при росте сети, `OnNetworkGrown`):
  - `RouteScratch[Workers]`: `OverlaySearcher` без `_plan/_path/_stack`, плюс `_plan`, `_stk`, `_dirs`, `_steps`, `_ubuf` роутера;
  - арена плана воркера 16 384 `int`;
  - массивы кандидатов и результатов на `MaxCandidates`;
  - `RouteQueryJob`.
  Делегатов и замыканий нет (ADR-0017). `RouteScratch[0]` — нынешние буферы `Router` (главный поток), лишней памяти нет.
- Рост сети (`BuildRoad` → `DirSegCapacity` не меняется: это `2 · net.Segments.Length`, ёмкость сценария) — пересоздавать не нужно.
- Цена на воркер (`DirSegCapacity = 2 · max_segments`): поиск 29 Б (`_gs` 4 + `_parent` 4 + `_parentLevel` 1 + `_seen` 4 + `_closed` 4 +
  куча 12) + роутер 8 Б (`_plan`, `_stk`) = **37 Б/DirSeg**.

## 6. Кастомизация (`OverlayCustomize`)

- Волна `RunWave` пишет `Matrix` по строкам на месте, а запрос читает `Matrix`. Это гонка, поэтому волна **остаётся последовательной
  и после (C)**, как сейчас (шаг 5 `RoutePhase.Run`). Запросы тика видят матрицы после волны прошлого тика (routing.md §15, как сейчас).
- `RecalcWeights` (`Graph.RecalcCosts`, `RefreshSignalCosts`, `Rebuild`) тоже после (C). `Overlay.AfterRecalc` — там же.
- `OnNetworkGrown`, `RebuildAfterEdit`, `RebuildAll` — из команд (фаза 1), до фазы 3. Пересечения нет.
- Волна — следующий кандидат на воркеры, прежде всего для s1m. Её бюджет 2 M релаксаций ≈ 30 мс последовательно на тик волны.
  Строки одного уровня независимы: строка = Дейкстра внутри ячейки, пишет свою строку матрицы. Уровень ℓ+1 читает матрицы ℓ.
  Схема та же (A–B–C): строки по курсору `(ℓ, gc, row)` считаются параллельно в буфер строки, фиксация копирует их в порядке курсора,
  пока работа < `customize_budget_per_tick`. Остановиться нужно на границе уровня. Это задача P5 со своей проверкой; в P1–P2 не входит.

## 7. Ожидаемый выигрыш и что остаётся

**Фаза 3, s100k, 4 потока** (числа §1):
- Доля запросов в работе фазы: 258 k / (258 k + 8.6 k развёртываний дозаполнений + 17.3 k волны) ≈ **0.91**.
  Остальное — дозаполнения, `EnqueueTimed`, сбор и фиксация, волна; всё последовательное.
- Ускорение параллельной части `k`: 2.5–3.0 на 4 потоках. Это ≈ 11 элементов на 4 воркера с LPT; шаг поиска упирается в память;
  у фазы 5 `k` = 1.57 на 2 потоках (ADR-0017), у фазы 4 — 2.25–2.4 на 4 потоках (S1, агенты 149 и 153).
- Амдал: `4.76 / (0.09 + 0.91 / k)`. При k = 2.5 → 2.06 мс, при k = 3 → 1.83 мс. Добавить ≈ 0.1 мс на сбор, раздачу и фиксацию.
  Итог: **фаза 3 ≈ 2.0–2.3 мс mean (−2.5…−2.8 мс)**. Предел при k = 4 — 1.51 мс.
- p95 фазы 3 (8.12 мс) падает сильнее среднего: всплески маршрутов — это пакеты запросов после пересчёта весов. Тики волны (+100 k
  релаксаций ≈ 1.7 мс) остаются последовательными.
- Tick p95 (p95/mean ≈ 1.31 в этом прогоне): **−3…−3.5 мс**, то есть s100k `off` 26.94 → **≈ 23.5–24 мс**.

**Что остаётся в тике** (mean, мс, тот же прогон): behaviour 8.59 + gate 6.67 + integrate 1.34 + snapshot 0.89 + transition 0.53 +
arrival 0.45 + прочее 0.19 = **18.7 мс** без фазы 3. На 4 потоках фазы 4–5 уже параллельны (S1, ADR-0017). Значит, K1 = 15 мс p95
в режиме **`off`** недостижим при любой фазе 3. То же предсказывала модель `scale.md` §2: «без meso K1 не берётся».
K1 в `scale.md` §0 определён на **`lod.mode = auto`** (15 k micro + 85 k Q). Модель §2 закладывала маршруты ≤ 2 мс mean «после S6».
S6 этого не дал (4.76 мс), а параллельный пакет даёт ровно эти ≈ 2 мс. **Параллельные запросы необходимы, но не достаточны.**
Второй рычаг — S7: `s100k.json` → `lod: auto, queue, micro_budget 15 000` (сейчас так только `s100k-q`, и то с `all_meso`). Вопрос В1, §9.

**s1m:** фаза 3 на рампе 20.5 мс при `work_budget` 2 M. Тот же Амдал → ≈ 8–9 мс, пропускная способность запросов ×2.3–2.6, рампа
быстрее. Дальше рампу s1m ограничивает волна (≈ 30 мс на тик волны) → P5.

## 9. Риски и открытые вопросы

**Риски**
1. **Мало элементов на тик** (11 запросов, хвост тяжёлых — до `query_work_cap` = 4 · DirSeg = 256 k релаксаций ≈ 4 мс): `k` < 2.5.
   Мера — LPT-порядок. Даже k = 2 даёт фазу 3 ≈ 2.6 мс (−2.2 мс).
2. **Скрытая общая запись в дереве `Compute`** (новый счётчик, кэш в `RouteGraph`/`Overlay`). Мера: `RouteCompute.Run` статический,
   без `World`, только явные аргументы `(net, g, ov, scratch, ref result)`; тесты хэша 1..4 потока и `MaxCandidates` 0 против 256.
3. **Расхождение фильтров (A) и (C).** Результат не ломается (ключ, досчёт), но параллельность тихо теряется. Мера: `Mismatch`/`Inline`
   в bench JSON и Debug-проверка в тестах.
4. **Лишняя работа при ограничивающем бюджете** (рампа, s1m) ест время воркеров. Мера: `Kwork` по `avgWork`; `Discarded` в отчёте P3; P4.
5. **Вытеснение воркера** в общем контейнере посреди тяжёлого запроса: главный ждёт этот элемент (ADR-0017 риск 1; с чанком 1 — не
   дольше одного запроса). Мера — та же, что у фаз 4–6: замер p95 при load ≤ 1, отчёт `uptime`.
6. **Rust-порт.** Схема ложится на `rayon`: `par_iter` по кандидатам, scratch по номеру воркера (`map_init`). Фиксация последовательная.
   Без `unsafe`.

**Открытые вопросы (с рекомендацией)**
- **В1 (владельцу). На каком режиме зачёт K1?** `scenarios/s100k.json` идёт в `lod off` (все 100 k машин — micro), 26.94 мс измерены на нём.
  Параллельные запросы дадут ≈ 23.5–24 мс, но не 15 мс. `scale.md` K1 записан на `auto`.
  Рекомендация: после P2 — S7 (`s100k.json` → `lod auto`, `queue`, `micro_budget 15 000`) и замер. Это смена поведения сценария
  (не golden-тестов): отдельный коммит, сравнение ожиданий ≥ 60 с и stuck по 3 seed.
- **В2. Перенос лишних результатов на следующий тик.** Рекомендация: не в P2. Это кэш с эпохой, ошибку эпохи тесты хэша ловят только
  на тиках правок. Делать по замеру `Discarded` (P4).
- **В3. `MaxCandidates` — константа ядра или параметр среды** (`SimRuntimeOptions`, как `WorkerThreads`). Рекомендация: константа 256
  и тестовый хук. На результат не влияет, в сценарий и сейв не идёт.
- **В4. Пороги timed-reroute** (−27% запросов, меняют поведение, `stage5-plan.md` §5.2). Рекомендация: после P3 и только если фаза 3 —
  ещё заметная часть хвоста. Отдельный ADR с before/after ожиданий.
- **В5. Пути пешеходов 3b** (`PedPhase.Route`) и параллельная волна (P5) — та же схема A–B–C. Рекомендация: по замеру, не в 5.2 для s100k.
